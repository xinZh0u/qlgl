# 图像管线设计（`<img>` / 解码 / 绘制）

> 状态：**设计（待实现）**。目标读者：要实现解码器、`blit_image`、`<img>` 布局与
> 工具链转码的人。文档站上的覆盖度清单见 [HTML5 标签覆盖与裁剪](../manual/ui/HTML5标签覆盖与裁剪.html)。

这份文档定三件事：**格式怎么分工**、**数据放在哪**、**绘制怎么落到两个后端**。
每一节都给出"为什么"和"不做什么"，因为图像是最容易把"外来数据"引进来的一块，
而这个库的红线是**外来数据必须有界**。

---

## 0. 结论摘要

| 问题 | 决定 |
|---|---|
| 自己写还是调库 | **自有解码器写 BMP / QOI / PNG；JPEG、GIF 等一律不自己写** |
| PC/移动的 JPEG/GIF | **两条路**：① 构建期转码成 QOI 嵌入（默认，运行时零依赖）；② 运行期交给**平台后端**（libjpeg-turbo / ImageIO / WIC / BitmapFactory） |
| **构建期转码** | **所有平台的默认路径**（MCU 与 PC 一样）：`qltext assets` 在开发机上解好，产物直接是**目标像素格式**（MCU 常是 RGB565） |
| MCU | **默认零解码器**：素材经构建期转成 `RAW` 放 `.rodata`，`px` 直接指向 Flash（`owned = 0`）→ 运行时零解码、零 RAM。可选开 `QL_FEAT_UI_IMAGE_DECODE` 才编进 QOI/BMP 解码器；JPEG/GIF 无后端 → 报错 |
| stb_image | **不进产线**，只做测试用的对拍 oracle |
| 像素格式 | **构建期就定型**，与显示驱动的 `QLColorFormat` 一致（MCU 常是 RGB565，PC 常是 RGB888/RGBA8888）→ 运行时**零转换** |
| 解码时机 | `RAW` 不解码；需要解码的格式在 `ql_ui_build` 时一次性解（上限 `QL_CFG_UI_IMAGE_MAX`）；**尺寸在 doc 里就有**，所以布局永远不依赖解码 |
| 绘制 | 新增 `QLDraw2D->blit_image()`；CPU 逐像素、GPU 一次纹理上传 + 一个 quad（复用现有 `mode` 分派） |
| 尺寸控制 | `object-fit` 在**绘制期**算，不动布局；`border-radius` / `clip-path` 复用现有 SDF 与 mask |
| 失败语义 | 构建期解码失败 → **明确报错**；运行期注册失败 → 明确错误码 + 占位不画（不猜） |

## 1. 目标与非目标

**目标**

1. `<img src>` 在 PC 上"贴一个真图片文件就能显示"，在 MCU 上"贴一个位图就能显示"。
2. 解码路径**完全有界**：任何输入（含畸形/超大）都不许 OOM、不许越界、不许死循环。
3. 有 alpha 的 PNG 能正确叠加（源覆盖 + 圆角裁剪）。
4. 解码结果**只解一次**，每帧只做像素搬运。

**非目标（明确不做）**

- GIF/WebP/APNG 的**动画**播放（要帧时钟 + 帧缓冲 + 循环策略；首帧可以，动画不做）。
- SVG（等于第二个渲染器，见覆盖表 §5）。
- 图片编辑、缩放算法的高质量版本（默认最近邻；双线性作为可选项，见 §6.2）。
- EXIF 方向自动旋转（PC 后端解码时由平台库处理，自有解码器不管）。

## 2. 平台分档

**构建期转码是所有平台的默认路径**，不只是 PC —— MCU 尤其需要它：把"解码"这件事
整个挪到开发机上，固件里就只剩"把像素搬到屏幕"。

| | MCU | PC / 移动 |
|---|---|---|
| 默认路径 | **构建期转码 → `RAW`（目标像素格式）** | **构建期转码 → `RAW` / `QOI`** |
| 运行时解码器 | **默认不编进去**（`QL_FEAT_UI_IMAGE_DECODE=0`） | 编进去（`=1`），另加平台后端 |
| 运行时支持的格式 | 只认"已经解好的" `RAW` | `RAW` `QOI` `BMP` `PNG` + 平台后端（JPEG/GIF…） |
| 第三方依赖 | 无 | 可选（平台库） |
| 典型用途 | 图标、位图 UI 素材、开机图 | 照片、用户内容、网络图 |
| 像素格式 | 常是 `RGB565`（每像素 2 B，Flash 减半） | `RGB888` / `RGBA8888` |
| 宏 | `QL_FEAT_UI_IMAGE` + `QL_CFG_IMAGE_*` | 同左 + `QL_FEAT_UI_IMAGE_DECODE` + `QL_FEAT_UI_IMAGE_PLATFORM` |

MCU 上两种产物的取舍（**都由构建期决定，运行时只是读**）：

| 产物 | Flash | RAM | 需要的代码 | 什么时候选 |
|---|---|---|---|---|
| **`RAW`**（已解码、目标像素格式） | `w·h·2` | **0**（`px` 指向 `.rodata`） | 无（连 memcpy 都不用） | **默认**。Flash 换 RAM，MCU 上最划算 |
| **`QOI`** | 约为 RAW 的 50–70% | `w·h·2`（解码缓冲） | ~130 行 QOI 解码 | Flash 紧张、图多、同屏少 |

> 所以"MCU 也要构建期转码"在实现上就是两条：
> ① `qltext assets --pixel-format rgb565 --format raw` 直接产出可指向 Flash 的位图；
> ② 运行时 `QL_FEAT_UI_IMAGE_DECODE=0` 时**链接期就不带任何解码器**，
> 遇到非 `RAW` 的资源是**构建期**就该报的错，运行时根本走不到。

**为什么不自己写 JPEG**：baseline 1200–1800 行、渐进式再 600 行、4:2:0/4:2:2 上采样、
restart marker、色域转换。手写 JPEG 的典型失败不是崩溃，而是**色偏**与块效应 —— 那是最难
查的一类 bug。而 PC 上系统库满地都是，MCU 上根本不需要照片。收益/风险完全不划算。

**为什么 PNG 自己写**：它的"难"只有 DEFLATE 一处，而 DEFLATE 是**无状态纯算法**
（32KB 固定窗口 + 输出直接写进目标行缓冲），可以完全有界，写完还能拿 fuzz 打。
PNG 的其余部分（chunk、5 种 filter、调色板/位深/tRNS）都是纯数据搬运。

**为什么不用 stb_image**：① 7k 行不可裁（`STBI_ONLY_*` 只裁格式入口，代码还在）；
② 整幅解码到单一 `malloc` 缓冲，MCU 不适用；③ 顺带支持 GIF/PSD/HDR，等于**扩大攻击面**；
④ 部分路径用 `float` 做颜色转换，与本库定点风格不一致。它能当测试 oracle（离线跑）。

## 3. 三个入口（入口 1 是默认，其余是增量）

```
                     ┌── ① 构建期（默认，MCU 唯一路径）
                     │    qltext assets：系统库/自有解码 → 直接转成目标像素格式（RAW）
  <img src="logo.jpg">┤                     → .rodata，px 直指，owned=0，运行时零解码
                     │
                     └── ② 运行期：ql_ui_register_image(ui, "logo.jpg", bytes, len)
                          bytes ──► 格式探测 ──► ③ 自有解码器：BMP/QOI/PNG（DECODE=1 才有）
                                            └─► ④ 平台后端：JPEG/GIF…（PC 可选，MCU 无 → 报错）
                                                │
                                                ▼
                                    QLImage{ w,h,stride,format,px }
                                                │
                                                ▼
                                    QLDraw2D->blit_image()   ← 每帧只搬像素
```

| 入口 | 场景 | 平台 | 运行时依赖 |
|---|---|---|---|
| ① **构建期转码**（`<img src>` 由 `qltext assets` 处理） | 产品 UI 素材、图标、开机图 | **MCU + PC 都是默认** | **零**（连解码器都不编进去） |
| ② 运行期注册 | PC 从文件/网络拿到图 | PC/移动 | ③ 或 ④ |
| ③ 自有解码器 BMP/QOI/PNG | PC 动态图片；MCU 想省 Flash 时用 QOI | 可选（`QL_FEAT_UI_IMAGE_DECODE`） | 编译进来 |
| ④ 平台后端 | 用户内容（照片） | PC/移动 | 系统库 |

**关键点**：入口 ① 在**开发机上**就把"解码 + 像素格式转换 + 可能还有缩放"全做完，
所以 MCU 固件里既没有解码器、也没有图片 RAM —— 只剩"指向 Flash 的指针 + 宽高"。
②③④ 是 PC 侧的增量能力，MCU 默认一个都不带。四条路互不干扰，且都由
`QL_FEAT_UI_IMAGE_DECODE` / `QL_FEAT_UI_IMAGE_PLATFORM` 在编译期裁掉。

## 4. 数据模型

### 4.1 解码结果（跨模块唯一契约）

```c
typedef enum {
    QL_IMAGE_RGB565 = 0,     /* 2 B/px */
    QL_IMAGE_RGB888,         /* 3 B/px */
    QL_IMAGE_RGBA8888,       /* 4 B/px，非预乘 */
    QL_IMAGE_A8,             /* 1 B/px，蒙版/图标 */
} QLImageFormat;

typedef struct {
    const uint8_t *px;       /* 有效数据；NULL = 还没解码或解码失败 */
    uint32_t       len;      /* 字节数 = stride * h */
    uint16_t       w, h;
    uint16_t       stride;   /* 字节/行（允许大于 w*bpp，方便对齐） */
    uint8_t        format;   /* QLImageFormat */
    uint8_t        owned;    /* 1 = 归 QLUIRoot，ql_ui_free 负责释放 */
} QLImage;
```

三件事刻意没做：

- **没有 mipmap/多级缩放**：缩放是绘制期的事（§6.2），不做纹理金字塔。
- **不预乘 alpha**：预乘能让 GPU 混合公式更简单，但会让 CPU 侧每次缩放都要反算，
  而且 `QLImage` 还要能被后端复用。统一不预乘，混合时现算。
- **`stride` 而不是"w × bpp"**：硬件对齐、行缓冲、以及"把一行解码进目标图的一行"
  都要求每行能独立寻址。

### 4.2 doc 里的资源条目

```c
typedef struct {
    uint16_t name;      /* text 池下标：资源名（"logo.png"），报错与运行期注册都靠它 */
    uint32_t off;       /* 编码字节在资源段内的偏移 */
    uint32_t len;       /* 编码字节数 */
    uint16_t w, h;      /* 构建期已知的原始像素尺寸 */
    uint8_t  format;    /* QLImageSrcFormat：BMP / QOI / PNG / RAW / 未知 */
    uint8_t  reserved;
} QLUIImageSrc;
```

- **`w/h` 存进 doc**，所以**布局永远不依赖解码**：哪怕这张图解码失败，位置和占位尺寸
  仍然是对的（画个占位框就行）。这也是将来做"惰性解码"的前提。
- **`off/len` 指向新增的 blob 段**（`QL_UI_BLOB_VERSION` → 13，`off_images` /
  `off_image_data` 两个字段）。裸机侧也可以不用 blob，让工具直接生成
  `static const unsigned char` 数组，由 `QLUIDoc.images[i]` 指过去。

### 4.3 节点怎么指向图像

`<img>` 的 `src` 存进 `node->text`（**复用**文本池下标，存的是资源名）。

- 不新增 `QLUINode` 字段（那是每个节点 2 字节的常驻成本）；
- `text` 本来就是"text 池下标"，资源名也在同一个池里，语义一致；
- 需要配套的两处特殊处理（必须写测试钉住）：
  1. `border_width_of()` / `max_content_main()` 里"文本尺寸"的判断要**排除 `<img>`**，
     否则会按资源名的宽度排版；
  2. `ql_ui_node_text()` 对 `<img>` 返回 `NULL`（名字不是要显示的文字）。

`alt` 属性暂时只存不用（没有 tooltip / 朗读），**不静默假装有**，文档里写明。

### 4.4 运行期池

```c
struct QLUIImageRT {
    QLUINodeRT *node;
    QLImage     img;      /* px == NULL 表示未解码/失败 */
    uint8_t     failed;   /* 解码失败过：不要每帧重试 */
};
/* QLUIRoot：images[] + image_count（没有 <img> 时为 NULL，零字节） */
```

## 5. 解码层

### 5.1 自有解码器

| 格式 | 要点 | 量级 |
|---|---|---|
| **BMP** | 24/32 位、8 位调色板、`BITFIELDS`（565/888）、自下而上/自上而下、行长补齐 4 字节。**不解** RLE | ~150 行 |
| **QOI** | 规范极小（index/run/diff/luma/rgb/rgba 六种 op）。适合当"构建期转码的中间格式" | ~130 行 |
| **PNG** | 见下 | ~1300 行 |

**PNG 拆成两层**

```
inflate（DEFLATE 解码）   ← 独立、可单独 fuzz
    ↓ 输出直接写到"当前行的裸字节"（不落地整幅未滤波数据）
PNG 容器（chunk / filter / 颜色转换）
```

- inflate：固定 Huffman 与动态 Huffman、`stored` 块、长度/距离码表。窗口固定
  `QL_CFG_IMAGE_SCRATCH`（默认 32KB）。**输出不缓冲整幅图**，而是按行喂给反滤波。
- PNG：`IHDR/PLTE/tRNS/IDAT/IEND`；位深 1/2/4/8/16；颜色类型 0/2/3/4/6；filter 0–4
  （`None/Sub/Up/Average/Paeth`）；`interlace` 为 1 时 **明确报错**（Adam7 不做，占位说明）。
- 输出：按目标 `QLImageFormat` 直接转换（调色板展开、16→8 取高字节、灰度复制三通道、
  alpha 直通）。

### 5.1.1 零解码器构建（MCU 默认）

```c
/* qlconfig.h */
#define QL_FEAT_UI_IMAGE         1
#define QL_FEAT_UI_IMAGE_DECODE  0     /* 不编入 BMP/QOI/PNG 解码器 */
```

- 只认 `QL_IMAGE_SRC_RAW`（构建期已解好的位图），`px` 直接指向 `doc` 的资源段；
- `QLImage.owned = 0` → `ql_ui_free` 不碰它（数据在 `.rodata`）；
- 链接期省下：inflate + PNG 约 1.3K 行、QOI 130 行、BMP 150 行 —— 对 64–256 KB Flash
  的 MCU 是实打实的一块；
- 这条路径**必须有一条构建配置的测试**：`-DQL_FEAT_UI_IMAGE_DECODE=0` 下用一份 RAW
  资源跑完整布局+绘制，并且确认 `ql_image_decode()` 对 PNG 字节返回 `QL_ERR_UNSUPPORTED`。

### 5.2 平台后端接口（PC/移动）

```c
typedef struct {
    /* 返回 1 = 认识并解出来；0 = 不认识；-1 = 认识但失败（错误原因写 err） */
    int (*decode)(const uint8_t *data, size_t len, QLImage *out, char *err, size_t err_cap);
    const char *name;         /* "libjpeg" / "ImageIO" / "WIC"，报错文案用 */
} QLImageBackend;

/* 产线里由平台层调用；不设 = 只有自有解码器 */
void ql_image_set_platform_backend(const QLImageBackend *be);
```

| 平台 | 建议实现 | 备注 |
|---|---|---|
| Linux / PC | libjpeg-turbo（`jpeg_read_header` + 缩放到目标尺寸） | 顺带能解 GIF 首帧（giflib） |
| macOS / iOS | ImageIO（`CGImageSourceCreateWithData`） | 一行出 `CGImage` |
| Windows | WIC（`IWICImagingFactory`） | |
| Android | `BitmapFactory.decodeByteArray` | 走 JNI 由宿主提供 |
| MCU | **不提供** | 探测到 JPEG 魔数 → `QL_ERR_UNSUPPORTED` 并给出文案 |

后端返回的 `QLImage` 必须满足：`stride` 自洽、`len == stride*h`、`format` 在枚举内、
`w/h` 在 `QL_CFG_IMAGE_MAX_PIXELS` 内 —— **不信任第三方库的返回值**，拿回来先做一遍
校验再进绘制（这是唯一一处"外来数据"进入绘制层的关口）。

### 5.3 有界与失败语义

| 常量 | 默认 | 作用 |
|---|---|---|
| `QL_CFG_UI_IMAGE_MAX` | 8 | 一个界面最多几张图（运行期池条目数） |
| `QL_CFG_IMAGE_MAX_BYTES` | 512 KB | 单张**编码**字节上限（超出直接拒绝） |
| `QL_CFG_IMAGE_MAX_PIXELS` | 4096×4096（PC）/ 512×512（MCU） | 解码后像素数上限 |
| `QL_CFG_IMAGE_SCRATCH` | 32 KB | inflate 窗口 + 行缓冲 |

**必须显式检查的溢出**（经典漏洞，写测试钉住）：

```c
/* w * h * bpp 会溢出 32 位；先除后乘或判上界 */
if (w == 0 || h == 0) return 0;
if ((uint32_t)w > QL_CFG_IMAGE_MAX_PIXELS / (uint32_t)h) return 0;   /* 除比乘安全 */
if ((uint64_t)w * bpp > 0xFFFFu) return 0;                            /* stride 是 uint16 */
```

**失败语义**

| 时机 | 行为 |
|---|---|
| 构建期（`qltext`）解码失败 | **报错并中止**，错误信息带文件名与原因 |
| `ql_ui_build` 解码嵌入资源失败 | **报错**（`ql_ui_text_last_error()` 风格），`ql_ui_build` 返回 NULL |
| 运行期 `ql_ui_register_image` 失败 | 返回 `QL_ERR_UNSUPPORTED` / `QL_ERR_NOMEM`，**该 img 保持空框**（尺寸仍按 doc，画占位）；不要每帧重试（`failed` 位） |

## 6. 绘制层

### 6.1 接口

```c
/* QLDraw2D 新增一个函数指针 */
void (*blit_image)(QLDraw2D *self, const QLImage *img, QLRect dst,
                   const QLRect *src, uint8_t alpha);
```

- `src == NULL` → 整幅；否则取子矩形（给 `object-fit: cover` 用）。
- `dst` 是设备像素矩形（`QLDraw2D` 已经处理了 `scale_fx`、`offset`、`elem_scale`）。
- 缩放由后端负责（`dst` 与 `src` 尺寸不同就是缩放）。
- 裁剪/遮罩**不在接口里**：沿用 `d2d->set_clip()` 与 `set_mask()`，所以
  `overflow: hidden`、`border-radius`、`clip-path: circle()` 自动生效，不用写第二套。

### 6.2 CPU 实现要点

| 项 | 决定 | 为什么 |
|---|---|---|
| 缩放 | **默认最近邻**；`QL_CFG_IMAGE_BILINEAR=1` 时双线性 | 最近邻的 MCU 成本是双线性的 1/4，且 UI 素材大多整数倍缩放 |
| alpha | 源覆盖：`out = src*a + dst*(1-a)`，逐像素用 8 位定点 | 与 `fill_rect(alpha)` 同一套混合，结果与形状一致 |
| 格式矩阵 | 源 `RGB565/RGB888/RGBA8888/A8` × 目标 `RGB565/RGB888/ARGB8888/L8` | 12 种组合，用 `switch` 特化热路径（照抄 `qlcanvas.c` 已有的形状填充套路） |
| 圆角 | 复用 `fill_round_rect` 的 SDF 判定（每像素算到圆角矩形边界的距离） | 不要新写一套抗锯齿 |
| 空图 | `img->px == NULL` → 画一个 1px 虚线框的占位（仅 `QL_CFG_IMAGE_PLACEHOLDER=1`） | 让"图没加载"肉眼可见 |

### 6.3 GPU 实现要点

- 上传：每个 `QLImage` 一次 `glTexImage2D`（`GL_RGB` / `GL_RGBA` / `GL_R5G6B5`），
  纹理 id 缓存在 `QLImage` 的旁边（`QLUIImageRT.gl_tex`，由后端私有表维护，不进公共结构）。
- 绘制：新增 `mode = 3`（图片），复用现有的 `emit_quad` + `u_atlas` 采样器；
  **uv 必须用目标矩形的角点算**（和 `emit_quad_shear` 里"剪切前角点"是同一个坑）。
- 混合：`GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA`；**不预乘**（与 CPU 侧一致）。
- 不做：mipmap、各向异性、sRGB 转换、纹理压缩（这些是"PC 全有"之后的事）。

## 7. 布局层

### 7.1 内在尺寸（intrinsic size）

`<img>` 是"用内在尺寸排版"的节点，和文本节点同构。两处必须改：

| 位置 | 现状 | 改法 |
|---|---|---|
| `border_width_of()` | `node->text != NULL` ⇒ 按文本宽度 | 先判 `tag == IMG` ⇒ 用 `style->width` 或资源 `w` + padding/border |
| `max_content_main()` | 同上 | 同上，按行/列取 `w` 或 `h` |

没有 `width`/`height` CSS 时用资源的 `w/h`；有 CSS 宽度时高度按 CSS 或按宽高比
推算（`aspect-ratio` 不做，直接 `h = w * 固有h / 固有w`，整数运算，避免浮点）。

### 7.2 `object-fit`

**在绘制期算目标矩形，不动布局**：

| 值 | 目标矩形 |
|---|---|
| `fill`（默认） | `dst = 内容盒`（允许变形，与浏览器默认一致） |
| `contain` | 等比缩到**完全装进**内容盒，居中 |
| `cover` | 等比放大到**盖满**内容盒，居中，`src` 取中间那块 |
| `none` | 原始像素尺寸，居中，超出部分被 `overflow` 裁掉 |
| `scale-down` | `contain` 与 `none` 取小的那个 |

全部整数运算（用 16.16 定点算比例，最后取整），避免浮点在 MCU 上的代价。

## 8. HTML / CSS 面

```html
<img src="logo.png" alt="QLGL">
<img src="avatar.jpg" width="48" height="48">     <!-- CSS 尺寸优先 -->
<picture>                                          <!-- media 查询不做：只用兜底 <img> -->
  <source srcset="a.webp"><img src="a.png">
</picture>
<map name="m"><area shape="rect" coords="0,0,100,40" href="#a"></map>
```

- **属性白名单新增**：`src` `alt` `width` `height` `usemap`；`<area>` 用 `shape` `coords`。
  `srcset` / `sizes` / `loading` / `decoding` 静默忽略（不影响渲染）。
- **UA 默认样式**：`img { display: inline-block }`；`picture/source/map/area { display: none }`
  （只有 `img` 产生盒子；`area` 只是热区数据）。
- **`<map>`/`<area>` 热区**：命中测试时若命中 `img` 且它有 `usemap`，再按 `coords`
  判断点落在哪个 `area`（rect / circle / poly 都支持，全部整数），命中则把该 `area`
  节点当成点击目标（`click_cb` 收到的是 `area`）。**不做导航**（没有 URL 概念）。
- **`picture`**：不支持 `media`/`type` 选择，只用其中的 `<img>` 兜底那张 —— 文档里写明。

## 9. 工具链：构建期转码（所有平台的默认路径）

```bash
$ qltext assets --html app.html --css app.css --root . --out build/ \
                --pixel-format rgb565 \      # 目标设备像素格式（决定产物）
                --format raw                  # raw | qoi | png-pass
# 扫描 HTML 里所有 src，构建期解码（可用系统库/任何工具），
# 直接转成**目标像素格式**，生成：
#   build/ui_app_img_logo_raw[]   （C 数组 / .rodata）
#   build/ui_app_img.h            （名字 → {ptr,len,w,h,format} 表）
```

| 参数 | 取值 | 说明 |
|---|---|---|
| `--pixel-format` | `rgb565` / `rgb888` / `rgba8888` / `a8` | **构建期就定型**，运行时零转换。`a8` 给蒙版/单色图标 |
| `--format` | `raw` | 已解码，`.rodata` 直指；MCU 默认 |
| | `qoi` | 无损压缩，需运行时 QOI 解码（`DECODE=1`） |
| | `png-pass` | 原样嵌入 PNG，需运行时 PNG 解码 |
| `--scale` | `1` / `2` / `WxH` | **构建期预缩放**：MCU 直接拿目标尺寸，省 Flash 也省绘制期缩放 |
| `--dither` | 开关 | `RGB565` 量化时的有序抖动（默认关，避免 golden 抖动） |

三条规矩：

1. **构建期允许用任何库**（PIL / libjpeg / gdk-pixbuf）—— 那是在开发机上跑，不进固件。
2. 找不到文件 / 解码失败 / 超上限（§5.3）/ 目标格式不支持 → **构建失败**，信息带路径。
3. 同一张图在 `--pixel-format` 不同时会产出不同字节 —— 这是**故意的**：把转换代价
   留在构建期。所以 golden 基准要按目标格式分开存（或者只对 PC 格式做基准）。

## 10. 测试策略

| 层 | 手段 | 判据 |
|---|---|---|
| 解码器 | 手写最小样例（纯色 1×1、2×2 四色、调色板、带 alpha、16 位、每行补齐） | 逐字节等于期望像素 |
| 解码器 | **对拍**：脚本用 PIL 生成同样内容，比对 RGB 值 | 完全一致（QOI/BMP/PNG 都无损） |
| 解码器 | **fuzz**：随机字节 + 截断/篡改合法文件 | 只允许"返回失败"，不许崩溃/越界/OOM（ASan + UBSan 下跑 10 万次） |
| 有界 | 喂 `w=65535,h=65535` 的头部 | 直接拒绝，不分配 |
| 绘制 | 已知图案缩放到目标矩形 | 四角/中心像素抽样；CPU vs GPU 差异阈值 |
| 布局 | 无 CSS 尺寸时的内在尺寸、有 CSS 尺寸时的等比 | `border_box` 数值 |
| golden | 一页"图标 + 照片 + 圆角头像 + object-fit 四态" | 图像容差比对 |
| 工具链 | `qltext assets` 对固定输入的产出 | 生成的 C 数组逐字节稳定（可提交基准） |
| 工具链 | `--pixel-format rgb565` 的量化结果 | 逐像素等于期望（含 `--dither` 两态） |
| 构建配置 | `-DQL_FEAT_UI_IMAGE_DECODE=0` | RAW 资源能布局+绘制；PNG 字节返回 `QL_ERR_UNSUPPORTED`；目标里不含 inflate 符号 |

## 11. 内存账（举例）

| 场景 | Flash（资源） | RAM（解码缓冲） | 说明 |
|---|---|---|---|
| MCU 240×160 RGB565 背景，`RAW` | 76.8 KB | **0** | `px` 指向 `.rodata`；一张就吃掉 1/4 个 256 KB Flash，所以背景图要么缩、要么用渐变画 |
| MCU 240×160 RGB565 背景，`QOI` | ~50–55 KB | 76.8 KB | Flash 省下来了，但 RAM 吃得下才行 |
| MCU 32×32 图标 × 8（`RAW`） | 16.4 KB | **0** | 典型 UI 素材规模，这条路才现实 |
| PC 800×600 RGBA8888 | 1.9 MB | 同左（`owned=1`） | 宽松 |
| inflate 临时 | — | 32 KB（固定） | `QL_CFG_IMAGE_SCRATCH`；`DECODE=0` 时**不存在** |

> **给 MCU 的默认姿势**：`RAW` + `--pixel-format rgb565` + `--scale` 预缩放，
> 放 `.rodata`，`owned = 0`，`QL_FEAT_UI_IMAGE_DECODE=0`。
> 这样固件里既没有解码器、也没有图片 RAM —— 只有"指向 Flash 的指针 + 尺寸"。

## 12. 分期与工作量

| 期 | 内容 | 估时 |
|---|---|---|
| **P3a** | `QLImage` + `QLDraw2D->blit_image`（CPU 最近邻 + GPU 纹理）+ `<img>` 标签 + doc 资源段（blob v13）+ 布局内在尺寸 + **`RAW` 直指 `.rodata` 的 `owned=0` 路径** | 3–4 天 |
| **P3f** | `qltext assets`：`--format raw` + `--pixel-format` + `--scale`（**MCU 的默认路径**） | 1.5–2 天 |
| **P3b** | BMP + QOI 解码器 + fuzz（`QL_FEAT_UI_IMAGE_DECODE=1` 时才编） | 1 天 |
| **P3d** | `object-fit` 五态 + 圆角/遮罩组合 + golden 页 | 1 天 |
| **P3c** | PNG（inflate + 容器）+ 对拍 + fuzz（`DECODE` 内的最高档） | 3–4 天 |
| **P3e** | `map`/`area` 热区、`picture`/`source` 忽略 | 0.5 天 |
| **P3g** | 平台后端接口 + 一个参考实现（Linux/libjpeg-turbo） | 1 天 |

合计 **≈ 12–15 天**，`img` `picture` `source` `map` `area` 五个标签一次到位。

建议顺序：**P3a → P3f → P3b → P3d → P3c → P3e → P3g**。
理由：P3a + P3f 就能端到端跑通"图片文件 → 构建期转码 → MCU 固件里显示"，
这是**唯一的必达路径**（MCU 默认只走它）；解码器与 PNG 是 PC 侧的增量。

## 13. 风险与已知限制

| 风险 | 应对 |
|---|---|
| **P3c（PNG/inflate）最容易出隐蔽 bug** | 先把 fuzz 与对拍建起来再写解码主体；inflate 单独一个文件、单独一套测试 |
| 整数溢出 / 越界读 | 所有尺寸先过 §5.3 的检查；用 `uint64_t` 算中间值；ASan+UBSan 常态跑 |
| 平台后端返回脏 `QLImage` | §5.2 的"回来先校验"关口 |
| 每帧重复解码 | `failed` 位 + 解码只在 build/register 时发生；测试钉住"每帧不动解码器" |
| **构建期转码工具变成必经之路** | 它会成为 MCU 的**唯一**入口，所以：① 工具的错误信息必须能直接定位到文件与原因；② 产出的 C 数组要能提交进版本库（不依赖每次构建都跑工具）；③ 给一条"手工写 RAW 数组"的文档路径，保证没有工具也能跑起来 |
| golden 图受图片影响抖动 | 测试用的图片全部是**程序生成的无损小图**（纯色/渐变/四色块），不提交照片 |

**明确不做**：动画 GIF/APNG、WebP、SVG、EXIF 旋转（自有解码器）、
图像金字塔/mipmap、`srcset` 选择、`<picture>` 的 media 查询。
