# 与主流框架对比：qlgl 站在哪一格

> **一句话**：qlgl 不是"又一个 GUI 框架"，而是**把 HTML + CSS 当界面描述语言、在构建期
> 编译掉**的一条窄路。它的对手不是 Flutter / Electron（那两家要赢的是"应用开发效率"），
> 而是"同一份界面既要跑 PC 又要跑 MCU"时**没有答案**的那一格。

本文的自我要求：**不美化自己**。第 9 节是完整的短板清单，第 10 节写"什么时候你不该用它"。
凡是能实测的数字都给复现命令（第 11 节）。

---

## 1. 比什么：六条硬指标

| 指标 | 为什么重要 | 怎么量 |
|---|---|---|
| **体积** | 板子上的 flash 与安装包大小 | 二进制 `size` + 依赖库 |
| **内存** | 常驻 RSS，以及**是否有界** | `time -v` 峰值 RSS + 有没有动态分配点 |
| **启动 / 最坏帧** | 工业 HMI 关心"按下到响应"的确定性 | 冷启动时间、p99 帧耗时 |
| **界面语言** | 决定"设计稿能不能直接搬"、团队要不要学新东西 | HTML+CSS / QML / Dart / C API |
| **跨端一致** | 同一份界面在 PC 与板子上是不是同一个东西 | 是否需要两套代码 |
| **生态** | 控件、主题、工具、遇到问题的答案 | 有没有设计器 / 第三方库 / 社区 |

---

## 2. 一页速览

| | 界面语言 | 渲染 | 典型体积 | 能否下到 MCU | 生态 |
|---|---|---|---|---|---|
| **qlgl** | **HTML + CSS（子集，构建期编译）** | 自绘，CPU 光栅 + GL 双后端 | PC 全量 **519 KB**；最小构建 **262 KB** | ✅ 理论可（**尚无移植样板**） | **≈ 0** |
| **Electron** | 完整 Web（HTML/CSS/JS） | Chromium | 安装包 80~150 MB | ❌ | 巨大（npm） |
| **Flutter** | Dart widget 树 | Skia / Impeller | 桌面 release 20~30 MB 量级 | ❌ | 大 |
| **GTK 4** | C API + 自己的 CSS 子集 | GSK（GL/Vulkan） | 依赖链十几 MB 量级 | ❌ | 成熟（GNOME） |
| **Qt（Widgets / Quick）** | C++/QML（Qt for MCUs 是 QML 子集） | 原生绘制 / 场景图 GPU | 十几~几十 MB | ⚠️ 仅 Qt for MCUs（专有） | 很大 |
| **LVGL** | C 控件 API（+ 类 CSS 样式） | 自绘，小缓冲 | 数十 KB~数百 KB flash | ✅ 就是干这个的 | 中（工业用量大） |

> 体积那一列里，只有 **qlgl 与 LVGL 是同一个量级**；其余都是"整数量级"的差距。
> 这不是谁好谁坏，是**目标不同**：它们卖的是开发效率与生态，qlgl 卖的是确定性。

## 3. vs Electron：不是一个赛道，但常被拿来问

**Electron 的真实优势**

- **完整 Web**：任意 CSS/JS/DOM，Canvas/WebGL、npm 上百万个包；
- **调试体验**：DevTools、热更新、几十万篇 StackOverflow 答案；
- **三端一致**：Windows / macOS / Linux 一套代码。

**qlgl 的真实优势**

| 项 | qlgl | Electron |
|---|---|---|
| 二进制 | 519 KB（全量）/ 262 KB（最小） | 80~150 MB 安装包 |
| 常驻内存 | **3.2 MB**（最小构建实测）；PC 全量 140 MB，其中 19 MB 是 CJK 字体、其余是 Mesa 软件光栅 | 150~300 MB 起 |
| 冷启动 | 毫秒级 | 1~3 秒量级 |
| 确定性 | 无 GC、无 JIT、节点数上限编译期固定（`QL_CFG_UI_MAX_NODES`） | V8 GC + 合成器线程，最坏帧不可控 |
| 下到 MCU | ✅ 设计目标 | ❌ 差三个数量级 |

**Electron 明显更好的场景**（该用它）

- 应用本身就是"网页 + 一点本地能力"；
- 需要 npm 生态（图表、编辑器、PDF、地图…）；
- 团队是前端，且**不需要**考虑 MCU；
- Windows/macOS 桌面是主战场（qlgl 目前**只有 Linux 后端**，见 §9）。

**换到 qlgl 要付的代价**

- CSS 是子集：实测语料**声明级 73.6%**（§11），照抄真实站点会撞"不支持的属性"；
- 没有 JS：动态逻辑只能写 C；
- 没有 DevTools 那种"点一下看盒子"的调试器（有 `--dump` 截图 + 单测断言）。

## 4. vs Flutter：理念最接近的对手

两家都是**自绘、不嵌 WebView**（Flutter 也自带 Impeller/Skia）。差别在语言与运行时。

**Flutter 强在哪**

- Dart AOT，**热重载**（改一行看结果，迭代速度是 qlgl 的十倍以上）；
- 渲染管线成熟：Impeller 的着色器预编译、抗锯齿、动画性能都是工程化过的；
- 控件与生态：Material/Cupertino 一整套，`pub.dev` 几万个包；
- 移动端（Android/iOS）是真战场，且**六端**都能出（含 Web、桌面三端）；
- 无障碍、IME、平台通道（原生弹窗、相机）都有现成答案。

**qlgl 强在哪**

| 项 | qlgl | Flutter |
|---|---|---|
| 运行时 | **没有**（纯 C，无 VM、无 GC、无 Dart runtime） | Dart VM + AOT 快照 |
| 界面语言 | HTML + CSS（**设计稿/网页可搬**，构建期编译成静态数据） | Dart 代码里写 widget 树 |
| 二进制 | 262 KB~519 KB | 桌面 20~30 MB 量级 |
| 内存 | 最小构建 3.2 MB；节点/样式/文本全静态 | 60~150 MB 量级（GPU 驱动另算） |
| 可裁到 MCU | ✅ | ❌ |
| 集成到已有 C 程序 | 直接 `#include <qlgl/qlgl.h>` | 要嵌 Flutter Engine（C++ API + 平台壳） |

**共同短板**（qlgl 并不能靠换框架解决）

- 复杂文字整形（阿拉伯/印度语系）与 RTL：qlgl 明确不做（要 HarfBuzz/SheenBidi）；
- 平台原生观感：自绘框架都不像系统控件（GTK/Qt 才是那一档）。

**该选 Flutter 的时候**：做移动端产品、要现成控件与生态、要热重载、团队愿意学 Dart。

## 5. vs GTK 4：桌面这一侧的正面对手

**GTK 4 强在哪**（这几点 qlgl 明确不做，也不打算做）

| 能力 | GTK | qlgl |
|---|---|---|
| 原生控件集 | 一整套（含树、表、文件选择器、颜色选择器） | 无控件类，只有 HTML 元素 + CSS |
| 无障碍（a11y） | AT-SPI，能用读屏器 | ❌ 明确后置 |
| 输入法 | ibus 完整链路（候选窗、预编辑） | ⚠️ X11 走 XIM；Wayland **没有** `text-input-v3`（手机/软键盘做不了） |
| 系统集成 | 多窗口、系统菜单、托盘、打印、DnD、设置存储 | ❌ 一个进程一个窗口，全都没有 |
| 渲染器 | GSK（GL/Vulkan + 离屏合成） | CPU 光栅 + GLES3，无离屏合成 |
| 主题 | GTK CSS（**不是网页 CSS**）+ Adwaita | 网页 CSS 子集（`hover/focus/active`、伪元素、flex…） |
| 生态 | 二十年积累、GNOME 全线 | ≈ 0 |

**qlgl 强在哪**

- **依赖与体积**：GTK 拖的是 glib/pango/cairo/graphene/harfbuzz/fontconfig… 一条长链；
  qlgl 全量只有可选的 FreeType / X11 / Wayland / EGL 四个外部接口，最小构建**零外部依赖**；
- **界面语言是网页那一套**：会 CSS 就能写界面，不需要学 C API + GTK CSS 的另一套驼峰；
- **一份界面能下到 MCU**（GTK 差三个数量级）；
- **确定性**：没有保留式场景图（GTK4 的 GSK 每帧要维护 render node 树），
  静态界面下 `ql_ui_anim_tick()` 直接返回 0，主循环整帧跳过。

**诚实的结论**：做 Linux 桌面应用，**GTK/Qt 是更合理的选择** —— 你要的那些系统集成
qlgl 都没有。qlgl 的战场是"这块屏幕上只有我自己画的界面"。

## 6. vs Qt：广度 vs 确定性的两极

Qt 有三条产品线，要分开说：

| 产品线 | 界面语言 | 跑在哪 | 与 qlgl 的关系 |
|---|---|---|---|
| **Widgets** | C++ | 桌面 | 功能广度完胜；qlgl 不竞争 |
| **Quick / QML** | QML + JS | 桌面 / 移动 / 嵌入式 MPU | 理念不同：声明式 + JS 引擎 |
| **Qt for MCUs** | QML 子集（专有工具链） | 裸机 / RTOS | **这是 qlgl 在 MCU 上的直接对手** |

**Qt 强在哪**

- 功能广度：网络、多媒体、数据库、打印、多窗口、DBus、国际化、无障碍；
- 工具链：Qt Creator、Designer、`qmlscene`、性能分析器；
- 商用支持与长期维护；嵌入式生态（Boot to Qt）成熟；
- QML 比 HTML/CSS 更适合"数据绑定"（那是它活下来的原因）。

**qlgl 强在哪**

- **MIT 许可**（Qt 是 LGPLv3/GPL 或商业授权；静态链接闭源要注意合规）；
- **没有 moc / 元对象编译器 / C++ ABI 问题**：编译就是编译，接口就是 C 函数；
- 体积与内存小一档；无 JS 引擎、无 GC；
- 界面语言是 HTML+CSS（**Web 技能直接复用**，Qt 要学 QML）；
- 明确失败：不支持的写法**构建期报错**，不是运行时半对半错（对"板子上才发现效果不对"是硬需求）。

**该选 Qt 的时候**：几乎总是——如果你需要"一整套功能"而不是"一个自己画的界面"。

## 7. vs LVGL：MCU 这一侧的对手，也是老师

LVGL 与 qlgl 最像：**C 语言、自绘、小缓冲、跑 MCU**。差别在"界面怎么写"。

| 项 | LVGL | qlgl |
|---|---|---|
| 界面语言 | C 控件 API（`lv_obj_create`、`lv_label_set_text`…）+ 类 CSS 的样式 API | **HTML + CSS**（构建期编译成静态表） |
| 控件 | **一整套**（按钮/滑条/表/图/键盘/图表/滚轮…） | 无控件类；用 HTML 元素 + CSS 拼（`<button>`/`<input>`/`<select>`/`<progress>` 有 UA 默认样式） |
| 布局 | flex（近年）+ grid 子集 | **flex + 绝对定位 + 文本折行 + 行内混排** |
| 文本交互 | 无输入框编辑（需自己写） | `<input>` / `<select>` / `<textarea>`（含光标、选区、Ctrl+A/C/V、Tab 焦点） |
| 最小体积 | **数十 KB~数百 KB flash**（随功能与字体） | **实测 219 KB text、3.2 MB RSS**（无 FreeType/GL/窗口后端，位图字体） |
| 设计器 | SquareLine Studio（商业+社区版） | ❌ 无 |
| 生态 | 工业用量大、移植样板多（STM32/ESP32/NXP…） | ≈ 0；**连 MCU 移植样板都还没有** |
| PC 上跑 | 有 SDL/DRM 驱动，但界面是同一套 C 代码 | **同一份 HTML/CSS 既能上 PC 也能上板子** |

**qlgl 在 MCU 上的现状（不吹）**

- 能力包（`QL_FEAT_*`）目前**只有图像那几个真的在代码里生效**；
  `QL_FEAT_CSS_*` / `QL_FEAT_UI_*` 还只有名字（见 [CSS3 覆盖与裁剪](手册/ui/CSS3覆盖与裁剪.md) §21）；
- 没有移植样板、没有 RTOS 集成示例、没有 DMA/双缓冲的板级文档；
- 219 KB 比 LVGL 的典型配置重 —— 因为这里带着完整 HTML/CSS 编译器产物结构、
  flex 求解器、文本折行与输入框编辑。

**所以**：如果目标只是"一块 MCU 上有界面"，**LVGL 现在更合适**。
qlgl 的赌注是"**PC 上的原型和板子上是同一份 HTML/CSS**"这件省钱的事。

> 顺带一提同类：**Dear ImGui / Nuklear** 是即时模式（每帧重画整棵树，无布局引擎，
> 适合工具与调试面板）；**Slint**（Rust，声明式，也能下 MCU）理念上比 LVGL 更接近 qlgl。

## 9. qlgl 的短板清单

### 9.1 结构性：**设计决定，不会补**

| 项 | 为什么不做 |
|---|---|
| 无 JS / 无 DOM | JS 引擎 + DOM 是另一个数量级的体积与不确定性；动态逻辑走 C |
| 不嵌 WebView（任何平台） | 一旦在 PC 换引擎，两端渲染必然分叉 —— 那正是本库最贵的东西 |
| 不做运行期 CSS 匹配 | 样式在构建期消解（运行期解析是"加载时算一次"，不是每帧匹配，且可整块摘掉） |
| 无保留式场景图 | 那是 GTK4 的 GSK 路线，每帧重建节点，体积与确定性全都丢 |
| 不支持的写法**构建期报错** | 明确失败优于半个正确（板子上调试成本太高） |
| 不与 GTK/Qt 比功能广度 | 可访问性、多媒体、网络、打印都不做 |

### 9.2 现在缺，但路线图上有

| 项 | 状态 |
|---|---|
| `calc()` / `min()` / `max()` | 要改 `QLUILength` 表示（+40 字节/样式），未开始 |
| `border-radius` 四角、`border-style: dashed` | 未开始 |
| `transform: rotate()` / `skew()` | 要一条旋转光栅路径，单独立项 |
| 真 group `opacity`（离屏图层） | 现在是逐图元降透明 |
| `visibility` / `cursor` / `pointer-events` / `outline` / `text-shadow` / `list-style` / `background-size` | 未开始（`!important`、`var()` 之类同理） |
| CSS Grid / `float` | Grid 未排期；`float` 明确不做 |
| `:checked` / `:disabled` / `::placeholder` | 要先有能表达"禁用/勾选"的控件 |
| CSS / HTML 能力包真的生效 | 现在只有名字（图像那几个是真的） |

### 9.3 平台与工程：**当前最硬的短板**

| 项 | 现状 | 影响 |
|---|---|---|
| 桌面后端 | **只有 Linux**（X11 + Wayland）+ 内存显示 | Windows / macOS 用户完全用不了 |
| Wayland 输入法 | 没有 `zwp_text_input_v3` | 软键盘弹不出来，中文打不进去（X11 侧走 XIM，可用但受限） |
| 无障碍 | 无 AT-SPI | 无法过无障碍合规 |
| 多窗口 / 系统菜单 / 托盘 / 打印 / DnD | 全无 | 做不了"真正意义上的桌面应用" |
| 复杂文字整形 / RTL | 无 HarfBuzz / bidi | 阿拉伯、印度语系、希伯来语全不行 |
| MCU 移植样板 | 无 | "可裁到 MCU"目前是**架构上成立、工程上未验证** |
| 控件库 | 无（只有 HTML 元素 + UA 样式） | 复杂控件（树、表、图表）要自己拼 |
| 设计器 / 可视化编辑 | 无 | 设计师交付物只能是 HTML/CSS |

### 9.4 项目风险（对一个库的评价必须包含这些）

- **单人项目**：没有第二个人能 review，也没有 LTS 承诺；
- **API 未冻结**：`QLUIStyle` 这一轮已涨到 156 字节、blob 到 v20，"抬版本 + 重生成 golden"是常态；
- **文档全中文**：对非中文用户等于没有文档；
- **无第三方使用者**：所有用例都是自己写的，真实项目会撞到的坑还没有人替你踩过。

## 10. 该选它 / 不该选它

**适合（会明显受益）**

1. 嵌入式 Linux / MPU 上的 **HMI**（工控面板、仪器、车载中控的小屏部分）；
2. 想"**在 PC 上先用 HTML/CSS 做原型，再把同一份文件编译进板子**"；
3. 体积、内存、启动、最坏帧都要有**上限**的场合（无 GC、无 JIT、节点数静态）；
4. 已经有 C 程序，只想嵌一层界面（`#include` 就走，不需要 C++/脚本运行时）；
5. 团队会 CSS、不想学 QML/Dart/GTK API。

**不适合（别用，会痛）**

1. 需要 Windows / macOS 桌面；
2. 需要 npm/pub 生态、图表库、富文本编辑器；
3. 需要无障碍合规、完整输入法、多窗口、打印、托盘；
4. 需要复杂文字整形 / RTL / 多语言排版；
5. 需要现成控件库（树、表、文件对话框…）；
6. **只有一块 MCU 且要被工业验证** —— 现阶段选 LVGL 更省事；
7. 需要商业支持与 LTS。

## 11. 数字怎么来的

### 11.1 体积（本机实测，min-size / release）

```bash
# 最小构建：关掉 FreeType / GL / X11 / Wayland / 运行期解析 / JPEG
cmake -S . -B /tmp/qlmin -DCMAKE_BUILD_TYPE=MinSizeRel \
      -DQLGL_BUILD_TESTS=OFF -DQLGL_BUILD_BENCHMARK=OFF \
      -DQLGL_BUILD_TEXT_PARSER=OFF -DQLGL_BUILD_FREETYPE=OFF \
      -DQLGL_BUILD_JPEG=OFF -DQLGL_BUILD_WAYLAND=OFF \
      -DQLGL_BUILD_GL=OFF -DQLGL_BUILD_X11=OFF
cmake --build /tmp/qlmin -j && size /tmp/qlmin/example/example_01_window

# 全量：FreeType + GL + X11 + Wayland + 运行期解析 + 图像
cmake -S . -B /tmp/qlrel -DCMAKE_BUILD_TYPE=Release -DQLGL_BUILD_TESTS=OFF
cmake --build /tmp/qlrel -j && size /tmp/qlrel/example/example_01_window
```

| 构建 | text | data | bss | 磁盘二进制 |
|---|---|---|---|---|
| 最小（位图字体、内存显示） | **217 KB** | 4.6 KB | 20 KB | **262 KB** |
| 全量（FreeType 动态库、GL、X11+Wayland、运行期解析） | **475 KB** | 5.4 KB | 27 KB | **519 KB** |

> FreeType / libjpeg / Mesa 都是**动态库**，不计入上表 —— 这台机器上
> `libfreetype.so` 一个就 600 KB 级，Mesa 的软件光栅驱动更大。
> 这也是 §11.2 里 PC 全量 RSS 达 140 MB 的主因。

### 11.2 常驻内存

```bash
/usr/bin/time -v /tmp/qlmin/example/example_01_window --frames 1 --dump /tmp/x.ppm
/usr/bin/time -v /tmp/qlrel/example/example_01_window --frames 1 --dump /tmp/x.ppm
```

| 构建 | 峰值 RSS | 里面都是什么 |
|---|---|---|
| 最小 | **3.2 MB** | 库 + 内置 4bpp 位图字体 + 一块 640×480 缓冲 |
| 全量 | 140 MB | 其中 **19 MB 是 Noto Sans CJK 字体文件**（mmap），其余主要是 Mesa 的软件光栅（llvmpipe）与 EGL 初始化 |

> 换句话说：**140 MB 不是这个库的体量**，是"矢量中文字体 + 软件 GL 驱动"的体量。
> 真要报数，报最小构建那 3.2 MB 更接近事实；但也要老实说 ——
> PC 上想要中文与 GL，就得付这两笔账（Electron 也一样要付，只是它付得更多）。
