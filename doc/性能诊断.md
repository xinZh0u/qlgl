# 性能诊断：怎么量、怎么判、往哪儿改

调"卡"的时候，**肉眼是最差的工具**：CPU 打满、GPU 打满、在等 vsync、被合成器拖住，
四种表现都是"顿一下"，但改法完全不同。这份文档记录 qlgl 自带的测量手段，
以及用它们抓到的一个真实问题（拖动窗口掉帧）。

> **想跟着做一遍**：看 [教程 17 · 性能诊断与 MCU 基准](./tutorial/17_perf.html)。
> 这份文档是**参考手册**（参数、口径、判读清单），教程是**动手流程**。

## 1. 三件工具

| 工具 | 量什么 | 怎么跑 |
|---|---|---|
| `qlperf`（`tools/qlperf`） | 进程的 CPU / GPU / RSS / 线程数，并可驱动窗口缩放 | `./build/qlperf run -- ./build/example/example_22_media` |
| `example_* --stats` | 每帧耗时，**其中等 swap 占多少** | `./build/example/example_22_media --seconds 5 --stats` |
| `example_* --dump` + `doc/html` | 画面是否正确（性能问题的副产品） | 见各例程 |

### 1.1 `qlperf`：进程级探针

```bash
./build/qlperf run --interval 200 --seconds 6 -- ./build/example/example_22_media
./build/qlperf run --seconds 6 --resize "22 media" -- ./build/example/example_22_media
./build/qlperf watch 12345            # 监控已有进程
```

```
  t(s)   CPU%  GPU进程%  GPU整机%  RSS(MB)  线程
  0.25    5.0      3.2      18.0    151.0    11
```

数据全部来自内核/驱动，**不猜**：

| 指标 | 来源 | 口径 |
|---|---|---|
| CPU% | `/proc/<pid>/stat` 的 `utime+stime` 差分 | 单核 100%（多线程可能 > 100） |
| GPU 进程% | `/proc/<pid>/fdinfo/*` 里 `drm-engine-*` 的纳秒计数器差分 | 引擎时间 / 墙钟；> 100 表示多引擎并行 |
| GPU 整机% | `/sys/class/drm/cardN/device/gpu_busy_percent` | 驱动报告，amdgpu/部分 i915 有 |
| RSS | `/proc/<pid>/status` 的 `VmRSS` | 常驻内存 |
| 缩放驱动 | X11 `XResizeWindow`，每 ~8ms 一步 | 模拟拖边框的密度 |

汇总会直接给一句结论（CPU 打满 / GPU 打满 / 在等 vsync），因为这一步最容易看反。

### 1.2 `--stats`：帧时间与"等 swap"的拆分

```bash
./build/example/example_22_media --seconds 5 --stats
帧时间：p50 6.93ms  p95 7.37ms  max 15.12ms  （300 帧，p50 ≈ 144 fps）
其中等 swap：p50 6.84ms  max 15.04ms
```

- `frame_us - swap_us` = **我们自己花的**（布局 + 提交 + 光栅）；
- `swap_us` = `eglSwapBuffers` 里等垂直同步 / 合成器取帧。

**p50 6.93ms 而其中 6.84ms 在等 swap** → 我们一帧只花了 0.1ms，
144fps 是刷新率上限，不是我们的上限。这种"跑不满 300fps"不是性能问题。

### 1.3 例程的循环参数

| 参数 | 含义 |
|---|---|
| （默认） | **事件驱动**：没有脏区就阻塞等事件，界面静止时 0 帧、0% CPU |
| `--spin` | 每帧都渲染（基准测试用） |
| `--frames N` | 渲染 N 帧后退出（隐含 `--spin`） |
| `--seconds S` | 跑 S 秒后退出并打统计 |
| `--stats` | 退出时打帧时间百分位 + 等 swap 时间 |
| `--vsync 0/1` | 强制开关垂直同步（默认开，拖动缩放期间自动临时关闭） |

## 2. 一个真实案例：拖动窗口掉帧

### 2.1 现象

`example_22_media`（820×420，几十个节点）静止时 p50 ≈ 7ms（144Hz），
但拖动窗口边缘时肉眼可见地"卡一下"。

### 2.2 测量

```bash
./build/example/example_22_media --seconds 6 --stats      # 终端 A
./build/qlperf watch --seconds 6 --resize "22 media" <pid>  # 终端 B
```

修复前：

| 指标 | 值 |
|---|---|
| CPU | p95 4% |
| GPU（进程） | 0.1% |
| 帧时间 | p50 6.93ms，**max 58.50ms** |
| 其中等 swap | p50 6.82ms，**max 58.40ms** |

结论一目了然：**卡的那一帧 58.4ms 全在 `eglSwapBuffers` 里**，我们自己的活是 0.1ms。
再开 `--vsync 0` 复测，卡顿完全消失（max 4.4ms）——说明是"等 vblank"被合成器拖住，
不是我们画得慢。

Mesa 的 Present/XCB 路径在合成器忙于重配窗口时不会及时收到 frame callback，
最坏会一直等到它的 1 秒超时（实测复现过 `swap max 1000.8ms`）。

### 2.3 两个修复

**① 事件驱动循环（例程 + `common.h`）**

以前每帧都 `begin → render → swap`，静止的界面也每秒交换 144 次。
现在默认"有脏区才画"：`ql_ui_consume_dirty()` 拿到脏矩形，没有脏区就
`ql_gfx_gl_wait()`（`poll(2)`）阻塞等事件。拖动时"一个 ConfigureNotify 画一帧"，
其余时间不占 CPU，也不和合成器抢帧。

**② 拖动期间不跟 vblank（`qlgfx_gl.c`）**

收到 `ConfigureNotify` 后 200ms 内把 `eglSwapInterval` 设为 0（`ql_gfx_gl_end` 里
按 `resize_until_ms` 判断），拖动结束自动恢复。这是 GTK/Qt 在互动缩放期间的常规做法：
拖动时优先"跟手"，静止时再回到垂直同步（避免撕裂）。

**③ 不跟 vblank 时按显示节奏节流（同一个函数）**

关掉 vsync 就等于"谁快谁赢"：`--spin`（或基准测试）的循环每帧只花 0.6ms，
fps 会直接飙到 1700+，看起来像坏了，也白烧 CPU 和电。

所以后端记了两个量：
- `pace_us`：跟 vsync 时的帧间隔滑动平均（EMA，7:1，限幅 1~100ms），默认 16666；
- `last_end_us`：上一帧 swap 结束的时刻。

**只在 `vsync_eff == 1` 的帧更新 `pace_us`**（否则被测到的"无 vsync 快帧"会把
pace 拉到 0.6ms，节流等于没做）；拖动期间在**下一帧开头**（`begin_common`，
且在抓 `t0` 之前）补睡到 `last_end_us + pace_us`。

放在帧开头而不是帧末，是为了让 `frame_us`（begin→end）把等待算进去 —— 这样
`--stats` 的帧时间/fps 与跟 vsync 时的口径一致，不会出现"帧时间 0.6ms 却报 1700fps"
这种吓人的数字。

**④ 例外：刚改变尺寸的那一帧不等**

节流不能无脑套在"每一帧"上。窗口被拉大时，新露出来的那块区域正等着我们填；
如果这一帧还先睡 7ms，看到的就是"缩放时闪一下空白"，而且画面永远比鼠标慢半拍。

所以 `ConfigureNotify` 会置 `present_now`，紧接着的那一帧**跳过等待**，
立刻画、立刻 swap；之后的帧照旧按 `pace_us` 补。实测这一改把
"配置事件 → 新画面推上屏"的中位延迟从 7ms 级压到 **1.2ms**（p95 1.9ms），
帧率仍然稳在 144。

```bash
# 量这个延迟（每个 ConfigureNotify 打一行）
QLGL_LAG_DEBUG=1 ./build/example/example_22_media --seconds 10 &
./build/qlperf watch --seconds 4 --resize "22 media" $!
```

**⑤ 接上 `_NET_WM_SYNC_REQUEST`（让窗口管理器跟我们的帧对齐）**

上面的节流只解决"我们自己什么时候画"。还有一半在窗口管理器那边：
X11 的交互式缩放里，WM 不知道客户端什么时候把新尺寸画完。它可能连着发好几次
`ConfigureNotify`，也可能等一阵再把尺寸**一次跳到位** —— 肉眼就是
"拖动时窗口大小停住一会儿，然后突然变大"。

标准解法是 EWMH 的 `_NET_WM_SYNC_REQUEST`（GTK / Qt 都实现了）：

1. 建一个 XSync 计数器，把它的 XID 写进窗口属性 `_NET_WM_SYNC_REQUEST_COUNTER`；
2. 把 `_NET_WM_SYNC_REQUEST` 加进 `WM_PROTOCOLS`；
3. WM 每次要缩放，会先发一条带**新计数值**的 `ClientMessage`；
4. 客户端画完这一帧（`eglSwapBuffers` 之后）`XSync` 一下，再把计数器设成那个值。

我们在 `qlgfx_gl.c` 里按上面四步接好了（`XSyncCreateCounter` 需要 libXext，
CMake 会自己判断，没有就退回旧的"不接协议"路径）。另外有个细节：如果 WM 发来
请求、而我们这一轮**没有**东西要画（比如只是移动窗口，尺寸没变），
`ql_gfx_gl_wait()` 会立刻回执，否则 WM 会一直等我们。

### 2.4 修复后

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 拖动时 max 帧时间 | 58.5ms（偶发 1000ms） | **≤ 7.3ms**（3 次复测） |
| 拖动时 p50 帧时间 | 6.9ms（被 vsync 限住） | **7.3ms**（按 144Hz 节流，我们只花 0.6ms） |
| 静止时 CPU | 3~8%（持续 swap） | **0%**（0 帧） |
| 静止时帧数 | 144 fps | 0 fps |
| 拖动时帧率 | 144 fps | **144 fps**（p50 6.97ms / p95 8.30ms / max 15ms） |
| 配置事件 → 上屏延迟 | 7ms 级（先睡再画） | **p50 1.2ms / p95 1.9ms** |

```bash
# 复现修复后的数字
./build/example/example_22_media --seconds 4 --stats &
./build/qlperf watch --seconds 3 --resize "22 media" $!
```

## 3. 判读清单

看到"卡"时按顺序问：

1. **CPU 满了吗？** `qlperf` 的 p95 > 85% → 找热点（布局？光栅？事件循环空转？）。
2. **GPU 满了吗？** 进程 GPU% > 85% 或整机 > 85% → 填充率 / 批次问题。
3. **两个都没满，帧时间却大？** 看 `--stats` 的"等 swap"占比：
   - 等 swap 占大头 → 在等 vblank / 合成器，**不是我们的问题**；
     若拖动时爆到几十上百 ms，就是本轮的案例（已在库里规避）。
   - 我们自己占大头 → 用 `qlperf --csv` 存曲线，配合 `--frames` 二分定位。
4. **"跑不满 xxx fps"**：先确认 p50 是不是正好等于 1/刷新率（如 6.94ms ≈ 144Hz）。
   是的话就是 vsync 上限，别改代码。

## 3.5 `qlperf` 的其它选项

| 选项 | 用途 |
|---|---|
| `--interval MS` | 采样间隔（默认 250ms）；要看瞬时突发就调小 |
| `--csv FILE` | 每次采样写 CSV（`t,cpu_pct,gpu_proc_pct,gpu_busy_pct,rss_mb,threads`），接画图/看板 |
| `--resize TITLE` | 期间不停缩放标题含 TITLE 的窗口（X11） |
| `--resize-range A-B` | 缩放宽度范围（默认 700-900） |
| `--quiet` | 只打汇总 |
| `watch <pid>` | 监控已经在跑的进程（不需要由它启动） |

## 4. MCU 侧：QEMU 上的 Cortex-M4 基准

PC 上的数字不能外推到 MCU，所以有一套裸机基准：`test/mcu/`。

```bash
./test/mcu/build.sh             # 交叉编译 + 在 QEMU 的 Cortex-M4 上跑
./test/mcu/build.sh --no-run    # 只看 ROM/RAM 占用
```

跑的是**和 PC 完全同一份** `src/` 源码，只换三样：文档是构建期静态数据、
画布是一块静态 RGB565 数组、时钟走 ARM 半主机。

**口径**：QEMU 用 `-icount shift=0,align=off,sleep=off`（每条指令推进 1ns 虚拟时间），
`SYS_ELAPSED` 的虚拟纳秒 ≈ 指令数。实测把宿主机打满后数值不变（±1%），
所以它是与主机无关的确定性指标。换算到 M4@200MHz 就乘 5（每条指令 5ns），
即 `ns / 200 = µs`。**这是乐观下界**：M4 无 cache、flash 取指有等待周期，
真实板子按 ×1.5~2 估计。

当前数字（240×160 RGB565，21 节点 / 11 样式：flex 三列卡 + 圆角 + 边框 +
渐变 + 折行文本 + 裁剪）：

| 动作 | 虚拟 ns | M4@200MHz |
|---|---|---|
| `ql_ui_layout()` 全树重排 | ≈ 63 500 | **0.32 ms** |
| 一帧整屏光栅（含清屏） | ≈ 1 200 000 | **6.0 ms** |
| 1×1 脏区重绘 | ≈ 4 700 | **0.024 ms** |

结论：60fps 的 16.7ms 预算里，"光栅 6.0 + 布局 0.3" 只占 **36%**；
而且**局部更新只要 0.02ms** —— MCU 上真正该做的是脏区重绘，不是每帧全画。
详见 `test/mcu/README.md`。
