CSS 覆盖与裁剪（全量清单）

这份文档回答三个问题，口径与 HTML5 标签覆盖与裁剪 一致：

  1. CSS 的每一样东西，本库支持到哪一步？ —— 按模块穷举，一条不漏。
  2. 不支持的为什么不做？ —— 每条给一个原因码（§2），不写"暂不支持"这种废话。
  3. 哪一批先做？ —— 按"收益 / 风险 / 是否动 QLUIStyle"排批次（§22）。

0. 一份代码，两档目标（先读这一节）

从这一版起，"支持 / 不支持"按平台分开回答。两档的差距不是程度问题，是数量级问题：

PC / Mobile 档 MCU 档
目标 尽可能完整兼容 HTML/CSS，第三方库（FreeType / HarfBuzz / SheenBidi / libpng…）该上就上 确定性性能 + 自由裁剪，一个能力包一行 -D 就能摘掉
Flash 不设上限（MB 级随便用） 典型 M4 板 256 KB~1 MB；当前全量 131.5 KB（§2.1）
RAM 几十 MB 随便用 几十~几百 KB
帧率 60~144 fps，掉一帧要查原因 30 fps 够用，宁可少画也不掉帧
布局算法 该有的都要有：Grid、表格、多栏、border-image 按能力包裁剪；但 Grid 反而是减负（§11）
文本 自由字体列表 + 真整形（连字/字距/双向） 内建 ASCII 位图字体（≈9 KB），或裁剪后的子集 TTF
"不做"的东西 只剩与"构建期定型"根本冲突的（运行期 CSS 匹配、DOM/JS 引擎） 按需裁剪，不是"不做"

因此本文里的 ❌ 只有三种含义：① 与"构建期定型"冲突（P）；② 与 GUI 无关（N）； ③ 已明确排到某个后续批次（⏳）。"MCU 上装不下"不再是 ❌ 的理由 —— 那属于能力包（§21）的裁剪口径，PC/Mobile 档照样全做。

一句话现状：

布局与绘制的骨架已经齐了（盒模型、flexbox、定位、圆角、阴影、渐变、变换、过渡、动画）， 五批（B1–B5）把"真实页面天天用的细节"补完了。 下一阶段的重点是PC/Mobile 档的兼容广度：Grid（B6）、表格与多栏（B7）、 第三方文本栈（B8：FreeType + HarfBuzz + 双向）、filter / rotate（独立立项）。 MCU 档同步只做一件事：把这些新能力都做成可裁的能力包。

口径：MCU 那一列按 test/mcu/README.md 的换算——QEMU -icount 下"虚拟 ns ≈ 指令数"， 换到 M4@200 MHz 乘 5。这是乐观下界（M4 无 cache，实际 IPC 常 0.6~0.8）， 真实板子上乘 1.5~2 更接近。库体积（text）是 ELF 实测，不含栈与堆。

横比优先于绝对值：绝对值会随 QEMU 版本 / 编译选项漂（本机两次测量差过 ~30%）， 但"同一批、同一台机器、连着跑"的相对比较是可用的 —— 下文所有"快 xx%"都是这么来的。

三条能直接推出结论的读数：

  1. MCU 档的瓶颈是 Flash，不是"布局算法多"：一个 HarfBuzz 就是当前整个固件的 8.9 倍；一份全量 CJK 字体是 160 倍。所以"字体栈"必须按 G 处理（PC 上，MCU 裁）， 而布局算法（Grid/表格）加起来也就几 KB，够不上一个数量级。
  2. Grid 在 MCU 上不是负担，是减负：见 §11 的实测对比 —— 用嵌套 flex 拼 3×3 网格要 0.427 ms 布局，换成 Grid（同一视觉）只要 ≈0.229 ms，省 46%， 因为省掉了 3 个 wrapper 容器（每层 ≈3 个叶子节点的代价）。
  3. PC/Mobile 档完全不缺这点性能：整帧 0.72 ms 的预算里，加一个 Grid 求解器 增加的是"每容器一次 O(行×列) 的加法"，量级在 µs；真正的成本只有代码体积（MB 级预算里的几 KB）。

2.2 两档"能不能加"的判据

给一个新属性/新能力，按这个顺序问：

① 与"构建期定型"冲突吗？        → 是：P（不做，任何档）
② 与 GUI 无关吗？               → 是：N（不做，任何档）
③ 要第三方库吗？                → 是：G（PC/Mobile 上，MCU 裁）
④ 要新子系统吗？                → 是：S → 进 §22 的批次；PC/Mobile 必做，MCU 归"大核"包（默认关）
⑤ 只是"多解析一个值 / 多画一种线"？ → 直接做，进对应能力包（§21）

没有"因为 MCU 装不下所以不做"这一条了。 MCU 装不下就裁； PC/Mobile 装得下就必须做 —— 这是这次重新定档的核心变化。

11. Grid（B6 ✅ 已完成，MCU 归"大核"包）

这一块从"不做"改成"要做"、并且已经做完了，理由是实测出来的：

同一视觉：3×3 卡片格（240×160） 节点数 布局耗时 @200 MHz
嵌套 flex（3 个 .row 各 3 张卡） 15 0.427 ms
扁平 flex（flex-wrap: wrap + 固定宽） 12 0.229 ms
Grid 版（1 个容器 + 9 张卡，无 wrapper） 12 ≈0.229 ms（与扁平同量级）

也就是说：Grid 在 MCU 上比"用嵌套 flex 拼"更快，因为它省掉了 wrapper 层 （实测一层 wrapper ≈ 3 个叶子节点的代价）。它唯一的成本是 Flash 里的求解器代码， 和 layout_node（6.1 KB）同量级 —— 在一个 MB 级预算的 PC 档里可以忽略。

18.1 CSS 变量为什么能便宜地支持

早期结论是"❌ 明确不做：会让运行期样式变复杂"。这个理由站不住 —— 本库根本没有 运行期样式表（没有 JS、没有动态改样式的入口），所以变量天然只可能是编译期的值：

UA 默认 + 级联 + 行内 + 继承  →  out（这个元素最终可见的声明）
out 里先把 `--x` 自己的值解析掉   →  再把所有 var() 换成字面量

替换完，compile_style() 看到的就是字面量，QLUIStyle 与 blob 版本都不用动。 语料里 var() 占 10.0% 的声明（537 条，Bootstrap 5 一半样式靠它）， 是整个"补细节"清单里收益最高的一条。

规则 实现
--x 继承 collect_inherited() 把父级所有 --* 带下来
后代覆盖 就是普通级联（decls_set 语义）
var(--x, <fallback>) 有定义用定义值，否则用 fallback；fallback 里可再套 var()
嵌套 --a: var(--b) 先解析 --x 自己的值，再解析普通属性
循环引用 深度上限 8，超了报错（不会挂死）
找不到且无 fallback 构建期报错（不静默留成字面量）
简写里用（border: 1px solid var(--c)） 简写先按 token 形态展开成长属性，值是 var(...) 字符串 → 之后统一替换
名字大小写 属性名统一折小写，所以 --Brand 与 --brand 是同一个（与 CSS 的"大小写敏感"不同，写进限制）
content: var(--x) 报错：伪元素在级联之前就展开了，那时还没有自定义属性
运行期改主题 不支持 —— 换肤走"换一份 CSS / 热重载"（见 对比与取舍 §12）

18.3 calc()：为什么不能算成一个数

calc() 里可以有 %、vw、vh —— 它们的基准（父内容盒、视口）只有布局时才知道。 所以不能像 em 那样在构建期折成一个 px 数（em 能折，是因为那时字号已定）。

做法：把公式编译成一段后缀字节码，与样式分开存放。

calc((100% - 16px) / 3)
  ↓ 构建期：先做常量折叠（/3 折进每个操作数）
TERM(33, %)  TERM(5, px)  SUB  END        ← doc->calc_ops[]（每条 4 字节）
  ↓ 样式里只留一个下标
#a { width: 148 }                          ← QLUILength{ .value = 下标, .unit = CALC }
  ↓ 运行期：ql_ui_layout 里求值（一份 16 深的栈，没有递归、没有分配）
33% × 基准 - 5
项 支持
+ - * /、括号、嵌套 calc() ✅
min() / max()（2..8 个参数）、clamp(lo, val, hi) ✅ 参数可以是长度表达式
单位 px / % / em / rem / vw / vh / vmin / vmax
能用在哪 width / height / min-width / max-width / min-height / max-height / top / right / bottom / left
只能"常量"的字段 font-size / border-width / border-radius / letter-spacing / text-indent / margin / padding：只接受构建期能折成 px 的 calc()（如 calc(10px + 6px)），带 %/em/vw 的报错 —— 这些字段存的是 int16 数值，没有放表达式下标的地方
上限 QL_CFG_UI_MAX_CALC_OPS（默认 256 条，0 = 整套裁掉）

四条实现注意：

  1. 标量乘除只能对纯数字：calc(10px * 2) 可以（构建期折成 20px），calc(10px * 2px) 报错。 折进操作数是"逐项乘"，所以 calc(2 * (100% - 10px)) = 200% - 20px；
  2. 精度按存储单位走：百分比存整数，所以 calc(100% / 3) 是 33%（不是 33.33%）。 一个像素级别的偏差，比"支持不了"更可接受；
  3. 百分比高度仍然守父级确定的规矩：父级高度 auto 时，height: calc(50% - 5px) 按 auto 处理（与 height: 50% 一致），不会算出一个负高度；
  4. flex 项主轴上的 % / calc() 会先折成 px：measure 与真正的 layout_node 各解析一遍的话，calc(100% - 40px) 会被减两次（width: 50% 也会变成四分之一 —— 这是本轮顺带修掉的老 bug）。

18.4 B5 小件：十二个"只加开关"的属性

这一批的共同点是不动布局大框架，各自挂到一个已有机制上：

属性 挂在哪 实现要点
visibility: hidden 绘制 + 命中 只是"不画自己"，布局照常 → 与 display: none 的区别就在这里。它是继承属性，子级写 visible 能显示回来
pointer-events: none 命中测试 自己不作为命中目标，子节点照常（子级写 auto 能重新接住）——盖在按钮上的装饰层用它
align-self flex 交叉轴 auto = 跟容器的 align-items；stretch 只在交叉轴尺寸是 auto 时撑满
order flex 子链表 布局开头按 order 稳定 排一遍子链表，之后测量/断行/摆放/绘制/命中全都自动跟着走（比"每次遍历按 order 挑下一个"少六七处改动）
flex-flow 简写展开 <flex-direction> \|\| <flex-wrap>，两个 token 任意顺序；展开进 flex-direction / flex-wrap
overflow-x / overflow-y 裁剪 + 滚动 分轴只改裁剪矩形的一个方向（另一轴沿用外层裁剪）；只有 auto 的轴算可滚范围、才画滚动条

position: sticky 布局末尾补偿平移 在流里占位；滚动平移之后再把自己推回可视边缘，约束在包含块内（这就是"跟到头就一起滚走"）。改的是 border_box，所以绘制/命中/脏区/paint_box 全都自动正确
inset 简写展开 inset: <t> <r> <b> <l> → 四条长写，复用 margin/padding 的 1/2/4 值解析
cursor 命中测试 只算意图（ql_ui_cursor_at()）：命中节点往上找第一个写了 cursor 的祖先，都没写时输入框给 text、其余 default
user-select 输入框选字 none → 点还是能点（光标落点不变），但拖拽不再连选
scroll-behavior: smooth ql_ui_anim_tick 只记目标偏移，由每帧推进（160ms ease-out）；"跳"和"滑"共用同一份 scroll_x/y 状态

顺带修掉一个真缺陷（这是本轮最重要的收获）：align-items: center / flex-end 在"容器有确定高度、只有一行"这个最常见的情况下完全没有效果 —— 因为单行的 交叉尺寸取的是"各项最大值"，room 恒为 0。CSS 的默认 align-content: stretch 要求单行撑满容器的交叉尺寸，补上之后 align-items 才真的能用（golden 的 align 页因此变化，肉眼核对过：两个方块现在在 120px 高的容器里居中）。

同一轮把 align-content 也补上了（多行的行间分配），所以现在单行、多行两种 情况的交叉轴都按 CSS 语义走。

18.4.1 position: sticky 与分轴 overflow 为什么便宜

这两件看起来都要"动滚动子系统"，实际都只挂到已有机制上：

滚动      apply_scroll：把子树整体平移 -scroll         （早就有）
sticky    平移之后再把自己推回可视边缘，改的是 border_box
          → 绘制/命中/脏区/paint_box 读的都是 border_box，一行都不用改
overflow-x 裁剪矩形只改一个方向（另一轴沿用外层裁剪）
          → QLDraw2D 的裁剪本来就是矩形，逐轴覆盖一个边就够

sticky 的三条约束（都写在 sticky_adjust 里）：

  1. 只贴给了 inset 的方向（CSS 也是这样：不给 top 的 sticky 等于 relative）；
  2. 贴边位置按最近的滚动容器的内容盒算；没有滚动容器就按视口；
  3. 不能推出包含块（父内容盒）—— 这就是"跟着列表滚到头就一起走"， 而不是永远钉在屏幕上。

cursor 则刻意只做一半：CSS 值 + 命中测试算出意图（ql_ui_cursor_at()）， 真正设光标要窗口系统配合（X11 XDefineCursor / Wayland wl_cursor）， 后端目前没有接 —— 写进 API 手册 §3.13，不让它悄悄失效。

18.5 B4 第一批：border-style: dashed/dotted 与 outline（blob v25）

这两样都只改绘制、不动布局，所以实现上都不碰布局求解器：

border-style: dashed/dotted
  → 绘制期把四条边切成小段，每段一个 fill_rect（点线宽 >= 4 时用 fill_round_rect 画圆点）
  → 图案尺寸跟线宽缩放：dashed = 段 3w + 缝 2w，dotted = 点 1w + 缝 1w
  → CPU 与 GL 走的是同一条 fill_rect，天然像素一致（golden 的 b4 页差异 0.5%）

border-style: none
  → 解析期把 border-width 按 0 存（CSS 的 computed border-width = 0）
  → 不改布局代码，但内容盒不会再莫名缩水 2×width

outline: W style color
  → 绘制期用 stroke_round_rect：外沿 = 边框盒外扩 (offset + width)，厚度 = width
    → 这圈线正好落在 [offset, offset + width] 区间；offset 为负就压进边框里
  → 不参与布局：盒子位置/尺寸、兄弟位置、命中测试都不受影响
  → CSS 语义照抄：outline-style 初值是 none，只写 outline-width **不画**

为什么 dashed 不走 SDF：SDF 里只有"到形状边界的距离"，没有"沿周长走了多远"， 要画虚线段得在着色器里反解周长参数，成本远高于"切段填矩形"。代价是与 border-radius 同用时圆角按直角画 —— 这条写在覆盖表里，不藏着。

验收：test/web/test_b4.c（64 项：解析 + 逐点取色）、 golden 新页 b4（CPU vs GPU 0.52%）、例程 example/25_b4。

18.6 B4 收尾：四边四角 / 两层阴影 / 细节属性（blob v26）

这一批把 QLUIStyle 里的"单值边框"换成了"四边 + 四角"：

uint8_t  border_w[4]        /* 上 右 下 左 */
uint8_t  border_style4[4]   /* 每边自己的样式 */
uint32_t border_color4[4]   /* 每边自己的颜色 */
int16_t  radius[4]          /* 左上 右上 右下 左下 */
QLUIShadow shadow[2]        /* 两层，先写的画在下面（视觉上在最上） */
QLUIShadow text_shadow

布局侧的改动很机械：2 * border_width 变成了 ql_ui_border_h(s)（左右之和） 与 ql_ui_border_v(s)（上下之和），内容盒原点按 border_w[3] / border_w[0] 内缩 —— CSS 的"四边宽度不同"就是这样影响内容盒的。

绘制侧分三条路（paint_border）：

四边全同        → 一次整圈描边（最常见，也是最快的一条）
有 dashed/dotted → 逐边切段（角上按直角）
各边不同        → 整圈描边被"按边裁四次"，每次换一种颜色

第三条里的裁剪必须原样恢复：一开始忘了恢复，结果 .sides 之后的所有兄弟节点 都被裁进那一个小盒子里 —— 画面表现为"某一行之后整页空白"。写进注释，别再踩。

四角圆角则靠两个新入口：

  • QLDraw2D::fill_round_rect4 / stroke_round_rect4 / fill_round_rect_gradient4 （四角不全同时才走；全同仍走单半径的快路径）
  • CPU：round_row_span4() —— 每行左右两侧各算一次圆心到边的 dx
  • GPU：新增顶点属性 a_radii（vec4），片元里按象限挑半径，SDF 不变

投影与文字：

  • box-shadow 最多两层，inset 用反向 SDF（GPU mode=7，CPU 逐像素但只算"环"）
  • text-shadow 一层，blur 用 5 次采样近似（不需要离屏缓冲，MCU 也能跑）

细节属性都很便宜：image-rendering（GL 切纹理滤波）、 scrollbar-width/color（内置滚动条的宽度与颜色）、 object-position（object-fit 之后在余量里摆位，cover 时改的是源矩形）。

验收：test/web/test_b4.c（104 项）、golden 的 b4 页（CPU vs GPU 0.05%）、 例程 example/25_b4（九节，含滚动条与 focus 环）。

18.7 B2 / B3 尾巴与背景图（blob v27）

这一节收掉五批里最后三项。它们共同的思路是：能在构建期算清的一律不算在运行期。

状态选择器（QLUINode 20 → 28 字节）：

style_disabled / style_checked / style_placeholder   /* 各一份变体样式下标 */
placeholder                                          /* 文案在文本池里的下标 */
flags: QL_UI_NODE_CHECKBOX / _CHECKED / _DISABLED
  • 与 :hover 完全同构：多带一个状态位再跑一遍级联，与基础样式不同才建一份新样式；
  • 运行期优先级 disabled > active > focus > checked > hover；
  • :enabled 是"没有 disabled"，所以基础样式按节点属性决定要不要打开这个位；
  • 复选框有自己的 UA 默认（内部标签名 #cb → 16×16、无内边距）， 并且不进输入框池（它没有文本）；

文本细节（QLUIStyle 240 → 272 字节）：

  • word-spacing 只加在空格之后（量宽与绘制走同一个 adv_of）；
  • tab-size 在建表期把 \t 展开成 N 个空格 —— 运行期一个字符判断都没有；
  • text-decoration-* 的形态用 fill_rect 拼（double 两条、dotted 点、dashed 段+缝）， 不需要新图元，CPU / GPU 天然一致；overline 占 deco_style 的高位。

背景图：与 <img src> 共用资源表。

绘制：object-fit 的同一套几何（cover / contain / <w> <h>）+ position + repeat

当时没做的：filter。颜色矩阵类（brightness/grayscale/...）技术上可行， 但 blur() / drop-shadow() 需要离屏图层（子树先合成到一张图再整体模糊）， 当时留作单独立项 —— 后来 M9.3 落地（§18.10），transform: rotate 也在这层上 长出来（§18.11）。

18.8 B6/B7 的代价是怎么估出来的

新批次（Grid / 表格 / 多栏 / border-image）都要在"进 MCU 能力包"之前先说清代价。 这一节说明怎么量，数字见 §2.1。

① 布局的边际成本（test/mcu 的同一份 CSS，只改卡片数量）：

12 节点 0.23 ms → 39 节点 0.82 ms → 75 节点 1.94 ms
拟合斜率 ≈ 4.4k 指令/节点 ≈ 22 µs/节点 @200 MHz

② wrapper 容器的成本（同一视觉，两种结构）：

3×3 卡片用嵌套 flex（3 个 .row，15 节点）   0.427 ms
同一视觉用扁平 flex-wrap（12 节点）         0.229 ms

差 0.198 ms 只换来 3 个"什么都不画"的 .row —— 一层 wrapper ≈ 3 个叶子节点。 这条读数直接推翻了旧文档"Grid 太贵所以不做"的判断：

  • Grid 的求解是"轨道定尺 → 放置 → 对齐"三段，都是整数加法，没有逐像素；
  • 而"用 flex 拼网格"要付 wrapper 的钱，每次重排都付；
  • 所以 Grid 落地后，网格类页面的 MCU 布局时间是下降的（省 46%，见上）。

③ 表格为什么比 Grid 贵：table-layout: auto 的列宽分配要两遍 （第一遍量每列 min-content / max-content，第二遍按可用宽度分配）， 即"布局边际成本 ×2"；border-collapse 还要"半边边框相加"。所以它估 6–10 KB。

④ 多栏最贵：column-count 要求列高尽量相等，只能"先排一遍量总高、 算出目标列高、再排一遍断列"。同样是 ×2 遍，但还要维护"一个节点跨两列"的中间态 —— 这是唯一真正与"一个节点一个盒"冲突的一项，所以估 8–15 KB。

⑤ border-image 最便宜：九宫格 = 把源图切 9 块，四角原样、四边单向拉伸、 中间双向拉伸。绘制走的是现成的 ql_canvas_blit_image()（只是采样区间不同）， 解析期切一次就存进样式，运行期零额外状态。估 2–3 KB。

⑥ 第三方库为什么必须按 G 处理（@font-face / 整形 / 双向）：

libharfbuzz.so   1,178 KB   = 当前整个 MCU 固件（131.5 KB）的 8.9 倍
libfreetype.so     813 KB   = 6.2 倍
libfribidi.so      106 KB   = 0.8 倍（fribidi 本身还勉强，但单独它不解连字）
一份全量 CJK TTF    21 MB   = 160 倍

这几样在 PC/Mobile 档是必须的（否则中文以外的语言、真字重、连字全都没有）， 在 MCU 档是必须裁的（裁掉后仍是内建 ASCII 位图字体 + 可选子集 TTF）。 这就是 G 这个原因码存在的意义：它标的是"依赖关系"，不是"不做"。

18.9 B6 落地：Grid 与 border-image 是怎么做的

① 数据放哪：模板进池，摆放进样式

QLUIStyle 只长了 40 字节（272 → 312），因为轨道列表不进样式：

/* QLUIStyle：容器 3 个字段、子项 4 个字段 */
uint16_t grid;          /* doc->grids[] 下标；QL_UI_NO_GRID = 不是 grid 容器 */
int16_t  grid_col, grid_row;        /* 起始线（1-based）；0 = 自动 */
uint8_t  grid_col_span, grid_row_span;
uint8_t  grid_flow, justify_items, justify_self;
int16_t  grid_auto_row, grid_auto_col;

/* doc 里三段池（所有容器共享；同一模板经样式去重后只存一份） */
QLUIGrid      grids[];       /* col/row 轨道的起止下标 + 具名区域起止 */
QLUIGridTrack grid_tracks[]; /* { min_kind, max_kind, min_val, max_val } */
QLUIGridArea  grid_areas[];  /* { 名字, 列, 行, 列跨, 行跨 } */

一条轨道是 [min, max] 区间：100px → 两边都定长；1fr → min=auto, max=fr； minmax(60px, auto) → min=60px, max=auto。定尺时先满足 min，再把剩余按 max 侧的 "拉伸能力"分配（fr 权重 / auto 取内容）。

② 摆放与模板搜索为什么在构建期

grid-area: main 要查父容器的具名区域，grid-column: 1 / -2 要查父容器有几列 —— 这些在样式编译时都还不知道（编译是逐节点、按声明集去重的）。所以分两趟：

  1. compile_style() 只把 Grid 属性的原文挂到"按样式下标"的侧表上；
  2. 整棵树都有了样式之后，grid_resolve_all() 统一解析：模板 → 池； 每个子项的线号/跨度 → 4 个整数写进样式。

去重带来一个坑：同一个 .cell 可能被两个不同模板的容器使用，摆放值就不一样。 这里用写时复制——样式第一次被占用时直接写，第二次要不同的值就复制一份样式 （sig = NULL，不再参与去重）。运行期因此永远只读整数，没有任何字符串比较。

③ 布局：三段，全是整数

① 放置   ：显式位置 → 只给列 → 只给行 → 全自动（游标扫描，dense 时回原点）
② 列定尺 ：min → 定长上限 → auto 取内容 max-content → fr 分剩余（累计推进）
③ 行定尺 ：先按"列宽已定"把每项真排一遍拿高度 → auto 行取最大值 →
           span>1 按差额均摊 → fr 行分剩余（容器高度确定时）
④ 定位   ：按 justify-self / align-self 在格子里摆，默认双向 stretch

fr 的份额用累计分子（num += 总额×权重; 份额 = num/权重和; num %= 权重和）， 与 flex 的 grow 同一套 —— 三列 1fr 1fr 1fr 在 100px 里是 33+34+33，右边界严丝合缝。

④ 嵌套 grid 的临时区：按栈的纪律切

轨道数组、列/行起点、每项的放置结果都是临时数据。不能用一份全局数组： 测量阶段会递归进入内层 grid，把外层刚算好的列宽冲掉（实测：内层列宽对、外层整体 缩小一半）。所以 QLUIRoot 里放一个只增不减的缓冲 + bump 指针：

const uint16_t saved_place = ui->grid_place_used;
const uint32_t saved_coord = ui->grid_size_used;
... 用 ...
ui->grid_place_used = saved_place;   /* 函数出口（含降级路径）都还原 */
ui->grid_size_used  = saved_coord;

ql_ui_layout() 每次把两个指针归零，所以稳态下零分配（不违反"热路径不 malloc"）。

⑤ border-image：九宫格 = 9 次 blit

后端早就有 blit_image(dst, src)（子矩形采样），所以九宫格不需要新图元：

四角：src 原样 → dst 角块（缩放）
四边：src 单条 → dst 单条（stretch / repeat / round / space）
中间：src 中心 → dst 中心（stretch，或裁剪后平铺）

切片值 border-image-slice 是源图上的像素（或百分比）； 画出来的宽度用 border-image-width，默认等于切片值。 写了 border-image 就不再画 border-style（CSS 语义）。

资源走的是 <img src> / background-image 的同一张表： ql_ui_register_image(ui, "frame", ...) 填一次像素，三种用法共享。

18.10 M9.3 落地：离屏图层（filter / mix-blend-mode / mask / 真 group opacity）

四样特性共用一句前提：先把子树合成到一张临时图上，再整体处理。

触发条件（style_needs_layer()）

样式 开图层？
filter_n > 0 是
mix_blend != normal 是
mask_image != none 是
opacity < 1 且有子节点 是
其余 否 —— 走原来的单批次路径

绘制范围

bounds = 边框盒 ∪ paint_box（子树可能画到的范围）
       ∪ blur·3 的外扩
       ∪ drop-shadow 的偏移与 blur·3
       ∩ 当前裁剪（不裁剪就会为屏幕外的东西分配缓冲）

裁剪仍然按元素的边框盒 + 圆角：所以"圆角卡片 + 模糊光晕"的四个角是干净的， 光晕不会漏到圆角外面（QLDraw2DLayerFx.box + .corner 就是为这一条存在的）。

后端协议（qldraw2d.h）

int  (*layer_begin)(QLDraw2D *, QLRect bounds, const QLDraw2DLayerFx *);
int  (*layer_end)(QLDraw2D *);      /* 返回 1 = 请把同一棵子树再画一遍 */

layer_end 返回 1 是 CPU 侧的协议：它要两遍。

CPU：两遍哑光反解

CPU 光栅有二十多条混合路径（整行快路径、SSE2 块、字形位图、图片搬运…）， 它们全都写成"只在 RGB 上混、alpha 恒 0xFF"。要让它们各自累积 alpha， 改动面大且极易漏。于是换个方向：同一棵子树画两次，一次在黑底、一次在白底。

黑底：B = C·a          白底：W = C·a + 255·(1-a)
⇒  a = 255-(W-B)，而**预乘色就是 B**

既不用除 alpha（除法的量化误差很大），也不用知道 C。代价是子树画两遍 （实测：一块 200×120 的卡片多花 ~0.2 ms），换来的是零风险—— 所有既有图元的混合语义一个字都没改。

三个通道各自给出的 alpha 会差 1~2（8 位量化），实现里取平均把误差摊掉。

GPU：真 RGBA FBO + 一个合成着色器

GL 有 RGBA 帧缓冲，只画一遍。合成走 LAYER_FS：

  • 颜色矩阵族（6 个 uniform 对，按顺序作用在直通色上，再乘回 alpha）；
  • opacity / 圆角裁剪（SDF + smoothstep，与 CPU 同一公式）/ mask（第二张纹理）；
  • 混合模式：把目标表面那一块先 glBlitFramebuffer 成一张纹理当背景， 片元里按 CSS 公式算（和毛玻璃同一个套路）；
  • drop-shadow：额外的两趟模糊 + 一次"只画影子"的合成（先画影子，再画本体）。

踩过的坑（都在代码注释里留了记号）：

  1. layer_ensure() 建纹理时临时切了 FBO，结尾一句 glBindFramebuffer(0) 把外层图层的输出丢到了默认帧缓冲 —— 嵌套时外层整个不见。必须存/还原绑定。
  2. 模糊那几趟把 viewport 改成了模糊纹理的尺寸，不切回来合成四边形就会按错误投影 画出去。抽了 gl_bind_target() 统一负责"绑定 + viewport + scissor"。
  3. 毛玻璃那套 BLUR_FS 的片元固定输出 alpha = 1（它背后永远是不透明的页面）。 拿它糊图层会把透明区域糊成不透明黑，图层边缘立刻出现黑边。 所以另开了一个 4 通道版本 BLUR_RGBA_FS。
  4. GLSL 的 mat3(a,b,c, …) 是按列填的，照抄 CPU 的行主序色相矩阵会得到转置 （色相旋转不对称 → 颜色明显跑偏）。改成逐行写死 dot()。
  5. CPU 侧 ql_layer_drop_shadow() 里写反了合成顺序 （shadow + layer*(1-shadow_a) 是"影子盖住元素"），现在固定为 layer + shadow*(1-layer_a)。
  6. glBlitFramebuffer 也受 scissor 影响（它是片元流水线之外的少数例外之一）。 混合模式要把"图层背后那一块"先 blit 进一张纹理，那张纹理的目标矩形在 (0,0)； 脏区重绘时 scissor 却是"屏幕上那一小块"，两块不重叠 → 整次拷贝被静默丢弃， 没有 GL 错误。表现：multiply/overlay/darken 全黑、screen/difference 退化成原色（首帧背景纹理刚建 = 黑；之后的帧会读到上一次抓的背景）。 整屏重绘时 scissor 恰好覆盖 (0,0)，所以只测整屏的用例永远是绿的 —— 回归用例必须让"背后的颜色变了、而只重画这一小块"（test_gl_dirty 第 5 节）。

18.11 M9.4 落地：旋转光栅（transform: rotate/skew/matrix + transform-origin）

CSS 的 transform 作用于元素的渲染结果，不是"把每个图元按矩阵画一遍"。 这条语义决定了实现方式：

子树先按原样画进离屏图层  →  再按 2×3 矩阵做一次仿射重采样  →  贴回目标

逐图元转（另一种做法）会把文字转成马赛克、把圆角转成方角、把 filter 的结果 转丢，所以从一开始就否掉了。好处是它完全复用 M9.3 的图层基建： style_needs_layer() 里只要多一条"有 xform 就要图层"。

数据：矩阵进 doc 池，样式只留下标

项 做法 理由
矩阵存哪 QLUIDoc.xforms[]（QLUIXform = 6 × int32，26.6 定点） 24 B/样式在 MCU 上不可接受；同一份 CSS 里重复的 rotate(15deg) 只存一份（按值去重，池上限 32）
样式里存什么 int16_t xform（QL_UI_NO_XFORM = -1）+ QLUILength origin[2] 共 +8 B/样式（336 → 344），blob v30、头 144 → 152
坐标系 矩阵在 CSS px 空间定义 设备空间 = 同一份线性部分；平移与原点乘 dpr（等比缩放与线性变换可交换）
transform-origin 的百分比 千分比（0..1000） 与宽度类的 /100 不同：这里用 1000 才能表达 1‰ 的微调，且与 sc_x 同一口径

轴对齐的 translate() / scale() 不进矩阵池（零重采样，走老的绘制期变换）。 一条声明里只要出现 rotate/skew/matrix，整串（含 translate/scale）乘成一个矩阵 —— 这是 CSS 的语义，也避免了"一半在布局期、一半在合成期"。

CPU：逆向映射 + 双线性

正向映射（把源像素搬到变换后的位置）会在放大时留空洞，所以按目标像素反查：

q（目标像素中心） → u = q - origin - t → p = origin + M⁻¹·u → 在图层缓冲里采样

圆角 / 遮罩用局部（未旋转）坐标判定，也就是"先裁再转"，与浏览器一致。 轴对齐矩阵（含 matrix(1,0,0,1,0,0)）仍走原来的整块贴回快路。

GPU：变换四角 + 一个 u_local 开关

四边形还是 4 个顶点，只是把四角按矩阵摆过去。平行四边形上的 v_uv 线性插值 恰好等于局部坐标，于是片元里一句就能换来正确的圆角判定点：

lp = (u_local != 0) ? u_lbounds.xy + vec2(uv.x, 1.0 - uv.y) * u_lbounds.zw : dp;

踩过的坑（最重要的两个）

  1. 图层合成整体上下翻转（M9.3 就存在，M9.4 才暴露）。 内容是按"CSS y 向下"画进 FBO 的（主着色器里 ndc.y = -ndc.y）， 所以纹理的 v=1 才是元素顶边；而合成四边形的 uv 一直按 v=0 在顶边取。 纯色、居中的规则方块上下对称，六个老用例全是绿的 —— 一旦图层里有"上红下蓝" 或者转过的文字，立刻原形毕露。现在四边形的 uv 顶边给 v=1，同时把依赖 v_uv 的三处一起翻正：遮罩图（1-uv.y）、背景纹理（直接按 uv）、 drop-shadow 的 y 偏移（改号）。
  2. 嵌套图层的位置：内层的 L->dev 已经是"相对外层 FBO"的坐标（进图层时 offset 已经减过外层原点），再减一次外层 dev 就会整体上移。合成四边形的 归一化分母取当前目标的 g->width/height 即可，别再减原点。

命中测试

把屏幕点按矩阵逆变换回局部空间再判盒，逐层下降正好是仿射连乘：

det = a*d - b*c;                          /* =0：压成一条线，点不中 */
lx  = (d*ux - c*uy) / det;   ly = (a*uy - b*ux) / det;   /* 出来就是 px */

（ux/uy 先乘 QL_FX_ONE，det 是 FX²，所以结果不用再除 —— 第一次写成了 再除一次，表现是"原位置也能点中"。）

18.12 B7 落地：表格（display: table 全家）

浏览器里表格是两套 display 交叉的结构，本库照搬：

table（有盒子） ← caption（有盒子，排在上方）
                ← row-group（**没有盒子**）← row（**没有内容盒**）← cell（真正的盒子）

所以样式要写在 td/th 上 —— 写在 tr/thead 上不会有边框和背景，这一点与 浏览器一致（不是偷懒）。

布局：五遍扫描，全部用"计数器"而非矩阵

遍 做什么
1 收集行（展开 thead/tbody/tfoot），按 rowspan 顺延算出真实列号，得列数
2 定列宽：首行显式 width 的单列单元格优先，其余列等分剩余宽度
3 量行高：rowspan == 1 的单元格各排一次，取最大值
4 跨行单元格：不够高就把差额补给覆盖范围内最后一行
5 摆放：按列宽/行高定位，再把单元格高度撑到整行、内容按 vertical-align 摆

关键数据结构是 24 字节：uint8_t live[QL_CFG_UI_TABLE_MAX_COLS] —— "每列还被上面几行的 rowspan 占着"。行是按顺序处理的，行末把大于 0 的减一即可。 不用 rows × cols 的占用矩阵（64×24 = 1.5 KB 栈，MCU 上不可接受）。

踩过的坑（都留了注释）：

  1. rowspan 之后的列号。只看"本行第几个格子"会把第二行的第一个单元格排到第 0 列， 压住上一行跨行的那个格子（第一版就是这样，截图里 Q1 和 二月 叠在一起）。 必须按"跳过被占用的列"来分配起始列 —— 五遍扫描每一遍都要做同样的记账。
  2. 单元格不能用文字撑宽。border_width_of() 里有一条"行内盒宽度由文本决定"的 快路，display: table-cell 不是 block，一开始就落进了那条快路 → 每个单元格只有 文字那么宽（34px）。现在把所有表格角色排除在"文本撑宽"之外。
  3. vertical-align 的余量要用"自然内容高"算。单元格自己写了 height: 60px 时 border_box.h 已经是 60，拿它当内容高就永远算不出余量（middle 和 top 一样）。 所以另写 table_cell_content_h()：有子节点取子树底边，纯文字按"折行后的行数 × 行高"。
  4. 文字直接挂在单元格上时（没有子节点），平移子节点是空操作 —— 要挪的是 content_box.y，绘制时文字才会跟着走。
  5. collapse 的相邻边框：把每个单元格朝左上挪"自己那半条边框"、同时把尺寸补回 同样的量，两个边框就落在同一像素上；右/下边缘仍落在网格线上（不挪则外框会跑出去）。

table-layout: auto：min/max-content 之间插值

第 2 遍（定列宽）有两条路，s->table_layout == 0 走 auto：

  1. 单列单元格各量一次 max-content（max_content_main）与 min-content （最长连续非空白段，中文按整句算），取该列所有单元格的最大值 → pref[] / floorw[]；
  2. colspan > 1 的单元格：它覆盖的列宽之和不够就均摊补差额（还不开循环，只做一遍）；
  3. 三种情形落定： - avail >= Σpref → 余量按 pref 比例摊给各列（表格式块级，盒子仍撑满容器， 所以余量只能摊到列上 —— 这一点与浏览器"表格盒子跟着内容走"不同，见 §19.1 的受限表）； - avail <= Σfloor → 直接取 floorw（宁可溢出也不把字压碎）； - 中间 → 按 [floor, pref] 线性插值。

<colgroup> / <col>

display: table-column(-group) 是真角色（不再是 display: none）：不产生盒子， 只在第二遍里提供列宽。<col span> 用 span 属性（不是 colspan），构建期就展开成多列。 fixed 下 <col> 的宽度优先于首行；auto 下它同时充当 pref/floor 的初值 （内容更宽时取内容）。

两个坑：

  1. 单元格宽度必须由列宽决定。td{width:250px} 在 fixed 下只是"这一列要 250"的申请， 列宽算完之后单元格必须填满整列。第一版没有这一步，td{width} 会把自己的 border-box 撑到 250，把列宽算出来的结果覆盖掉（<col> 明明写了 40，渲染出来还是 250）。 现在摆放前用 table_force_cell_w() 走 style_copy 把宽度改写成列宽。
  2. <col> 是空元素。不把 col 加进"空元素表"，<col> 会一路吞掉后面的兄弟节点， 报"结束标签不匹配"。

明确不做的

caption-side: bottom、empty-cells、跨行内容超高时"按比例分配差额"。 都在 §16 的表格里如实标着。

18.13 B7 后半落地：多栏（column-*）

多栏不是"把一份内容排两遍"。本库的做法是三步，且只有第一步真的排版：

步 做什么
1 按栏宽把每个子节点在 (0,0) 排一遍（这一次就是正常的 layout_node），顺带记下高度
2 定栏高：容器有 height 就用它；否则二分找"最小能让内容塞进 N 栏"的栏高（纯算术，不重排）
3 按顺序贪心分配 + translate_subtree 平移到最终位置（不重排）

栏数怎么来（n）：

n = column_count                      /* 只给了栏数 */
n = floor((宽 + 缝) / (栏宽 + 缝))     /* 只给了栏宽 */
n = min(column_count, 上一个式子)     /* 两个都给：取小的 */

然后 栏宽 = (容器内容宽 - 缝×(n-1)) / n，上限 QL_CFG_UI_COLUMN_MAX（8）。 column-gap 与 flex 共用 gap_col 字段；没写时按 CSS 的 normal≈16px 算。

为什么"不劈子节点"这条要写死：真分栏的断点可能落在文字行中间，需要把同一个节点的 绘制切成两段 —— 而本库的绘制、命中测试、滚动、paint_box 剪枝全都建立在"一个节点 一个盒"上。要支持就得引入"盒内分裂"整套机制，与 MCU 目标直接冲突。 所以：一个子节点整体落到某一栏，塞不下就换栏（空栏至少放一个，避免死循环）； 最后一栏放不下就溢出（宁可溢出也不丢内容）。

踩过的坑：

  1. cursor 与 target 单位不同。cursor 是绝对坐标（content_y + 已用高度）， target 是"栏高"。第一版直接写 cursor + adv > target，于是从第二个子节点起 永远判定为"放不下"，每栏只放一个、其余全堆在最后一栏（例程 34 第一节一跑就现形）。 正确的是 (cursor - col_top) + adv > target。
  2. 均分栏高不等于"等高"。ceil(总高/n) 在子节点高度不齐时会让第一栏连一个高个子 都塞不下（同上现象）。所以改成二分求"最小可容纳栏高"——栏高越大需要的栏数越少， 这个谓词是单调的，二分 12 次足够；代价是纯算术重扫，不打乱任何盒子。
  3. column-rule 不是 border。paint_dash_run() 会把"solid"也切成 3w + 2w 的虚线，直接复用会画成一串短横线。solid 要走一次 fill_rect。

绘制

栏间分隔线画在背景/边框之上、内容之下（render_node_inner 里）， x 取缝的中点，高度取内容盒高；column_rule_width == 0 或 style == none 时整条不画， 颜色 0 表示 currentColor。

验证

18.14 B8 落地：文本栈（@font-face / 家族列表 / 整形 / 双向）

三段是一件事的三个层次，所以一起落地：

@font-face          → 注册表：家族 →（字重, 斜体）→ 字体文件
font-family: A, B   → 回退链：逐字找"谁有这个字形"
HarfBuzz / fribidi  → 一行怎么排：连字、字距、连接形、视觉顺序

1. @font-face：构建期只存声明，运行期真读文件

CSS 里写：

@font-face { font-family: "My Sans"; src: url(/usr/share/fonts/.../DejaVuSans.ttf);
             font-weight: 400 }
@font-face { font-family: "My Sans"; src: url(...-Bold.ttf); font-weight: 700 }
@font-face { font-family: "My Sans"; src: url(...-Oblique.ttf); font-style: italic }

构建期把它变成 doc 里的一张 8 字节的小表（家族名 / 资源名都是文本池下标）， 不读字体文件、也不内嵌字体字节。运行期 ql_ui_build() 时按表注册进 字体注册表（ql_font_family_register()），注册表按 (文件, 字号) 缓存已加载的字面。

只认四样：font-family / src: url() / font-weight / font-style。 unicode-range（子集化）、src: local(...)（要 fontconfig）、font-display 一律构建期报错 —— 静默忽略会让"这段中文为什么用了别的字体"这类问题无迹可寻。

2. font-family 列表与逐字回退

样式里的 font_family 现在是"家族列表"的下标（blob v33）。运行期：

  1. 按顺序取列表里的名字：monospace / serif / sans-serif / system-ui 落到 本库的正文/等宽字体；其余名字查注册表；
  2. 第一个"装得上"的家族当主字体，后面的接成 QLFont.fallback_font 链；
  3. 缺字时 ql_font_find_glyph() 沿链往下问 —— 逐字回退， 所以"DejaVu + Noto CJK"这种混排不需要拆 span。

回退链为什么要包装体：注册表里的字体按 (字面, 字号) 共享，同一张字面可能被 两条不同的链用到（A, monospace 与 A, B）。直接改共享字体的 fallback_font 会让两条链互相污染，所以链上每一节都是一个只借后端与 impl 的包装体 （字形缓存是自己的，销毁时只放自己的部分；ql_font_family_reset() 负责真正的字体）。

链的缓存按 (文档, 列表, 字号, 字重, 斜体) 记 16 槽，DPR 放大时按同一个列表重取 （ql_font_set_scale_hook），否则放大后字族会悄悄变回默认。

3. 整形：HarfBuzz（直连或 dlopen）+ 内建兜底

ql_text_shape() 是唯一的入口：量宽度与画字形都走它，所以"量出来 3 个字符、 画出来 1 个连字"这种错位在原理上不会发生。

  • 有 HarfBuzz 时：按"字体 + 方向"切段 → 每段 hb_shape → 取字形下标 → 用 QL_GLYPH_ID_BASE + gid 这个合成码位复用原来那套有序字形缓存 （真实码位 ≤ 0x10FFFF，撞不上）；
  • 没有 HarfBuzz 时：逐码位查字形 + 逐字回退，行为与 B8 之前逐像素一致 （没有连字与字距）。

HarfBuzz 不写进链接依赖：构建期找到头文件就直连是理想路径，但很多发行版 只装运行库（libharfbuzz.so.0）而没有 -dev。所以这里用 dlopen + 手写的 16 个符号白名单（hb_glyph_info_t / hb_glyph_position_t 的布局从 1.x 起没变）， 拿不到就退回内建 —— 用户装不装库都能跑。

4. 双向：先整形后重排，不要先重排再整形

这是最容易写错的地方：

错：bidi 重排文本 → 交给 HarfBuzz 整形 → 阿拉伯字母变成一串孤立形
对：按"字体 + 方向"切段 → 每段整形（HarfBuzz 按方向给出视觉顺序）→ 段落 RTL 时倒段

direction: rtl 的段落里，"阿拉伯文 + 数字"会切成两段：阿拉伯段按 RTL 整形 （HarfBuzz 输出就是视觉顺序），数字段按 LTR 整形（UAX#9 里数字是"二级"， 整体保持 LTR），最后把段顺序整体倒过来。

内建路径（没有 HarfBuzz）没有连写能力，只能先把整行按 UAX#9 子集排成视觉顺序 再逐字画 —— 顺序能读对，但没有连写。

unicode-bidi：normal / embed / isolate 按同一层处理，bidi-override 记成 "强制按段落方向排"。嵌套隔离与括号镜像没做（见 §9.2 表格）。

5. 真字重 / 真斜体

@font-face 声明了 700 或 italic 字面时，font_of_style() 按"字重距离 + 斜体是否 匹配"挑最接近的字面；挑到的字面如果本身就是粗/斜体（QLFont.is_bold/is_italic）， 绘制层就不再合成（ts->bold && !font->is_bold 才抹粗）。挑不到真字面时退回原来的 合成加粗/倾斜 —— 这条兜底必须留着，否则"只装了一份 regular"的机器上粗体会消失。

20. 三处"看起来简单、其实不简单"

写在这里，免得后面有人当"漏了"顺手补成半成品：

  1. opacity 在"有子节点"时走离屏图层，单节点时不走。真 CSS 永远先合成整棵子树； 本库对单节点保留"把 alpha 乘进每个绘制入口"的老做法 —— 因为一个节点内部没有 "图元互相覆盖"这回事，两者逐像素等价，而省掉一层缓冲。一旦有子节点就必然走图层 （否则重叠区会乘两次 alpha、比别处更深）。判据见 style_needs_layer()，实现见 §18.10。
  2. margin: auto 是布局概念，不是值解析。块级盒要在有确定可用宽度时分掉剩余空间； flex 里的 auto margin 又是另一套（吸收剩余空间）。改动落在 layout_node() 与 flex 求解器两处。
  3. letter-spacing / word-break / text-overflow 都要动 ql_text_wrap()。 断行只有一份实现，布局（数行算高度）与绘制（逐行发射字形）共用它 —— 这是"布局与绘制对行数有分歧"这类 bug 的唯一防线。改它必须两边同时验。 已经落地的做法：折行参数收进 QLTextWrapOpt（ql_text_wrap_opt）， 布局与绘制都从 QLUIStyle 用同一个 wrap_opt_of() 取值。

21.3 四个反直觉的判断

  1. CSS_SELECTOR_ADV 是唯一"裁了不省多少"的包。B2 全部在构建期展开 （:nth-child → 内部类、::before → 真节点），运行期零成本。 裁它只省解析器代码（几 KB），不省 RAM、不省每帧开销。 MCU 上更值得的做法是：保留它，因为它让"同一份 HTML"能两端跑， 而省下的那点 Flash 比"改两套 HTML"便宜得多。
  2. CSS_GRADIENT 在 GPU 上几乎免费（顶点颜色插值，不加顶点、不加 draw call）， CPU 侧才是逐像素成本。所以"给 MCU 留渐变、裁掉阴影"是合理组合 —— 包之间是正交的，不搞"要么全有要么全无"。
  3. CSS_GRID 裁掉之后页面会变慢，不是变快（§11 实测：嵌套 flex 拼 3×3 要 0.427 ms，Grid 只要 ≈0.229 ms）。所以"MCU 上关 Grid"只在Flash 紧张 时才划算；Flash 够的板子建议留着，让同一份 HTML 两端通用。
  4. CSS_ANIM 与省电相关。关掉它不仅是省代码：没有 animation 就没有 "主循环必须一直醒着"的理由。MCU 上关这个包等于强制静止界面，这对电池更实在。

关键点：报错不能因为裁剪而消失。 关掉 CSS_SHADOW 之后写 box-shadow， 必须报"本构建未启用 QL_FEAT_CSS_SHADOW（阴影）"，而不是静默忽略 —— 否则"PC 上看着对、板子上错位"的老问题会从标签那边原样搬过来。

21.5 与 blob 的关系

裁剪不影响 blob 的读写。 理由与标签一致：结构体字段永远全量、 枚举永远全量，所以：

  • 全量构建产出的 .qlui，在裁剪构建上能读、能布局、能画 —— 只是被裁掉的效果不生效；
  • 反过来也可以（裁剪构建产出的 blob 在全量构建上读，一切正常）。

这让"PC 上设计、板子上跑"不需要两套产物格式。代价是裁剪构建的 .rodata 里 仍有那些属性名字符串（约 700 字节，k_supported_props[]）。

21.6.1 与 HTML5 能力包的交叉依赖

两边不是独立的 —— 有几个交叉点必须写进构建期检查（qltext cc 的报错里点出来）：

HTML5 包 需要哪些 CSS 包 说明
CONTROL（input/select/textarea） CSS_BASE 输入框的框体、光标都是 BASE 的绘制原语
IMAGE（<img>） CSS_BASE + 可选 CSS_RADIUS（圆角裁图）/ CSS_IMAGE_FIT（object-fit） 图像管线自己在 QL_FEAT_IMG_*
EMBED 占位盒 CSS_BASE 1px 边框 + 居中文字
任意包 + box-shadow / 渐变 / 模糊 / 动画 对应的 CSS_* 缺一个就报错，不静默丢效果

规则一句话：HTML5 包决定"这个标签能不能用"，CSS 包决定"它能不能被画得好看"， 两者都不满足时，报错信息里要同时点名（例： <dialog>: 需要 QL_FEAT_UI_CONTROL；它的 box-shadow 需要 QL_FEAT_CSS_SHADOW（本构建未启用））。

21.7 每个包的验收

一个新包落地时必须同时满足四条，缺一条就是"半个功能"：

  1. 关掉能编译：-DQL_FEAT_CSS_X=0 全量测试仍 60/60（用 lenient 或不用该特性）；
  2. 关掉会报错：写该属性时错误文案点名包名，且给出替代方案；
  3. 体积真的降：size build/libqlgl.a 前后对比，降幅记在包里；
  4. 两端一致：包开着时 test_gl_vs_cpu 逐像素一致（绘制类包强制）。

23. 怎么新增一个 CSS 属性（检查清单）

照着走，漏一步就会留下"能解析但没生效"或"只在一个后端生效"的坑：

  1. 解析：src/ui/qlui_parse.c - 加进 k_supported_props[]（否则报"不支持的属性"）； - 写 parse_xxx()，错误文案要能定位（set_error("%s: ...", where)）； - 若要进关键帧，再加进 k_keyframe_props[]； - 若是简写，在 expand_shorthands() 里展开成长属性（简写本身不落结构体）。
  2. 字段：include/qlgl/qlui.h 的 QLUIStyle - 只在末尾追加；抬 QL_UI_BLOB_VERSION；tools/qltext 的 Python 侧同步。
  3. 生效： - 布局类 → layout_node() / flex 求解器； - 绘制类 → src/ui/qlui.c 的 render_node()，且同时改 src/draw/qldraw2d.c（CPU） 与 src/port/qlgfx_gl.c（GL）。
  4. 测试： - 语义类：新建/扩 test/web/test_*.c，命中与不命中两侧都断言； - 绘制类：扩 test_effects（CPU 像素）+ 跑 test_gl_vs_cpu（两后端逐像素一致）。
  5. golden：test_golden 基准图会变，重生成并逐张看差异（别一把 cp 过去）。
  6. 文档：本文对应行改状态；QLUI阅读指南 补"实现要点/踩坑"；教程给个最小例子。
  7. 裁剪：要能被 MCU 裁掉就加 QL_FEAT_CSS_* 宏，按 §21 的口径裁绘制路径， 并走 §21.7 的四条验收（关掉能编译 / 关掉会报错 / 体积真的降 / 两端一致）。
  8. 归包：把新属性填进 §21.2 的包表。新建包之前先问"它能不能并进已有的包" —— 包太多会让"给板子选开关"变成一件苦差事。
