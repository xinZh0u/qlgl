2. 能力包

一个"包"= 一组标签 + 支撑它们的那部分引擎。包是编译期开关，也是构建期报告的单位。

现状（老实说）：除 QL_FEAT_UI_META、QL_FEAT_UI_IMAGE 与 QL_FEAT_IMG_* 之外，表里的宏目前只有名字、还没进代码（grep 不到）。 它们是"裁剪时的口径"，不是现在能 -D 的东西。已落地的开关见 图像管线设计 §2 与 include/qlgl/qlconfig.h。

CORE 里那 62 个是"不需要任何额外运行期机制、只靠样式+布局就能画"的那批 （含滚动容器）。判据是"要不要专用机制"，不是"有没有状态"：

  • <input> / <select> 是状态最重的两个（光标、选区、覆盖面板），但正因为如此 它们必须能被裁 —— 所以归 CONTROL；
  • <output> / <datalist> 其实零成本（前者等价 span，后者 display:none）， 仍归 CONTROL 是因为用户视角它们是表单控件，一起裁更省心。

3. 一条硬约束：枚举不可条件化

QLUITag 的数值会写进 blob（QLUINode.tag 是 uint16 索引），而且三张表 （QLUITag / k_tags[] / s_tag_names[]，外加 qltext 的 TAG_NAMES[]）必须同序。

所以：

允许 禁止
在末尾追加枚举项 因为"MCU 不用"而删掉/挪动枚举项
用宏裁掉函数体、UA 默认分支、绘制路径 用宏裁掉枚举项本身（值会错位，blob 跨平台就废了）
用宏裁掉报错文案 让同一份 .qlui 在两个平台上解释出不同标签

结论：枚举与名字表永远全量。代价是 .rodata 里多约 1.2 KB 字符串 （114 条名字 + 指针表），换回来的是"一份 blob 到处能读、调试名永远对得上"。

如果某天真的差这 1 KB，再加一个 QL_CFG_UI_TAG_NAMES_MIN（名字表退化成 ql_ui_tag_name() 返回 "?"），那是独立的一步，和裁包无关。

4. 裁包之后会发生什么

现状：机制与第一个包（META）已经落地，开关在 qlconfig.h： QL_FEAT_UI_META（默认 1）与 QL_CFG_UI_LENIENT_TAGS（默认 0）。 其余包（TEXT / TABLE / IMAGE / CONTROL / EMBED）随实现追加， 在那之前它们的标签还不在枚举里，遇到就是"不认识的标签"报错。

解析器先按名字认标签（tag_index()，全量表），再看这个标签所属的包开没开：

模式 行为
strict（默认） 明确报错，文案里点名缺哪个包：
<table>: 这个构建关掉了表格（QL_FEAT_CSS_TABLE=0）
lenient 降级成 div（块级）/ span（行内），并计入 doc->degraded_tags，ql_ui_load_text 之后可查

两条都不静默：strict 失败在编译期（CI 能拦住），lenient 有计数与名单（运行时能打日志）。 这就是本库"明确失败优于半个正确"的落地方式 —— 降级是显式声明的，不是悄悄发生。

lenient 的典型用途：MCU 上贴外部 HTML 片段、只想要"能看就行"。

6. 构建期就该知道结果

现状：下面的 --features 参数还没实现（qltext check 现在只报"能否编译"）。 这一节是设计意图 —— 包的名字在这里是用户可见的报错单位，所以名字得起对。

qltext 拿得到目标平台的能力包，所以不用等到跑起来才发现被降级：

$ qltext check --html app.html --css app.css --features core,image
app.html: 42 个节点，使用标签 9 种
  <table>   ×2  需要 QL_FEAT_CSS_TABLE  → 会被降级成 div
  <img>     ×3  ✅
  <ruby>    ×1  需要 QL_FEAT_UI_TEXT   → 会被降级成 span
结论：3 处降级。要么开包，要么改界面。

同一套开关也用在 qltext cc --features ...（生成 C 时直接按目标平台裁）。
