图像管线设计（<img> / 解码 / 绘制）

状态：设计；P3a 已实现（2026-11-09）。目标读者：要实现解码器、blit_image、<img> 布局与 工具链转码的人。文档站上的覆盖度清单见 HTML5 标签覆盖与裁剪。

这份文档定三件事：格式怎么分工、数据放在哪、绘制怎么落到两个后端。 每一节都给出"为什么"和"不做什么"，因为图像是最容易把"外来数据"引进来的一块， 而这个库的红线是外来数据必须有界。

0. 结论摘要

不分平台，只分开关。 每个能力都是独立的编译期开关（像 Linux 的 Kconfig）， "PC 配置"和 "MCU 配置"只是两套预设，不是两套代码路径 —— 任何组合都合法。

问题 决定
自己写还是调库 自有解码器写 BMP / QOI / PNG / GIF（首帧）；JPEG 一律不自己写（给平台后端）。GIF 的动画仍不做
构建期转码 一等公民：qltext cc --root 在开发机上解好，产物直接是目标像素格式。PC 想用也可以 —— 编译期多几 KB 换"零解码 + 像素完全确定"
运行时解码器 BMP / QOI / PNG / GIF 各自一个开关，默认全开；-DQL_FEAT_IMG_PNG=0 就只少 PNG
GIF QL_FEAT_IMG_GIF：自有 LZW，无外部依赖，任何平台都可用；只取首帧
JPEG QL_FEAT_IMG_PLATFORM + 平台后端（libjpeg-turbo / ImageIO / WIC / BitmapFactory）。想编进来就编，不想就砍 —— 砍掉后遇到 JPEG 明确报 QL_ERR_UNSUPPORTED
stb_image 不进产线，只做测试用的对拍 oracle
像素格式 构建期就定型（--pixel-format rgb565/rgb888/rgba8888/a8），运行时零转换
解码时机 RAW 不解码；需要解码的格式在 ql_ui_build 时一次性解（上限 QL_CFG_UI_IMAGE_MAX）；尺寸在 doc 里就有，所以布局永远不依赖解码
绘制 新增 QLDraw2D->blit_image()；CPU 逐像素、GPU 一次纹理上传 + 一个 quad（复用现有 mode 分派）
尺寸控制 object-fit 在绘制期算，不动布局；border-radius / clip-path 复用现有 SDF 与 mask
失败语义 构建期解码失败 → 明确报错；运行期注册失败 → 明确错误码 + 占位不画（不猜）

1. 目标与非目标

目标

  1. <img src> 既能"贴一个任意格式的图片文件，构建期转好直接显示"， 也能"运行期拿字节自己解" —— 两条路都由开发者按需选择，不被平台预设绑死。
  2. 解码路径完全有界：任何输入（含畸形/超大）都不许 OOM、不许越界、不许死循环。
  3. 有 alpha 的 PNG 能正确叠加（源覆盖 + 圆角裁剪）。
  4. 解码结果只解一次，每帧只做像素搬运。

非目标（明确不做）

  • GIF/WebP/APNG 的动画播放（要帧时钟 + 帧缓冲 + 循环策略；首帧可以，动画不做）。
  • SVG（等于第二个渲染器，见覆盖表 §5）。
  • 图片编辑、缩放算法的高质量版本（默认最近邻；双线性作为可选项，见 §6.2）。
  • EXIF 方向自动旋转（PC 后端解码时由平台库处理，自有解码器不管）。

2. 能力开关（不分平台）

设计原则：能力正交、各自可裁、组合都合法。没有"MCU 版本"和"PC 版本"两套代码， 只有一套代码 + 一组开关；预设只是把常用的组合打包，随时可以单品覆盖。

2.1 开关清单

能力 宏 默认 关掉的后果 依赖

2.2 预设（只是宏的打包，不是代码分支）

预设 展开 典型用途 代码量
full（默认） 全开 PC / 移动 / 资源充足的板子 全量
lean IMG_PNG=0、IMG_GIF=0、IMG_PLATFORM=0；留 BMP + QOI Flash 紧但想要运行期解码 省掉 inflate + PNG + GIF + libjpeg ≈ 2.9K 行
raw-only 除 <img> 与 RAW 外全关 只吃构建期转码产物：零解码器、零图片 RAM 只剩 blit

用法（CMake 侧只需一行，单品的 -D 永远优先）：

cmake -B build -DQLGL_IMG_PRESET=raw-only        # 预设
cmake -B build -DQL_FEAT_IMG_PNG=0               # 单品覆盖：只砍 PNG，别的照旧
cmake -B build -DQL_FEAT_IMG_PLATFORM=1 -DQLGL_BUILD_JPEG=ON   # 把 JPEG 编进来

"硬要保留也可以"是要点：开关之间没有互斥，raw-only 加上 -DQL_FEAT_IMG_PNG=1 也完全合法 —— 预设只决定起点。

2.3 产物格式与开关是正交的

--format raw|qoi|png-pass 决定"资源以什么形式进固件"，QL_FEAT_IMG_* 决定 "固件里有哪些解码器"。两者组合：

资源形式 需要哪个开关 Flash RAM 什么时候选
RAW（目标像素格式） 无 w·h·bpp 0（px 直指 .rodata，owned=0） 默认首选。Flash 换"零解码 + 像素完全确定"
QOI IMG_QOI 约 RAW 的 50–70% w·h·bpp（解码缓冲） Flash 紧张、图多、同屏少
PNG IMG_PNG + inflate 小 w·h·bpp + 行缓冲 需要无损且"改动后不动工具链"
GIF IMG_GIF 小 w·h·bpp + 16KB LZW 表 只需要首帧的调色板图

RAW 在 PC 上也是合法选择，而且很划算：编译期多几 KB，换来启动零解码和 像素完全确定（golden 基准不会因为换解码器/换库而漂移）。

2.4 为什么 JPEG 不自己写，而 PNG / GIF 自己写

  • JPEG：baseline 1200–1800 行、渐进式再 600 行、4:2:0/4:2:2 上采样、restart marker、 色域转换。手写的典型失败不是崩溃而是色偏与块效应 —— 最难查的那类 bug。 所以它做成"开关 + 平台后端"：想要就编，不想要就砍，但我们不自己实现。
  • PNG：难点只有 DEFLATE 一处，而 DEFLATE 是无状态纯算法（32KB 固定窗口 + 输出直接写进目标行缓冲），可以完全有界、可以 fuzz。其余（chunk / 5 种 filter / 调色板 / 位深 / tRNS）都是纯数据搬运。
  • GIF（首帧）：只有三个部件 —— 调色板查找、LZW 解码（码长 3..12 位）、 隔行四趟行序。没有色彩管线，写错的后果是"解不出来"而不是"颜色不对"， 所以风险等级和 QOI 一样。动画不做（那才是初稿把它推给平台后端的原因）。
  • 不用 stb_image：① 7k 行不可裁；② 整幅解码到单一 malloc 缓冲； ③ 顺带支持 GIF/PSD/HDR，等于扩大攻击面；④ 部分路径用 float 做颜色转换。 它能当测试 oracle（离线跑），但不进产线。

3. 三个入口（入口 1 是默认，其余是增量）

                     ┌── ① 构建期（零解码路径的入口，任何平台可用）
                     │    qltext assets：系统库/自有解码 → 直接转成目标像素格式（RAW）
  <img src="logo.jpg">┤                     → .rodata，px 直指，owned=0，运行时零解码
                     │
                     └── ② 运行期：ql_ui_register_image(ui, "logo.jpg", bytes, len)
                          bytes ──► 格式探测 ──► ③ 自有解码器：BMP/QOI/PNG（DECODE=1 才有）

                                                │
                                                ▼
                                    QLImage{ w,h,stride,format,px }
                                                │
                                                ▼

入口 场景 平台 运行时依赖
① 构建期转码（<img src> 由 qltext assets 处理） 产品 UI 素材、图标、开机图 任何平台 零（连解码器都不编进去）
② 运行期注册 从文件/网络拿到图（任何平台） 任何平台 ③ 或 ④
③ 自有解码器 BMP/QOI/PNG 运行期动态图片；或想用 QOI 省 Flash 可选（各自一个开关） 编译进来

关键点：入口 ① 在开发机上就把"解码 + 像素格式转换 + 可能还有缩放"全做完， 所以选择这条路的固件里既没有解码器、也没有图片 RAM —— 只剩"指向 Flash 的指针 + 宽高"。 ②③④ 是按需打开的增量能力，每个都由自己的宏在编译期裁掉。没有哪条是"某平台的路径"： 想全要就全开，想只留 ① 就全关。

4. 数据模型

4.1 解码结果（跨模块唯一契约）

typedef enum {
    QL_IMAGE_RGB565 = 0,     /* 2 B/px */
    QL_IMAGE_RGB888,         /* 3 B/px */
    QL_IMAGE_RGBA8888,       /* 4 B/px，非预乘 */
    QL_IMAGE_A8,             /* 1 B/px，蒙版/图标 */
} QLImageFormat;

typedef struct {
    const uint8_t *px;       /* 有效数据；NULL = 还没解码或解码失败 */
    uint32_t       len;      /* 字节数 = stride * h */
    uint16_t       w, h;
    uint16_t       stride;   /* 字节/行（允许大于 w*bpp，方便对齐） */
    uint8_t        format;   /* QLImageFormat */
    uint8_t        owned;    /* 1 = 归 QLUIRoot，ql_ui_free 负责释放 */
} QLImage;

三件事刻意没做：

  • 没有 mipmap/多级缩放：缩放是绘制期的事（§6.2），不做纹理金字塔。
  • 不预乘 alpha：预乘能让 GPU 混合公式更简单，但会让 CPU 侧每次缩放都要反算， 而且 QLImage 还要能被后端复用。统一不预乘，混合时现算。
  • stride 而不是"w × bpp"：硬件对齐、行缓冲、以及"把一行解码进目标图的一行" 都要求每行能独立寻址。

4.2 doc 里的资源条目

typedef struct {
    uint16_t name;      /* text 池下标：资源名（"logo.png"），报错与运行期注册都靠它 */
    uint32_t off;       /* 编码字节在资源段内的偏移 */
    uint32_t len;       /* 编码字节数 */
    uint16_t w, h;      /* 构建期已知的原始像素尺寸 */
    uint8_t  format;    /* QLImageSrcFormat：BMP / QOI / PNG / RAW / 未知 */
    uint8_t  reserved;
} QLUIImageSrc;
  • w/h 存进 doc，所以布局永远不依赖解码：哪怕这张图解码失败，位置和占位尺寸 仍然是对的（画个占位框就行）。这也是将来做"惰性解码"的前提。
  • off/len 指向新增的 blob 段（QL_UI_BLOB_VERSION → 13，off_images / off_image_data 两个字段）。裸机侧也可以不用 blob，让工具直接生成 static const unsigned char 数组，由 QLUIDoc.images[i] 指过去。

4.3 节点怎么指向图像

<img> 的 src 存进 node->text（复用文本池下标，存的是资源名）。

  • 不新增 QLUINode 字段（那是每个节点 2 字节的常驻成本）；
  • text 本来就是"text 池下标"，资源名也在同一个池里，语义一致；
  • 需要配套的两处特殊处理（必须写测试钉住）： 1. border_width_of() / max_content_main() 里"文本尺寸"的判断要排除 <img>， 否则会按资源名的宽度排版； 2. ql_ui_node_text() 对 <img> 返回 NULL（名字不是要显示的文字）。

alt 属性暂时只存不用（没有 tooltip / 朗读），不静默假装有，文档里写明。

5. 解码层

5.1 自有解码器

格式 要点 量级
BMP 24/32 位、8 位调色板、BITFIELDS（565/888）、自下而上/自上而下、行长补齐 4 字节。不解 RLE ~150 行
QOI 规范极小（index/run/diff/luma/rgb/rgba 六种 op）。适合当"构建期转码的中间格式" ~130 行
PNG 见下 ~1300 行
GIF（首帧） 逻辑屏幕 / 全局+局部调色板 / 图形控制扩展（透明色）/ LZW / 隔行四趟 / 画布偏移。不解动画，第二帧起忽略 ~260 行

PNG 拆成两层（src/draw/qlinflate.c + src/draw/qlimage.c 的 PNG 段）

inflate（DEFLATE 解码，QL_FEAT_IMG_INFLATE）
    ↓ 输出 = h*(1+row_bytes) 的"带过滤字节的行数据"
PNG 容器（chunk / 反过滤 / 颜色转换）
  • inflate：stored / 固定 Huffman / 动态 Huffman，长度与距离码表全按 RFC 1951。 不分配滑动窗口 —— 输出缓冲本身就是窗口（回溯距离 ≤ 32768，且合法的回溯一定 指向已解出的字节），所以额外 RAM 是 0，栈上只有 2×608 字节的 Huffman 表 + 256 字节输入暂存。实测 Release 下 1024×1024 RGBA ≈ 26 ms（155 MB/s）， 纯解码发生在构建期或注册时，不进帧。
  • 输入是流式回调：IDAT 会被拆成多个 chunk，中间夹 12 字节（长度/类型 + CRC）， 所以 ql_inflate 收 QLZSource{read, ctx} 而不是一段连续内存 —— 零拷贝、不拼接。
  • IDAT 是 zlib 数据流（RFC 1950）不是裸 DEFLATE：开头的 2 字节头要校验 （CM==8、CINFO<=7、FCHECK、FDICT==0），结尾 4 字节 Adler-32 顺手校验 （几乎零成本，坏流当场拒绝）。
  • PNG：IHDR/PLTE/tRNS/IDAT/IEND；位深 1/2/4/8/16；颜色类型 0/2/3/4/6；filter 0–4 （None/Sub/Up/Average/Paeth）；interlace 为 1 时 明确报 QL_ERR_UNSUPPORTED （Adam7 要做 7 趟子图重建，收益远小于风险）。
  • 不校验 chunk CRC：CRC 只说明"传输没坏"，而本库关心的是"能不能安全解出来"。 结构性错误（块越界、码表非法、回溯越界、调色板索引越界、行数对不上、Adler 不符） 一律明确失败。少一份 1 KB 查表，代价写在这里。
  • PNG 全是大端（BMP/QOI 是小端）—— 读长度字段时搞错的表现是"块长度像天文数字"。
  • 输出：按目标 QLImageFormat 直接转换（调色板展开、16→8 取高字节、灰度复制三通道、 alpha 直通）。
  • 上界：过滤后的字节数按"解码预算的 2 倍 + 每行 1 字节"卡（16 位 RGBA 是 8 字节/像素， RGBA8888 输出只有 4），这样 1024×1024 的 16 位 RGBA 正好卡在边上而不被误杀。

测试（test_png 1253 项 / test_png_assets 43 项 / test_png_fuzz 5 轮 4700 例）：

层 手段
容器与位深 测试里现场构造 PNG（只用 stored deflate 块），15 组 (颜色类型, 位深) 逐像素断言
反过滤 5 种 filter 逐行轮换，4 组 (类型, 位深)（含 bpp=8 的 16 位 RGBA）往返比对
真实压缩流 test/assets/png/*.png（PIL 生成，动态 Huffman）+ *.rgba 基准逐字节比对
有界 / 坏数据 30 条错误路径 + 4700 例随机/变异输入（ASan+UBSan 下只允许"返回失败"）

5.1.1 raw-only 配置（零解码器）

#define QL_FEAT_UI_IMAGE         1
#define QL_FEAT_IMG_BMP          0
#define QL_FEAT_IMG_QOI          0
#define QL_FEAT_IMG_PNG          0
#define QL_FEAT_IMG_INFLATE      0
#define QL_FEAT_IMG_PLATFORM     0
  • 只认 QL_IMAGE_SRC_RAW（构建期已解好的位图），px 直接指向资源段；
  • QLImage.owned = 0 → ql_ui_free 不碰它（数据在 .rodata/Flash）；
  • 链接期省下：inflate + PNG 约 1.3K 行、QOI 130 行、BMP 150 行 —— 这是本库能给 "最小固件"的最直接让步；
  • 但这不是 MCU 专属：PC 一样可以用（启动零解码、golden 像素完全确定）。 反过来，资源充足的板子把开关全开也完全合法 —— 组合没有限制。

这条路径必须有一条构建配置的测试：关掉全部解码器时用一份 RAW 资源跑完整 布局 + 绘制，并确认 ql_image_decode() 对 PNG 字节返回 QL_ERR_UNSUPPORTED。

5.2 平台后端（JPEG 走这里）

调度顺序是自有解码器优先：

格式识别（AUTO 探魔数：PNG / GIF8 / BMP / qoif / FFD8FF）
   ├─ RAW/BMP/QOI/PNG/GIF → 自有解码器
   │      └─ 返回 UNSUPPORTED（该格式被裁 / PNG 是隔行 / JPEG）→ 再问后端
   └─ 后端返回 0 或没装后端 → QL_ERR_UNSUPPORTED

这样后端永远抢不走原生支持的格式，又能补上原生明确不做的分支 —— 例如隔行扫描的 PNG：自家解码器说"不支持"，装了后端就由后端接手 （test_image_backend 用这个交叉点钉住了优先级）。

不信任第三方库（这是"外来数据进绘制层"的唯一关口）：

  1. 后端的 QLImage 回来先过 ql_image_validate()：stride ≥ w·bpp、 len == stride·h、format 在枚举内、w·h ≤ QL_CFG_IMAGE_MAX_PIXELS、 owned 只能是 0/1；
  2. 不合格 → 释放并按失败处理，ql_image_last_error() 写明是哪个后端、坏在哪；
  3. 合格但格式与请求不同 → ql_image_convert() 统一收口（转换代码只有一份）。
平台 实现 状态
Linux / PC libjpeg-turbo（src/port/qlimage_jpeg.c，QL_FEAT_IMG_LIBJPEG） ✅
macOS / iOS ImageIO（CGImageSourceCreateWithData） 接口就位
Windows WIC（IWICImagingFactory） 接口就位
Android BitmapFactory.decodeByteArray（JNI，宿主提供） 接口就位
无系统库的板子 不提供 → JPEG 魔数 → QL_ERR_UNSUPPORTED（明确失败） 默认

libjpeg 参考实现里有三处必须这么写：

  • error_exit 必须换成 longjmp：libjpeg 默认的 error_exit 是 fprintf + exit(1) —— 一张坏图会让整个应用退出。这是接 libjpeg 最容易踩的坑。
  • 像素缓冲要声明在 setjmp 之前且是 volatile：libjpeg 可能在扫描行中途报错， 那时缓冲已经分配；非 volatile 的局部变量在 longjmp 之后的值是未定义的。
  • "数据提前结束"按失败处理：libjpeg 会把缺的行填成灰色并只给警告。 那是典型的"半个正确"，本库不接受 —— 监听 JWRN_JPEG_EOF，见过就整张丢弃。

JPEG 是有损的，所以对拍不比逐字节，而是 最大色差 ≤ 3 且平均色差 < 1 （test_jpeg）—— 足以抓出通道错位/色偏，又不会因为不同 SIMD 路径的舍入假报。

5.2.1 GIF 为什么又自己写了

设计初稿写的是"JPEG / GIF 一律不自己写"，理由是 GIF 的动画（帧时钟、帧缓冲、 循环策略）。落地时改了：

  • 静态 GIF 只是"调色板 + LZW + 隔行"，和 QOI 一个难度档，没有色偏风险 （不像 JPEG 那套色彩管线）；260 行、可 fuzz、可完全有界；
  • giflib 并不像 libjpeg 那样到处都有（本机就只有运行时 .so、没有头文件）；
  • 更重要的：自己写之后 GIF 在任何平台都能用，不必等某个后端。

动画仍然不做，这条限制没变：第二帧起忽略，<img> 拿到的是首帧。

5.3 有界与失败语义

常量 默认 作用
QL_CFG_UI_IMAGE_MAX 8 一个界面最多几张图（运行期池条目数）
QL_CFG_IMAGE_MAX_BYTES 512 KB 单张编码字节上限（超出直接拒绝）

必须显式检查的溢出（经典漏洞，写测试钉住）：

/* w * h * bpp 会溢出 32 位；先除后乘或判上界 */
if (w == 0 || h == 0) return 0;
if ((uint32_t)w > QL_CFG_IMAGE_MAX_PIXELS / (uint32_t)h) return 0;   /* 除比乘安全 */
if ((uint64_t)w * bpp > 0xFFFFu) return 0;                            /* stride 是 uint16 */

失败语义

6. 绘制层

6.1 接口

/* QLDraw2D 新增一个函数指针 */
void (*blit_image)(QLDraw2D *self, const QLImage *img, QLRect dst,
                   const QLRect *src, uint8_t alpha);
  • src == NULL → 整幅；否则取子矩形（给 object-fit: cover 用）。
  • dst 是设备像素矩形（QLDraw2D 已经处理了 scale_fx、offset、elem_scale）。
  • 缩放由后端负责（dst 与 src 尺寸不同就是缩放）。
  • 裁剪/遮罩不在接口里：沿用 d2d->set_clip() 与 set_mask()，所以 overflow: hidden、border-radius、clip-path: circle() 自动生效，不用写第二套。

6.2 CPU 实现要点

项 决定 为什么
缩放 默认最近邻；QL_CFG_IMAGE_BILINEAR=1 时双线性 最近邻成本是双线性的 1/4，且 UI 素材大多整数倍缩放
alpha 源覆盖：out = src*a + dst*(1-a)，逐像素用 8 位定点 与 fill_rect(alpha) 同一套混合，结果与形状一致
格式矩阵 源 RGB565/RGB888/RGBA8888/A8 × 目标 RGB565/RGB888/ARGB8888/L8 12 种组合，用 switch 特化热路径（照抄 qlcanvas.c 已有的形状填充套路）
圆角 复用 fill_round_rect 的 SDF 判定（每像素算到圆角矩形边界的距离） 不要新写一套抗锯齿
空图 img->px == NULL → 画一个 1px 虚线框的占位（仅 QL_CFG_IMAGE_PLACEHOLDER=1） 让"图没加载"肉眼可见

6.3 GPU 实现要点（已实现）

项 做法 坑
上传 每个 QLImage 一次 glTexImage2D，按 (px,w,h,format) 缓存（8 条，环形替换） 行宽不等于 w*bpp 时要用 GL_UNPACK_ROW_LENGTH + GL_UNPACK_ALIGNMENT=1
内部格式 RGB565 → GL_RGB565；RGB888 → GL_RGB8；RGBA8888 → GL_RGBA8；A8 → GL_R8 5_6_5 配 GL_RGB8 是 INVALID_OPERATION：纹理没数据 → 采样全 0 → 图片整块消失（不是变色，所以特别难查）
采样器 新增 u_image（texture unit 2）；没有图片的批次绑 1x1 占位 采样器必须绑东西，否则采样结果是未定义值
批次 图片单独成批：整帧顶点共用一个纹理（图集），图片是另一张 → flush → 上传/绑定 → 画 → flush 与毛玻璃中途提交是同一个套路
滤波 必须与 CPU 一致：QL_CFG_IMAGE_BILINEAR=0 时用 GL_NEAREST 用 GL_LINEAR 会把半透明边缘插成渐变，CPU/GPU 比对立刻红（实测 3.4% 差异）
uv 上传第一行 = 图像顶部 = v=0，所以不翻（FBO 那种自下而上的纹理才翻）
着色 mode 5 = 位图（直接采样），mode 6 = A8 蒙版（rgb 取顶点色、alpha 取红通道）

验收：test_gl_vs_cpu 里新增一页"两张 <img>（RGB565 + 半透明 RGBA8888）"， CPU vs GPU 逐像素差异 0.00%，并断言批次数 ≥ 2（证明图片确实单独成批）。

7. 布局层

7.1 内在尺寸（intrinsic size）

<img> 是"用内在尺寸排版"的节点，和文本节点同构。两处必须改：

位置 现状 改法
border_width_of() node->text != NULL ⇒ 按文本宽度 先判 tag == IMG ⇒ 用 style->width 或资源 w + padding/border
max_content_main() 同上 同上，按行/列取 w 或 h

没有 width/height CSS 时用资源的 w/h；有 CSS 宽度时高度按 CSS 或按宽高比 推算（aspect-ratio 不做，直接 h = w * 固有h / 固有w，整数运算，避免浮点）。

7.2 object-fit

在绘制期算目标矩形，不动布局：

值 目标矩形
fill（默认） dst = 内容盒（允许变形，与浏览器默认一致）
contain 等比缩到完全装进内容盒，居中
cover 等比放大到盖满内容盒，居中，src 取中间那块
none 原始像素尺寸，居中，超出部分被 overflow 裁掉
scale-down contain 与 none 取小的那个

全部整数运算（用交叉相乘比较比例、整数除法取整），避免浮点代价与平台差异。

实现要点：

  • cover 的两个分支容易写反：box.w/iw > box.h/ih（受高度限制）时要裁上下， 否则裁左右。用交叉相乘判断，别用浮点除法。
  • none / contain 的目标矩形可能超出内容盒，绘制期用 set_clip 临时裁一下 （与 overflow: hidden 同效），画完恢复。
  • 圆角：blit_image 带 radius 参数，CPU 用与 fill_round_rect 同一个圆角 SDF 算覆盖率，GPU 在片元里用 sdRoundBox 乘进 alpha —— "圆形头像"不用自己套 mask。
  • 存储：QLUIStyle.font_flags 低 4 位是字体变体位，高 4 位是 object-fit （结构体仍是 120 字节，blob 不用再升版）；读取统一走 ql_ui_style_object_fit()。

7.3 <map> / <area> 热区

一张图上可以有几块可点区域。几何不进布局：<map> 与 <area> 的 UA 样式是 display:none，不产生盒子；热区数据存在 doc 的独立段里。

项 形式 说明
<map name="m"> 只提供名字 自身 display:none
<img usemap="#m"> 名字引用 允许写成 m（不带 #）
<area shape= coords= href= alt=> 空元素 shape：rect（默认）/circle/poly/default

配对在构建期完成：解析完整棵 HTML 后，把每个 <img usemap> 与 <map name> 对上，热区条目直接记下 <img> 的节点序号（QLUIArea.img）。于是运行期 没有"按名字查表"、没有字符串比较、<map> 写在 <img> 前面后面都一样。 <map> 里的文本节点（不在 <area> 里的）忽略。

存储（blob v14 新增两段）：

typedef struct {          /* 10 字节 */
    uint16_t img;         /* 关联的 <img> 节点序号 */
    uint16_t coord_off;   /* doc->area_coords[] 起始下标 */
    uint16_t href, alt;   /* 文本池下标，0xFFFF = 没有 */
    uint8_t  shape, ncoord;
} QLUIArea;
const int16_t *area_coords;   /* 所有热区共用的坐标池（图片像素，int16） */

坐标池是扁平共享的：热区条数受 QL_CFG_UI_AREA_MAX（默认 16）限制， 每条最多 128 个坐标 —— 而不是每条都开一个 int16_t[16]，MCU 上一页热区 只花"实际用到的坐标数 × 2 字节"。不需要热区时整套是 0 字节（area_count == 0）。

命中测试（ql_ui_area_at）：

  1. 取该 <img> 的实际绘制矩形（object-fit 之后，再与内容盒求交得可见区）；
  2. 点不在可见区 → 跳过；
  3. 把点按 img.w / dst.w 反算到图片像素坐标（整数除法，一张图只算一次换算）；
  4. 按形状判：rect 含边界（x0 > x1 自动交换）、circle 用 int64 比平方、 poly 走奇偶环绕（crossing number）、default 恒真；
  5. 命中第一条就返回（与浏览器一致）。

coords 数量与 shape 不自洽（rect 不是 4 个、poly 不足 6 个或奇数个、 default 带了坐标、写了非数字）→ 解析期报错，不做"猜一半"。 坐标超 int16 范围同样报错。

交互：ql_ui_set_area_cb() 注册回调，ql_ui_pointer_up 里先问热区 —— 命中就派发 area_cb(index) 并不再派发 click_cb（与浏览器"点击的 target 是 <area>，不是 <img>"一致）。ql_ui_area_href/alt/rect/image/get 提供 只读描述，href 只是字符串，本库不做导航。

已知限制：热区命中不叠加 transform（<img> 上带位移/缩放的写法下热区仍在 布局位置）；<area> 的 alt 不做提示气泡。

<img src="logo.png" alt="QLGL">
<img src="avatar.jpg" width="48" height="48">     <!-- CSS 尺寸优先 -->

9. 工具链：构建期转码（所有平台的默认路径）

实现形态与最初的草案不同：资源跟着 doc 走，所以不单开 assets 子命令， 而是给 cc / blob 加 --root —— 一个界面只有一份 .c / 一份 .qlui。

$ qltext cc --html app.html --css app.css --name app --out build/ \
            --root assets/ \              # <img src="x.bmp"> 按 assets/x.bmp 找
            --pixel-format rgb565 \       # 目标设备像素格式（决定产物）
            --scale 1                      # 可选：构建期整数倍缩小（面积平均）

qltext: 嵌入 1 张图片（32 字节，RGB565）
qltext: app -> build/ui_app.c（3 节点，…）

产出的 ui_app.c 里多两段，doc 字面量多四个字段：

static const uint8_t ui_app_img_data[32] = { 0xF8,0x00, … };
static const QLUIImageSrc ui_app_images[1] = {
    { .name = 0, .off = 0, .len = 32, .w = 4, .h = 4,
      .format = QL_IMAGE_SRC_RAW, .pixel_format = QL_IMAGE_RGB565 },
};
const QLUIDoc ui_app_doc = {
    …
    .image_count = 1, .image_data_size = 32,
    .images = ui_app_images, .image_data = ui_app_img_data,
};
参数 取值 说明
--root DIR — 资源根目录。不给就不嵌入任何图片（<img> 只能靠运行期注册）
--pixel-format rgb565（默认）/ rgb888 / rgba8888 / a8 构建期定型，运行时零转换
--format raw（目前唯一） qoi 需要编码器，待做
--scale N 整数 面积平均缩小；MCU 上直接拿目标尺寸

来源格式：现在支持 BMP 与 QOI（库里的解码器，与运行时是同一份代码，不会漂移）。 PNG 与 GIF 现在可以直接吃；JPEG 需要 libjpeg 后端（QLGL_BUILD_JPEG=ON 默认开）。

规矩没变：

  1. 构建期允许用任何库（那是在开发机上跑），运行时只认自有解码器。
  2. 文件缺失 / 解码失败 / 超上限 / 目标格式非法 → 构建失败，信息带路径。
  3. 同一张图多处使用只嵌一份；产出可提交进版本库（test/assets/ 就是这么用的）。

11. 内存账（举例）

场景 Flash（资源） RAM（解码缓冲） 说明
MCU 240×160 RGB565 背景，RAW 76.8 KB 0 px 指向 .rodata；一张就吃掉 1/4 个 256 KB Flash，所以背景图要么缩、要么用渐变画
MCU 240×160 RGB565 背景，QOI ~50–55 KB 76.8 KB Flash 省下来了，但 RAM 吃得下才行
MCU 32×32 图标 × 8（RAW） 16.4 KB 0 典型 UI 素材规模，这条路才现实
PC 800×600 RGBA8888 1.9 MB 同左（owned=1） 宽松
inflate 临时 — 0（窗口就是输出缓冲）+ 栈 1.5 KB DECODE=0 时整段不存在
PNG 过滤后字节 — h·(1+row_bytes)，临时 解码完立刻释放；16 位 RGBA 最多 8 字节/像素

小固件的推荐组合：RAW + --pixel-format rgb565 + --scale 预缩放， 放 .rodata，owned = 0，QLGL_IMG_PRESET=raw-only。 这样固件里既没有解码器、也没有图片 RAM —— 只有"指向 Flash 的指针 + 尺寸"。 这不是"MCU 专用路径"：任何平台想省 RAM/省启动时间都可以这么配。

P3e ✅ map/area 热区（rect/circle/poly/default，构建期绑定 <img>）+ picture/source + blob v14 0.5 天
P3g ✅ 平台后端接口 + libjpeg-turbo 参考实现 + GIF 首帧（自有 LZW） 1 天

合计 ≈ 12–15 天，img picture source map area 五个标签一次到位。

建议顺序：P3a ✅ → P3f ✅ → P3b ✅ → P3d ✅ → P3e ✅ → P3c ✅ → P3g ✅。 理由：P3a + P3f 就能端到端跑通"图片文件 → 构建期转码 → 固件里显示"这条 零解码路径（它不依赖任何解码器开关，是唯一"关掉一切也能用"的路）； 解码器与 PNG 都是在这之上的增量开关。

13. 风险与已知限制

风险 应对
P3c（PNG/inflate）最容易出隐蔽 bug 先把 fuzz 与对拍建起来再写解码主体；inflate 单独一个文件、单独一套测试
整数溢出 / 越界读 所有尺寸先过 §5.3 的检查；用 uint64_t 算中间值；ASan+UBSan 常态跑
平台后端返回脏 QLImage §5.2 的"回来先校验"关口
libjpeg 的 error_exit 直接 exit() 参考实现里换成 longjmp；test_jpeg 用截断/篡改输入钉住"只失败不退出"
每帧重复解码 failed 位 + 解码只在 build/register 时发生；测试钉住"每帧不动解码器"
开关组合爆炸 只测"预设三档 + 两个单品覆盖"，不测 2^8 组合；新增开关时必须同时给它一个预设归属
构建期转码工具变成必经之路 它会成为 MCU 的唯一入口，所以：① 工具的错误信息必须能直接定位到文件与原因；② 产出的 C 数组要能提交进版本库（不依赖每次构建都跑工具）；③ 给一条"手工写 RAW 数组"的文档路径，保证没有工具也能跑起来
golden 图受图片影响抖动 测试用的图片全部是程序生成的无损小图（纯色/渐变/四色块），不提交照片

明确不做：动画 GIF/APNG（只取首帧）、WebP、SVG、EXIF 旋转（自有解码器）、 图像金字塔/mipmap、srcset 选择、<picture> 的 media 查询。

GIF 的几条具体限制（都在 test_gif 里钉住）：只解第一帧；disposal 方法忽略 （没有第二帧要用它）；调色板索引越界 → 该像素留透明，不猜颜色；画布外的像素裁掉； 背景色不填（未覆盖处透明，与浏览器"逐帧叠加"的观感不同，但单帧看图更正确）。
