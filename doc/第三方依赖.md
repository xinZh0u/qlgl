# 第三方依赖与许可

> 状态：**现行清单（2026-12 核对）**。目标读者：打包/发版的人、评估"能不能用它"的人、
> 以及被法务问"你们用了什么开源库"的人。数据都是本机（Ubuntu 24.04、x86_64）实测。

一句话结论：**主库 MIT；最小构建零外部依赖；PC/Mobile 全量档只有 7 个运行期库，
而且全部是动态库（不占我们的二进制、可被系统替换）；MCU 档一个都不需要。**

## 1. 能不能引入一个库：三条红线

QLGL 是 MIT 的 C11 库，跑得起来的机器从 640 KB RAM 的 MCU 到桌面。任何一个第三方库进来都要过这三关：

1. **外来数据必须有界。** 解码器/解析器面对的是别人给的文件。库必须有明确的"最大尺寸"语义、
   失败必须能**干净退出**（不许 `abort`、不许无限分配）。这是 §2.2 里 libjpeg 要包一层
   `setjmp/longjmp` 的原因 —— libjpeg 错误路径默认直接 `exit()`。
2. **必须能在 MCU 上裁成 0。** 不是"关掉功能"，而是**关掉之后连符号都不进固件**。
   清单里 7 个库除了 `libm` 全部是真开关（见 §7 的体积账：MCU 全档 151,728 B，一个外部库都没链）。
3. **许可不能传染 MIT 主库。** 强 copyleft（GPL/AGPL）一律不走链接。目前唯一沾边的是
   fribidi（LGPL），处理方式见 §5.2。

反过来，**"能自己写就自己写"** 也是红线的一部分 —— 我们自己写了 DEFLATE、PNG、GIF LZW、
QOI、BMP、位图字体、UAX#9 子集（见 §4）。判断标准只有一条：

> **自己写的代码出错时，后果是"解不出来"还是"看起来对但其实不对"？**

PNG 的 DEFLATE 写错 → 校验和不过、直接失败，所以自己写（435 行）。
JPEG 写错 → 图能出来但颜色/块效应微妙不对，且要面对 20 年的霍夫曼+IDCT+色度上采样坑，
所以交给 libjpeg-turbo。字体同理：TTF 解析 + hinting + CJK 是几年工程，交给 FreeType。

## 2. 运行期依赖逐个说明

### 2.1 FreeType —— 矢量字体与任意字号

| 项 | 内容 |
|---|---|
| 语言 | C（自带 C 接口即原始接口） |
| 版本（本机） | 2.14.2，`libfreetype.so.6` **852 KB** |
| 代码位置 | [qlfont_ft.c](../src/text/qlfont_ft.c)（唯一接触 `ft2build.h` 的地方）、[qlfont_ft.h](../include/qlgl/qlfont_ft.h) |
| 我们只用它的 | `FT_Init_FreeType`（全局共享一个）、`FT_New_Memory_Face`（TTC 逐字面试探）、`FT_Set_Pixel_Sizes`、`FT_Get_Char_Index` / `FT_Load_Glyph`、`FT_Render_Glyph`（`FT_RENDER_MODE_NORMAL` → 8bpp 灰度）、`face->style_flags`（读 `FT_STYLE_FLAG_BOLD/ITALIC` 判断字面自带粗斜体）、`FT_Done_Face` |
| 我们不用它的 | 字距/连字（那是 HarfBuzz 的事）、`FT_Cache`（我们自己按字号做 glyph 缓存）、`FT_Outline` 自绘、bitmap/PCF/BDF 驱动、`FT_GlyphSlot` 的彩色位图（emoji） |

**为什么是它**：它已经是"读 TTF/OTF/TTC、按像素尺寸出灰度位图"这件事的事实标准，
Windows 的 `DirectWrite`、macOS 的 `CoreText`、Android 的 `Minikin`、浏览器的字体栈底层全是它的同类实现。
STB 类单头库（`stb_truetype`）只做 TrueType、不做 CFF/OTF 与 TTC、没有 hinting，
中文 TTC 直接不行 —— 这正是我们的主用例（`NotoSansCJK-Regular.ttc`）。

**为什么是"可选 + 动态"**：
- MCU 档关掉（`QLGL_BUILD_FREETYPE=OFF`），退回 `qlfont_ascii.c` 的内置 4bpp 位图字体（654 行，零依赖）。
- 关掉后 `@font-face` / `font-family: <家族名>` 在**构建期报错**，不会给你一个"运行期才好"的惊喜。
- 它只有 852 KB 动态库，桌面/Android 必然已经有（Android 直连系统 `libft2`），
  静态链进产物是最坏选择（体积翻 4 倍，还不带 CJK 字面）。

**许可义务**：FTL 是 BSD 风格但**带署名条款** —— 二进制分发时必须随附 FreeType 的版权与许可声明
（见 §5.1）。FreeType 是 **FTL 或 GPLv2 双许可**，我们只能走 FTL：MIT 主库和 GPLv2 不能共存。

### 2.2 libjpeg-turbo —— JPEG 解码

| 项 | 内容 |
|---|---|
| 语言 | C 内核 + x86/ARM 的 SIMD（NASM 或 intrinsics） |
| 版本（本机） | 2.1.5（`libjpeg.so.8`，**604 KB**） |
| 代码位置 | [qlimage_jpeg.c](../src/port/qlimage_jpeg.c)（201 行，含 `setjmp` 包装） |
| 我们只用它的 | `jpeg_mem_src`（内存当输入）、强制输出 `JCS_EXT_RGBA`、`jpeg_read_scanlines` |
| 我们不用它的 | 编码器、渐进式以外的扩展、色彩管理（ICC）、12/16 bit |

**为什么是它**：JPEG 的**解码器**是所有格式里最不该自己写的 —— 霍夫曼 + 反量化 + IDCT +
YCbCr→RGB 每一步都有"看起来能出图、实际偏差 2%"的坑，而 libjpeg-turbo 的 SIMD 路径比任何
C 手写快 3~5 倍。反过来 JPEG 的**编码器**我们完全不需要（构建期转码用 `qltext`，不产出 JPEG）。

**为什么包一层 `longjmp`**：libjpeg 的默认错误处理器调 `error_exit` → `exit()`。
在 GUI 库里这等于"用户给了一张坏图，进程没了"。所以 `qlimage_jpeg.c` 里
`jpeg_error_mgr` 换成 `longjmp` 回调用点（注意像素缓冲必须在 `setjmp` **之前**声明，
否则 `longjmp` 回来它的值是不确定的），并把 libjpeg 的原始文案原样带出去，
上层变成一条明确的"这张图解不出来"错误 —— **宁可明确报错，也不给半张灰图**：
libjpeg 对"数据提前结束"的处理是**把缺的行填灰**，我们把它判为失败。

**许可义务**：libjpeg-turbo 是 **IJG / BSD-3 / zlib 三重许可**，选任意一个即可，无传染性。
注意：**不要**把 `jpeg_*` 的符号暴露到公共头文件里 —— 保持"我们只依赖它、
用户的代码不必依赖它"（`qlimage_jpeg.c` 是目前唯一 `#include <jpeglib.h>` 的文件）。

### 2.3 libX11 —— Linux/X11 窗口后端

| 项 | 内容 |
|---|---|
| 语言 | C |
| 版本（本机） | 1.8.13，`libX11.so.6` **1.3 MB**（含 locale/IM 支持） |
| 代码位置 | [qldisp_x11.c](../src/port/qldisp_x11.c)、[qlinput_x11.h](../src/port/qlinput_x11.h)、[qlclipboard_x11.h](../src/port/qlclipboard_x11.h) |
| 我们只用它的 | `XOpenDisplay`/`XCreateWindow`/`XCreateImage` + `XPutImage`（每帧一次；**不用** MIT-SHM：省掉协商与失败回退两种代码路径）、`XNextEvent`、`XLookupString`、`XInternAtom`（剪贴板）、`XrmGetResource("Xft.dpi")`（High-DPI 缩放） |

**为什么是它**：X11 是 Linux 桌面的既成事实，协议层直接用 Xlib 比
SDL/GLFW/SFML 这类"窗口抽象层"代价小得多 —— 那些库每个都要 1~3 MB 并自带事件循环和渲染器，
而我们的定位正是**替代它们**。`XrmGetResource("Xft.dpi")` 那种小事（读 High-DPI 缩放）
也就是 8 行，不值得引入 `fontconfig`。

**为什么不引进 `xcb`**：`libxcb` 更底层、更快，但 API 面大 3 倍、剪贴板与 IM 要自己拼；
我们的窗口层每帧只做一次 `PutImage`，Xlib 的开销在噪声里。

### 2.4 wayland-client —— Linux/Wayland 窗口后端

| 项 | 内容 |
|---|---|
| 语言 | C |
| 版本（本机） | 1.24.0，`libwayland-client.so.0` **72 KB** |
| 代码位置 | [qldisp_wayland.c](../src/port/qldisp_wayland.c)、`src/port/protocols/xdg-shell.xml` → 构建期由 `wayland-scanner` 生成 |
| 我们只用它的 | `wl_display`/`wl_registry`/`wl_compositor`/`wl_shm`/`wl_seat`/`xdg_wm_base`，事件循环用裸 `poll()` |

**为什么是它**：Wayland 的协议没有稳定 ABI 的 C 绑定替代品 —— 客户端协议代码必须由
`wayland-scanner` 从我们**自己仓库里那份 `xdg-shell.xml`** 生成（这也是为什么我们把它 vendor 进
`src/port/protocols/`：不依赖 `wayland-protocols` 包的版本）。

**已知取舍**：**不链接 `xkbcommon`**。Wayland 的 `wl_keyboard.keymap` 我们忽略，
按键直接按 Linux evdev 码映射（`qlinput_evdev.h`），可打印字符按 US 布局近似 ——
代价是非 US 键盘布局在 Wayland 下输入字符不准。这是刻意的：`xkbcommon` 会带来
一个 XML 编译器依赖和数据文件，而我们 99% 的界面是鼠标/触摸。

### 2.5 EGL + GLESv2 —— GPU 后端

| 项 | 内容 |
|---|---|
| 语言 | C（Mesa 实现；厂商驱动闭源） |
| 版本（本机） | EGL 1.5 / GLES 3.2 头文件；`libEGL.so.1` 72 KB、`libGLESv2.so.2` 72 KB（这只是 glvnd 分发壳，**真正的 Mesa 驱动**在 `/usr/lib/x86_64-linux-gnu/dri/`，llvmpipe 数 MB） |
| 代码位置 | [qlgfx_gl.c](../src/port/qlgfx_gl.c)（唯一 `#include <GLES3/gl3.h>` 的文件） |
| 我们只用它的 | GLES 3.0 的极小子集：一个 VAO/VBO + 一个纹理图集 + 三种 `mode` 的着色器分派、`glScissor`、FBO（离屏图层/滤镜）、A8 蒙版的 `R8` 纹理 |

**为什么是它**：EGL/GLES 是**唯一在 Linux、Android、RPi、嵌入式 GPU 上都存在**的图形 API。
不用 Vulkan（驱动覆盖率、代码量都不合适），不用 SDL 的 `SDL_Renderer`（那会把后端选择权交出去，
我们就失去"CPU/GPU 双后端像素级一致"这个卖点）。
`QLGL_BUILD_GL=OFF` 后整个 GPU 路径消失，只剩 CPU 光栅，**行为完全一样**（golden 测试双向对拍）。

**为什么要 GPU 后端**：CPU 光栅在 4K 上填充率吃不消；GPU 路径把整棵树的矩形/圆角/
渐变/图片**合批成一次 `glDrawArrays`**（见 [CSS3覆盖与裁剪](手册/ui/CSS3覆盖与裁剪.md) §22）。

### 2.6 HarfBuzz —— 复杂文字整形（B8）

| 项 | 内容 |
|---|---|
| 语言 | **C++**（对外是纯 C 的 `hb_*.h` 接口） |
| 版本（本机） | 12.3.2，`libharfbuzz.so.0` **1.2 MB** |
| 代码位置 | [qltextshape.c](../src/text/qltextshape.c)（640 行，含内建兜底整形）、[qldl.c](../src/core/qldl.c) |
| 我们只用它的 | **11 个符号**：`hb_ft_font_create_referenced`、`hb_font_destroy`、`hb_font_set_scale`、`hb_buffer_create/destroy/add_utf8/guess_segment_properties/set_direction`、`hb_shape`、`hb_buffer_get_glyph_infos`/`hb_buffer_get_glyph_positions` |

**为什么是它**：整形（shaping）需要 Unicode 数据库（字素簇、连字、字距、阿拉伯呈现形式、
印度语系的音节重排）。这不是"写几百行"能解决的，是**每年都在更新的数据表**。
HarfBuzz 是 Android/Chrome/Firefox/GTK/Qt 的共同选择，MIT 许可，C 接口。

**为什么用 `dlopen` 而不是直接链接**：
1. 这台机器（以及很多发行版的最小安装）**只有 `libharfbuzz.so.0` 运行库，没有 `-dev` 头文件**。
   直接链接会让构建失败，`dlopen` 则"有就用、没有就退回内建"。
2. 它是**可选增强**：拿不到它，文本仍逐码位输出（与 B8 之前逐像素一致）。
3. `dlopen` 天然满足"可替换、可裁剪"，MCU 上 `QL_CFG_HAVE_DLOPEN=0` 一关就整段消失。

CMake 会探测头文件：**有头文件就走直连**（`QLGL_HAVE_HARFBUZZ=1`，编译期用
`_Static_assert` 钉住 `hb_glyph_info_t`/`hb_glyph_position_t` 的布局），没有才走 `dlopen`。
两条路径产物相同（测试 `test_text_shape` 双向覆盖）。

**为什么不用 SheenBidi / ICU**：ICU 一个库 30 MB 起，SheenBidi 只管 bidi 不管整形。
HarfBuzz + fribidi 是最小完备组合。

### 2.7 fribidi —— Unicode 双向算法（B8）

| 项 | 内容 |
|---|---|
| 语言 | C |
| 版本（本机） | 1.0.16，`libfribidi.so.0` **120 KB** |
| 代码位置 | [qltextbidi.c](../src/text/qltextbidi.c)（404 行内建 UAX#9 子集兜底） |
| 我们只用它的 | `fribidi_get_par_embedding_levels_ex` + `fribidi_reorder_line` |

**为什么不用 `fribidi_log2vis`**：它会顺手做**阿拉伯呈现形式替换**（presentation forms），
和 HarfBuzz 的整形重复 —— 两者叠加会把阿拉伯字母变成孤立形（B8 里踩过这个坑）。
所以只取"级别 + 重排"两步，整形完全交给 HarfBuzz。
**为什么需要它**：UAX#9 是纯算法、可以自己写（我们写了 404 行的子集），
但完整实现的边界情况（括号配对、显式嵌入/覆盖、L1 重置）多到不值得重写一遍。

**`dlopen` 的理由同 HarfBuzz**（只有 `libfribidi.so.0`、没有头文件的那台机器）。

**许可**：**LGPL-2.1+** —— 清单里唯一的 copyleft，处理方式见 §5.2。

### 2.8 libm / libdl / libc

- `libm`：`find_library(QL_LIBM m)`，用于 `sqrtf`/`sinf`/`powf`（圆角 SDF、渐变插值、缓动）。
- `libdl`：`${CMAKE_DL_LIBS}`，只在 `QL_CFG_HAVE_DLOPEN=1` 时需要；glibc ≥ 2.34 已并入 `libc`。
- `libc`（glibc / musl）：`malloc`/`memcpy`/`snprintf` 等。

glibc 是 LGPL-2.1 + 链接例外（正常动态链接不受影响）；musl 是 MIT。
**我们没有 `pthread` 依赖** —— 全库单线程，事件循环由用户驱动。

## 4. 明确**不**引入的库（以及我们写了什么替代）

| 需求 | 社区常见选择 | 我们的做法 | 行数 | 为什么能自己写 |
|---|---|---|---|---|
| DEFLATE 解压 | zlib | `qlinflate.c` 自研 inflate（+ 固定/动态霍夫曼、`fail` 语义） | 435 | 写错 = 校验和不过，不会静默出错 |
| PNG | libpng | `qlimage.c::decode_png`（去交错、`tRNS`/`PLTE`/`gAMA`、CRC） | ~389 | 容器只是块拼接，难点已由 inflate 解决 |
| GIF | giflib | `qlimage.c::decode_gif`（自研 LZW，**只取首帧**） | ~278 | 首帧解码 300 行；动画是另一件事，明确不做 |
| BMP / QOI | — | `decode_bmp` / `decode_qoi` | 124 / 306 | 格式本身就是"照文档抄" |
| 位图字体 | FreeType/位图字体库 | `qlfont_ascii.c`（表驱动 4bpp）+ `tools/qlfontgen` | 654 | MCU 档不能带 852 KB 的 .so |
| 文本整形兜底 | ICU | `qltextshape.c` 内建逐码位 + 连字近似 | （含在 640 行内） | 只在没有 HarfBuzz 时兜底，不追求复杂脚本正确 |
| 双向算法兜底 | ICU / SheenBidi | `qltextbidi.c` 内建 UAX#9 子集 | 404 | 纯算法，RTL 常用路径可覆盖 |
| 窗口/输入抽象 | SDL2 / GLFW / SFML | `src/port/qldisp_*.c` + `qlinput_*.h` | — | 我们就是要**替代**它们，不能自己依赖 |
| 2D 渲染器 | Cairo / Skia / pixman | `qlcanvas.c` + `qlgfx_gl.c` | — | 同上；而且需要 CPU/GPU 像素级一致 |
| 字体发现 | fontconfig | `@font-face` + 运行期注册（`ql_font_ft_register_*`） | — | fontconfig 的匹配规则是另一套语义，且要读系统配置 |
| 键盘布局 | xkbcommon | evdev 码直映射（US 近似） | — | 见 §2.4 的取舍 |

**为什么"少一个依赖"值钱**：每一个被砍掉的库，都让"从源码到能跑"的路径少一个可能失败的环节，
也让 MCU 档的体积账保持可控（§7）。

## 5. 许可合规清单（发版前必须过的 4 条）

### 5.1 署名与声明

MIT 主库（[LICENSE](../LICENSE)）本身只要求保留我们的版权声明。但**二进制分发**时还需要随附：

- **FreeType** 的 FTL 许可全文 + 版权声明（FTL 的署名条款要求"文档或随附材料中必须出现"）。
- **libjpeg-turbo**（IJG/BSD-3）的版权与免责声明。
- 其余（X11/Wayland/Mesa/HarfBuzz）都是 MIT 系，同样需要保留声明，但无额外义务。

做法：发版包里附一份 `THIRD-PARTY-NOTICES.txt`，逐库抄它们的 `LICENSE`/`COPYING`。
（**动态链接不等于免除署名义务** —— 免除的是源码开放义务。）

### 5.2 fribidi 是 LGPL-2.1+：三条硬约束

| 场景 | 是否合规 | 说明 |
|---|---|---|
| 默认路径：`dlopen("libfribidi.so.0")` 用系统库 | ✅ | 我们**不分发** fribidi 的代码；用户可自由替换系统库 |
| `QLGL_HAVE_FRIBIDI=1` 直连**动态**库 | ✅ | LGPL 允许动态链接，只要保留"可替换"（用户能换 `.so`） |
| 直连并**静态**链接进闭源产物 | ⚠️ **不合规** | 静态链接 LGPL 要求提供目标文件或重链接手段，闭源分发做不到 |

因此：默认配置永远是 `dlopen` 或动态链接；如果有人要用静态链接，**必须**
`-DQL_FEAT_CSS_BIDI=0`（走内建 UAX#9 子集，功能略减但零依赖）。这条写进了 §5.3 的检查清单。

### 5.3 发版前 checklist

```bash
# 1) 产物里到底链了谁（不允许出现意外库）
readelf -d build/example/example_01_window | grep NEEDED
# 期望：libc libm + 你启用的那几个（freetype/jpeg/X11/wayland-client/EGL/GLESv2）。
#   · 不得出现 libstdc++ / libharfbuzz / libfribidi（走 dlopen 就一个都不该有）；
#   · 没被用到符号的库不会出现（Ubuntu 默认 --as-needed），所以"少一个"不是问题；
#   · libz / libbz2 / libpng / libbrotli 是 FreeType 自己的传递依赖，不关我们的事。

# 2) 静态库形态（libqlgl.a）里不能有第三方符号
nm -g --defined-only build/libqlgl.a | grep -E ' (FT_|jpeg_|hb_|fribidi_|X[A-Z]|wl_|gl[A-Z])' && echo "违规！"

# 3) 确认 fribidi 没有被静态链接
readelf -d build/example/example_01_window | grep -i fribidi   # 应该没有（dlopen 不进 NEEDED）

# 4) MCU 档必须零外部依赖：链接完的 ELF 里不该有任何未定义符号（实测 0 个）
OUT=/tmp/mcu ./test/mcu/build.sh --no-run
nm /tmp/mcu/bench.elf | grep ' U ' && echo "违规！" || echo "OK：零外部符号"
arm-none-eabi-size /tmp/mcu/bench.elf     # 实测 text 144,808 / data 108 / bss 144,368
```

## 9. 闭源商业产品能用吗？（GPL / LGPL 会不会传染）

> ⚠️ **本节是工程与合规层面的分析，不是法律意见。** 真要发版请让法务看一遍
> （尤其 §9.6 的 iOS 场景）。但下面每一条都能在仓库里对着代码/CMake 验证。

**一句话**：**默认配置下不会。** 唯一有 copyleft 的是 fribidi（LGPL-2.1+），
它走 `dlopen` 动态加载、你我都不分发它的代码；其余 6 个库是 MIT/BSD/FTL 系，
只需"保留声明"。真正会出事的只有三种姿势：**静态链接 fribidi**、
**用 GPL 分支的 FreeType**、**把库源码拷进自己仓库**。三种都能靠一个编译开关避开（§9.5）。

### 9.1 先分清两件事：**主库** 和 **依赖**

| 层 | 许可 | 对闭源商业产品的影响 |
|---|---|---|
| QLGL 本身 | **MIT**（[LICENSE](../LICENSE)） | 无。可闭源、可商用、可改、可静态链，只需保留我们的版权声明 |
| 依赖库 | 见 §0.1 | **只有 fribidi 是 LGPL，其余全部宽松许可** |
| 只构建期用到的工具（CMake/Python/GCC/scanner） | — | 无。它们的产物（`.o`/`.a`/生成的 `.c`）不受感染；GCC 有 Runtime Library Exception |

所以问题不是"QLGL 能不能商用"（能），而是"**你链接的那几个 `.so` 能不能闭源分发**"。

### 9.2 FreeType：它是**双许可**，我们永远选 FTL —— 千万别选 GPL

FreeType 发两个许可，用户二选一：**FTL**（FreeType License，BSD 风格 + 署名条款）
或 **GPLv2**。这不是"看你高兴"，而是**你拿到的那份构建选的是哪一个**。

| 情况 | 结论 |
|---|---|
| 用发行版自带的 `libfreetype.so`（Debian/Ubuntu/Fedora/Android/macOS 全是 FTL） | ✅ 闭源商用完全没问题，只需在"关于/第三方声明"里附 FTL 全文 + 版权行 |
| 自己从源码编 FreeType，配置成 FTL | ✅ 同上（静态链接也可以，FTL 没有传染性） |
| 自己编 FreeType 时开了 GPL 分支（`--with-gpl` 之类），或用了某个 GPL 构建 | ❌ **你的整个程序必须 GPL 开源** —— 这才是真正的"传染" |

**核查一行就够**：

```bash
grep -l "License: FTL" /usr/share/doc/libfreetype6/copyright && echo "FTL，安全"
ldd build/example/example_01_window | grep freetype   # 动态库 → 连署名都只需放文档里
```

> 顺带说清：**静态链接 FTL 的 FreeType 不违法**，只是 FTL 的署名条款要求
> "在文档或随附材料中复现版权声明与许可全文" —— 闭源产品里通常就是"关于"对话框里那一页。

### 9.3 fribidi：LGPL-2.1+ 的三条硬约束（本节是重点）

LGPL 允许闭源程序使用它，但要求**终端用户能替换这个库**。落到工程上就是三件事：

| # | 要求 | 我们默认满足吗 | 怎么验证 |
|---|---|---|---|
| 1 | 动态链接 / 动态加载（不是把代码编进你的二进制） | ✅ `dlopen("libfribidi.so.0")`，连 `NEEDED` 都不进 | `readelf -d app \| grep -i fribidi` → **应该没有输出** |
| 2 | 用户能换成自己编的同名库 | ✅ 就是从系统路径 `dlopen`，换 `.so` 立刻生效 | 换掉 `/usr/lib/.../libfribidi.so.0` 试试 |
| 3 | 告知 + 提供该库源码（你没改它的话，指向上游即可） | ✅ 放进 `THIRD-PARTY-NOTICES.txt`，写清版本 + 上游地址 | 见 §5.1 |

**这几种做法会踩线（都在自己掌控内，避免即可）**：

- ❌ 把 `fribidi` 的 `.c` 拷进 `src/` 一起编（= 静态链接，闭源分发做不到"可重链接"）；
- ❌ `-static` 全静态构建、`-Wl,--whole-archive`、LTO 把静态库融进你的可执行文件；
- ❌ 在固件里烧进 fribidi（嵌入式静态固件同样要求提供可重链接的目标文件）；
- ❌ 修改 fribidi 源码却不公开修改（它自己的改动必须仍按 LGPL 发布）；
- ⚠️ 混淆/加壳到"用户无法替换该库"的程度。

**两条常被忽略的免费豁免**：

1. **不分发就不触发。** LGPL 的义务挂在"分发（distribution / convey）"上。
   内部工具、公司内网部署、纯服务端（用户拿不到二进制）—— **一条义务都没有**。
2. **只依赖系统库、不捆绑它** —— 你根本没有"分发 fribidi"，义务仅剩"声明你在用它"。

### 9.4 其余 5 个：宽松许可，只有"署名"义务

| 库 | 许可 | 闭源商用 | 需要做什么 |
|---|---|---|---|
| libjpeg-turbo | IJG / BSD-3 / zlib 三选一 | ✅ | 保留版权与免责声明 |
| libX11 | MIT | ✅ | 保留声明 |
| wayland-client（+ 我们 vendor 的 `xdg-shell.xml`） | MIT | ✅ | 保留声明（xml 文件头里已有） |
| Mesa（EGL/GLES 实现） | MIT | ✅ | 若**捆绑**了 Mesa 的 `.so` 才需要带上声明；用系统驱动则不用 |
| HarfBuzz | MIT（"Old MIT"） | ✅ | 保留声明 |

> 我们没用到任何 GPL/AGPL 的库，也没有一个库是"必须开源你的代码"的。
> 那张 `nm -g --defined-only build/libqlgl.a` 的检查（§5.3 第 2 条）就是用来证明
> **`libqlgl.a` 里没有一个第三方符号** —— 静态链 QLGL 不会把任何库拖进来。

### 9.5 想彻底零 copyleft？一个开关的事

| 目标 | 做法 | 代价 |
|---|---|---|
| **完全不想碰 LGPL**（fribidi） | `-DQL_FEAT_CSS_BIDI=0` | 改用内建 UAX#9 子集（`qltextbidi.c`，404 行）：常用 RTL/数字/混合方向正确，**极端嵌套/显式嵌入的边界情况**可能与完整 fribidi 有差异 |
| 完全不想碰 FreeType | `-DQLGL_BUILD_FREETYPE=OFF`（文本栈自动关） | 只剩内置 4bpp 位图字体，没有任意字号/中文 |
| 完全不想碰任何第三方 | §7 的"最小构建"命令 | 体积 340 KB，零外部依赖（实测） |
| 想静态链接 HarfBuzz/fribidi（例如 iOS/主机游戏机） | 先确认许可：HarfBuzz MIT ✅；**fribidi LGPL ❌**（要么换内建，要么买商业授权，要么动态加载） | — |

一句话记忆法：**MIT/BSD/FTL = 留着声明就行；LGPL = 别编进去、让它能被换掉；GPL = 别碰。**

### 9.6 分平台的现实提醒

| 平台 | 现实情况 | 建议 |
|---|---|---|
| Linux 桌面（动态链接系统库） | 最省事 | 默认配置即可 |
| Windows（MSVC 静态链接） | 静态链接很常见，fribidi 会成问题 | `QL_FEAT_CSS_BIDI=0`，或把 fribidi 编成 DLL |
| Android（APK 里捆 `.so`） | LGPL 允许，但**你就在分发它** | 附 LGPL 全文 + 提供 fribidi 源码（或上游链接 + 版本哈希），别混淆 `.so` |
| **iOS** | 生态以**静态**链接为主；App Store 对"可替换"不友好，LGPL 静态链接在这里最容易出事 | **默认关掉 BIDI**（内建兜底），或改用上游商业授权；HarfBuzz(MIT) 静态链接没问题 |
| MCU 固件（闭源烧录） | 固件无法"重链接"，LGPL 静态链接不可接受 | 我们在 MCU 档**根本不含** fribidi（§7：0 个外部库） |

### 9.7 发版最低动作（三行清单）

1. 附一份 `THIRD-PARTY-NOTICES.txt`：FreeType(FTL) + libjpeg-turbo + X11 + Wayland + Mesa + HarfBuzz
   的版权/许可全文；**若用了 fribidi，加它的 LGPL-2.1 全文 + 上游地址 + 你用的版本号**。
2. 在"关于"对话框里给出一句可读的说明（`MIT` 主库 + "本产品使用了 FreeType / HarfBuzz 等开源组件"）。
3. 跑一遍 §5.3 的四条命令，确认 `NEEDED` 里没有 `libfribidi`/`libharfbuzz`/`libstdc++`。
