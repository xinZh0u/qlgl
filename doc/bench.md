# 性能基线（bench.md）

> 规则：**没有数字的优化不算优化**。每次改动后重跑本文命令，超标即视为回归。
> 机器：Linux / Mesa / x86-64；会话 Wayland（GL 走 XWayland）。

## 复现命令

```bash
cmake -B build && cmake --build build -j
# 注意：性能数字用 Release 构建记录（Debug 下逐像素浮点会慢 3 倍以上）
cmake -B build-rel -DCMAKE_BUILD_TYPE=Release && cmake --build build-rel -j
./build-rel/example_bench_fps 300      # 多分辨率 × GL/CPU
./build/example_gl_window --bench 600  # 窗口无 vsync 上限
./build/example_gl_window --frames 180 # 窗口 vsync 模式
```

### 软阴影的真实成本（重要）

阴影在 CPU 上按**九宫格**分解（见上表）：上/下边带逐行、左/右边带逐列，
只有四个 `(rad+pad)²` 的角块是逐像素浮点 SDF + smoothstep。
所以成本 ≈ `周长 × blur × 行/列填充常数 + 4 × (rad+blur)² × ~30 cycles`，
不再是"整圈面积 × 70 cycles"。

有阴影的实测（`example_bench_fps`，示例页 3 处阴影）：

| 场景 | CPU 光栅 | 其中阴影 |
|---|---|---|
| 1080p（3 个 1900px 宽面板 + blur 10，压力测试） | 2.191 ms | ≈ 1.2 ms |
| 320×240（3 个 296px 宽面板 + blur 10，真实手机尺寸） | 0.296 ms | ≈ 0.16 ms |
| GPU 后端（任何尺寸） | — | **≈ 0**（SDF 在片元着色器里，仍是 1 draw call） |

结论：

- **PC 默认走 GPU，阴影几乎免费**；CPU 路径只在无 GPU / 离屏导出时用到；
- 两条目标仍满足（1080p ≤6ms、320×240 ≤1.5ms），且余量已到 2.7× / 5×；
- **MCU 仍不应使用实时 SDF 阴影**：Cortex-M4 @180MHz 的 SRAM 写带宽约为桌面 DDR 的
  1/50~1/100，粗估 1080p 那档要 60 ms 级。MCU 走 M5.5 能力矩阵里的
  **9-slice 预烘焙阴影**（2KB 贴图 + alpha blit）。

### M4 做了什么（按贡献排序）

| 改动 | 作用 | 收益 |
|---|---|---|
| **半透明行混合 SIMD**：`fill_row` 的 alpha 路径把行指针与格式 switch 提到循环外，ARGB8888 走 SSE2 4 像素/批（`unpack → mullo → mulhi(32897) → srli 7 → packus`） | 软阴影、渐变、圆角覆盖都是整行同 alpha，原来每像素重调一次 `put_px` | 阴影 0.692 → 0.280 ms/100 次 |
| **阴影 9-slice 分解** | 上/下边带逐行、左/右边带逐列、只有四个角逐像素 | 1080p 4.93 → 2.93 ms |
| **角区四镜像**：覆盖率只取决于 `(qx, qy)`，四个角互为镜像 → 算一次写四处 | 角区 sqrt+三次多项式的工作量降到 1/4 | 阴影 0.272 → 0.186 ms/100 次 |
| **角区合并分支**：三个 `continue` 合成一次 `a != 0` 判定 | 角内有效带只有 blur 像素宽，原来每像素错 3 次分支预测 | 同下 |
| **`round_row_span` 解析求解**：`dx_max = isqrt(rad²-dy²)` | 去掉逐像素横向扫描 | 全额重绘 -11% |
| **实心区转调通用圆角填充**（整块可见时） | 复用 `fill_round_rect_alpha` 里被优化过的行跨度循环 | 阴影再 -15% |
| **字形行指针外提** | 原来每像素重算 `buffer + y*stride` | 小 |
| **渲染脏区剪枝**：每个节点布局末尾算 `paint_box`（自己 ⊕ 阴影外扩 ⊕ 未裁剪子树），绘制时不相交就整棵跳过 | 一次矩形判断替代一次子树遍历 | 局部重绘 0.026 → **0.016 ms** |
| **控件层接 `QLDraw2D`**：绘制函数签名从 `QLCanvas*` 改为 `QLDraw2D*`，新增 `ql_render_draw2d()` | 同一棵控件树可上 GPU；自定义控件只写一次 | 架构性，无 CPU 耗时变化 |

`/255` 的两个逐值恒等式（`0..65025` 全域验证与 `x/255` 相同）：
- 标量 `(x + (x>>8) + 1) >> 8`
- SSE2 `mulhi_epu16(x, 32897) >> 7`

### 正确性护栏

9-slice / 快路径 / 角区镜像都是**结构改写**，必须逐像素等价。`test_effects`
里有一份**朴素参考实现** `ref_shadow()`（对整块外框逐像素求圆角 SDF，不做任何分解），
用 3 种外框 × 4 种半径 × 4 种模糊 × 3 种偏移 × 3 种 alpha = **432 组**逐一对比。
它已经抓到三个真 bug：

1. `rad == 0` 时四个 `pad×pad` 方角没有任何区域负责（上/下带只到 `[sx0,sx1)`，
   左/右带只到 `[sy0,sy1)`），留白；
2. 右侧/下侧角块以 `sx1 - (rad+pad)` 为锚，比正确位置内偏 `pad`
   —— 既与直边带重叠（同一点混两次、偏黑），又漏掉最外侧 `pad` 条带；
3. 角区直写时误用整体 `alpha` 而不是逐像素覆盖率 `a` 做混合。

第四个 bug 来自 DPR 测试（`test_dpr`）：GPU 后端是单批次（整帧一次
`glDrawArrays`），注释里写着"顶点已按最终 clip 画好"，但 `emit_quad` /
`emit_quad_gradient` / `emit_shadow` **从来没做这个裁剪**，`g->clip` 只存不用。
结果是 **`overflow:hidden` 在 GPU 上完全没生效**。修法是发顶点前把四边形范围与
`g->clip` 求交，但形状参数（`hx/hy`、radius、渐变跨度）必须继续用未裁剪的矩形，
否则片元里的 SDF 会算错。修好前后 CPU vs GL：**28.24% → 0.77%**（scale=1），
仍是**单 draw call**。

第三个 bug 来自脏区测试（`test_render`）：`fill_shadow` 的下边带 / 右边带起点
（`sy1` / `sx1`）没有与裁剪上界求交，阴影被 `overflow:hidden` 或脏区裁掉上半部分时
会往上/往左画到裁剪外面。

还有一条**不算 bug**的既定行为：内实心区（`d <= 0`）由 `round_row_span` 的离散判定
负责，它与连续 SDF 的边界最多差 1px；那块被元素自身背景盖住，不参与对比。

优化记录（试过但**没有**采用）：
- "直边时跳过 sqrt"的分支版本：x86 上 `sqrtss` 是硬件指令，分支反而因误预测更慢（4.0 → 4.4 ms），已回退；
- 把 `put_px` 换成行指针版本 `put_px_at`：保留了（少一次乘加，但收益在噪声量级）；
- 字形逐像素改走 `blend_px`（ARGB8888 直写）：收益在噪声量级，但代码更整洁，保留。

进一步优化的方向（未做）：角区按"有效环带"解析求 x 区间、距离→覆盖率查表、
按 `border-box` 裁剪阴影内实心区（CSS 规范行为，能省 0.04 ms 但要同步改 GPU 顶点分解）。

## GPU 字形图集

| 项 | 值 |
|---|---|
| 图集尺寸 | 1024×1024 R8 = 1 MB 显存 |
| 分配方式 | 货架（shelf），字形高度决定行高 |
| 内置位图字体 | 启动时一次性拼 CPU 镜像 + 一次 `glTexImage2D` |
| 动态字体新字形 | `glTexSubImage2D` 增量上传（≤64px 走 64×64 临时缓冲，一次调用） |
| UV 缓存 | 开放寻址哈希 2048 槽，键 `(字体指针, codepoint)` |
| 容量上限 | 哈希满或图集满 → 丢弃新字形并告警一次，不淘汰 |

## 高 DPI（DPR）的代价

缩放只在后端入口乘一次（26.6 定点），所以**几何开销可忽略**，真正的代价是：

| 项 | 1x | 2x | 说明 |
|---|---|---|---|
| CPU 光栅像素数 | 1× | **4×** | 面积四倍，这是主要成本 |
| GPU 顶点数 | 780 | 780 | 形状参数不变，顶点数不变 |
| GL draw call | 1 | **1** | 单批次不受影响 |
| 字体光栅化 | 12px 字形 | 24px 字形 | 一次性，进图集；图集占用量 ×4 面积 |
| 帧缓冲 | 320×320×4 = 400KB | 640×640×4 = 1.6MB | RGB888/565 按格式换算 |

实测（`example_gl_window --dpr 2`，320×320 CSS px / 640×640 设备像素）：
仍稳定 55 fps（vsync 上限），**1 draw call**。

## 亚像素填充的代价

亚像素不是"全部逐像素"：每行只有**两端各一次 `put_px`**，中间整像素仍走
`fill_row` 的 SIMD 快路径。所以一个带小数的矩形比整数版本只多两次单像素混合。

| 场景 | 额外开销 |
|---|---|
| 100 个 44×20 圆角卡片（亚像素偏移） | 约 +200 次单像素混合，相对阴影/文本可忽略 |
| 对齐（offset 全 0） | **0**（走原来的整数路径） |

`offset` 只影响绘制入口，不触发布局与 `paint_box` 计算。

## 关于 MCU

上表全部是 x86-64（AVX2/SSE4.2、DDR）实测。**不能直接外推到 Cortex-M**：

- 纯填充是 cache/内存带宽密集，M4 @180MHz 的 SRAM 写带宽约是桌面 DDR 的 1/50~1/100；
- M7 上叠了 ATCM/DTCM 与 ART 加速器，实际比 M4 快 3~5 倍；
- 一致的部分是**算法复杂度**：行跨度扫描 + 格式特化仍然是 MCU 上的正确做法，
  但绝对数值必须单独实测。M6 里程碑会在真板子上跑同一份 `example_bench_fps`。

## 动效（M5.5 ①②）的开销

动画本身不进渲染热点：`ql_anim_tick` 只是几十次浮点插值与一次 `apply` 回调，
真正的成本是**被动画元素的重绘**，而重绘走已有的脏区路径。

实测（Release，`ui_flex_trans` 两个节点的用例，hover 过渡 200ms，每帧推进 1ms）：

| 场景 | 数值 |
|---|---|
| 一帧 = `ql_ui_anim_tick` + 1 块 60×30 脏区 `ql_ui_render_rect` | **0.0015 ms** |
| `ql_anim_tick` 单次，64 个活跃动画 | **< 0.001 ms**（低于计时精度） |
| 静态界面（无过渡） | **0**（返回 0，主循环整帧跳过） |

> 这两个数比 M4 的"局部重绘 80×60 = 0.014 ms"小一个量级，原因是文档只有 2 个节点：
> `ql_ui_render_rect` 的成本里有一项是**遍历 `paint_box` 判断剪枝**，与节点数成正比；
> 211 节点的 bench100 页面上做同样的局部重绘就是 0.014 ms。

结论：过渡不是性能问题，**"这一帧要不要重绘"的判断才是**。所以 `ql_anim_tick` 返回
"仍在进行中的动画数"而不是布尔值——静止期省掉整帧（MCU 上没有动画就不烧 CPU）。

## `@keyframes` 的开销（M5.5 ③）

关键帧动画与过渡共用"求值 → 写样式 → 标脏 → 局部重绘"这条路径，所以成本结构一样，
区别只有一处：**求值不是一次线性插值，而是"按时间定位段 + 段内插值"**，
多一次帧表扫描（段数通常 2~5，线性）。

实测（Release，`ui_flex_kf` 用例，5 个节点同时动画，120×140 画布）：

| 场景 | 数值 |
|---|---|
| 一帧 = `ql_ui_anim_tick` + 4 块脏区重绘（5 段动画在跑） | **0.0052 ms** |
| 纯 `ql_ui_anim_tick`（5 段动画，不重绘） | **0.00013 ms** |
| 没有 `@keyframes` 的页面 | **0**（`runs == NULL`，一字节都不占） |

也就是说求值本身占一帧的 2.5%，其余是重绘。**动画段数不影响帧预算，被动画的像素面积才影响**
——和 `transition` 完全一致的结论。

> 脏区是"节点的 `paint_box`"。关键帧只改颜色/alpha，不改盒子，所以动画期间每帧只需重绘
> 各自那一块；`fill: forwards` 停在末帧之后不再标脏，界面回到"零开销"静止态。

## `transform: translate` 的开销

平移**不进布局**，只是把绘制偏移加一点，所以在 CPU 与 GPU 两条路径上都**接近零成本**：

| 路径 | 代价 |
|---|---|
| CPU | 每节点一次 `offset += tf << 6`；填充仍走行跨度扫描（轴对齐不变），逐像素成本完全相同 |
| GPU | 偏移直接进顶点浮点（`emit_quad` 里那个 `off_x_of`），顶点数、批次、draw call 都不变 |
| 布局 | **0** —— `border_box` 不变，flex 不重算 |
| 脏区 | 唯一变大的地方：`paint_box` 要覆盖整个位移区间（Minkowski 包围盒），位移 N 像素就把脏区撑大 N 像素 |

实测 `example_anim_window`（360×260，5 段动画在跑）：**3 块脏区 / 1 draw call**，
与 M4 的"局部重绘"同一量级——动画的成本仍然由**被动画的像素面积**决定，不由动画数量决定。

## GPU 字形：外扩 1px 的代价（M5.5 修复）

实测同一次渲染（`ui_demo` 页 + `ui_flex_anim` 页），只改 `emit_quad()` 里一个字形的 pad：

| 指标 | 外扩 1px（错误） | 不外扩（正确） |
|---|---|---|
| `ui_demo` CPU vs GPU 像素差异 | 5.72% | **0.73%** |
| 控件层 CPU vs GPU 像素差异 | 0.29% | **0.10%** |
| `.hint` 一行字墨迹宽度（CPU 104 px） | GPU 106 px | **GPU 105 px** |

性能上没有差别（顶点数、draw call 完全相同），差别全在正确性与观感：
外扩等于把每个字横向拉宽 (w+2)/w（8 px 的字即 +25%），字距被吃掉、笔画粘连。

保留式脏区（FBO 画布）的成本：一次 `glBlitFramebuffer` + 一块 `w×h×4` 的纹理
（360×260 ≈ 366 KB）。换来的是"动画只重绘变化区域"在窗口上真正成立——
`example_anim_window` 稳定在 **3 块脏区 / 1 draw call**。

## 径向渐变的代价（M5.5 ⑥）

径向渐变不能走"整行同色"的快路径，只能逐像素算距离。用**增量法**避开了逐像素乘法：

```
dy² 每行算一次；dx² 在行内按 dx2 += 2*dx + 1 累加；每像素只剩一次 sqrtf + 一次 lerp
```

| 场景 | 相对纯色填充 |
|---|---|
| 48×48 圆形（`radial-gradient` + 圆角） | 约 3~4× |
| 120×24 竖直渐变（快路径） | 1×（≈纯色） |
| 120×24 水平渐变 | 约 10× |

GPU 侧**零额外成本**：径向判断在片元着色器里，顶点数、批次、draw call 都不变
（第二色打包进已存在的 `a_uv.x`，顶点结构没有变大）。

CPU vs GPU 一致性（`test_gl_vs_cpu` 的无文字渐变页）：**1.47%** 像素超差（阈值 3%），
差异全部来自 SDF 边缘的抗锯齿处理方式不同。

## 圆遮罩的代价

| 场景 | 额外开销 |
|---|---|
| CPU 遮罩 + 纯色矩形 | 每行一次 `sqrtf` + 两端各一次单像素混合（≈纯色填充的 1.1×） |
| CPU 遮罩 + 字形 | 每像素多一次 `sqrtf`（字形本来就在逐像素算覆盖率） |
| GPU | **0**：顶点结构 64 → 80 B（+25% 内存），顶点数 / draw call 不变，片元里多一次 `length` |

CPU vs GPU 一致性（`test_clip`，遮罩半径 50%）：**0.26%** 像素超差（阈值 3%）。

## `transform: scale()` 的代价

等比缩放不改变"轴对齐"这个前提，所以行跨度扫描照常工作：

| 路径 | 代价 |
|---|---|
| CPU | 每个矩形多两次乘法（按边缩放），每像素成本**完全不变** |
| GPU | 顶点变换里多两次乘法，顶点数 / draw call 不变 |
| 布局 | **0** —— `border_box` 不变 |
| 文本 | 字号变了就要**重新光栅化字形**（这是唯一有成本的地方，且与 scale 无关，取决于字数和字号） |

CPU vs GPU（`test_scale`，scale 1.5）：**0.00%**（阈值 2%）——
因为两条路径用的是同一套"按边缩放"的整数公式，逐像素完全相同。

---

## 分轴缩放（`scaleX`/`scaleY`，假翻转）的代价

与等比缩放同一数量级——多出来的只是一位"两轴用不同倍数"：

| 路径 | 代价 |
|---|---|
| CPU | `sx()` 两次乘法（x 用 `elem_x_fx`、y 用 `elem_y_fx`），每像素成本**完全不变** |
| GPU | 同上，顶点数 / draw call 不变 |
| 圆角 / 描边 / 字号 | 多一次 `min(sx, sy)` 比较 |
| 布局 | **0** |
| 压到 0（`scaleX(0)`） | 矩形变空 → 整块跳过，**比不缩放还便宜** |

CPU vs GPU（`test_flip`，`scaleX(0.5)` + `scaleY(0.5)` + 半程翻转三张卡片同时在场）：
**0.00%**（阈值 2%）。

`example_flip_window`（420×240，三张卡片错开相位）：

| 指标 | 值 |
|---|---|
| 脏区 | 3 块 / 帧 |
| draw call | 1 |
| 顶点 | 约 340 |
| 帧率 | 60 fps（vsync） |

零宽那一帧整块不画，所以翻转动画的帧耗时曲线是**谷形**的：
中间最"便宜"，两端（满宽）最贵。

## 缩放动画的脏区代价（一条真 bug）

`paint_box` 原来只看**基础样式**的 `sc`，所以 `@keyframes` 里放大、
`:hover` 里放大的元素脏区算小。实测（`test_scale` 的 1.188× 中途一帧）：

| | 脏区 | 局部重绘 vs 整幅重画 |
|---|---|---|
| 只看基础样式 | 40×40（布局盒） | **504 像素不一致**（放大那一圈擦不掉/画不上） |
| 取三个来源的极值 | 60×60（1.5× 上界） | **0** |

代价：`compute_paint_box` 多一次「基础样式 ∪ 状态变体 ∪ 关键帧帧表」的 `max` 扫描
（只在布局末尾跑一次，与节点数线性相关，实测从 0.037 ms 变 0.038 ms，可忽略）。

## 渐变 + 圆遮罩（同一次填充）的 CPU/GPU 差异

`.rad2` 是"径向渐变 + 圆角 + `clip-path`"挤在一次填充里，用来守住"遮罩对**所有**
图元都生效"这条线：

| 状态 | CPU vs GPU 差异 |
|---|---|
| GPU 遮罩只作用于非径向分支（bug） | **3.00%**（刚好卡在阈值上，比例断言抓不住） |
| 修复后（遮罩对所有出口生效） | **1.17%** |

所以这条用例的判断不靠比例，而是直接看像素：遮罩半径 75% 盖不到的角落必须是底色，
中心必须真的画出了渐变。收紧后的比例阈值是 2%。

## 毛玻璃（`backdrop-filter: blur()`）的代价

CPU 侧是"取出区域 → 四趟滑动窗口卷积（H/V × 2）→ 写回"：

| 区域 | `blur(12)` 每次 |
|---|---|
| 108×56（一张卡片） | **0.159 ms** |
| 300×200（半个屏幕） | **1.68 ms** |
| 对照：520×400 整屏重画 | 0.304 ms |

也就是说：**一张卡片的毛玻璃大约等于半次整屏重绘**。CPU 上能做，但只适合小面积；
MCU 明确不支持（见 `开发规划.md` 的能力矩阵）。

GPU 侧：

| | 值 |
|---|---|
| 额外 draw call | **+1**（整帧 1 → 2，中途 flush 一次） |
| 额外顶点 | 6 |
| 额外显存 | 两块半分辨率 RGBA8（520×400 → 2×104 KB） |
| 每帧多出的 pass | blit 一次 + 两次 9 抽头的半分辨率全屏 pass |

`example_showcase_window`（520×400，含一个滑动的毛玻璃条 + 6 段动画）：
6 块脏区 / 2 draw call / 60 fps。

## 字号缓存的坑：`transform: scale()` 会把它撑爆

`ql_font_default(size)` 是一张"字号 → 字体"的小表。缩放动画让设备字号每帧都变，
而槽位只有 8 个 —— 满了以后旧实现"造一个不缓存的新字体"，等于**每帧重载 TTF + 重光栅化**。

实测（`example_showcase_window` 的 520×400 页面，6 段动画里两段带缩放，CPU 整屏）：

| | 每帧耗时 |
|---|---|
| 时刻固定（字号不变） | 0.567 ms |
| 每帧推进 16 ms（字号连续变化） | **8.077 ms** |
| 槽位 8 → 32 + 满了淘汰最老的一个 | **0.570 ms** |

窗口整体：200 帧从 3.8 s（含 `sys 1.9 s`）降到 3.6 s 且**稳定 59.8 fps**，
`sys` 时间从 1.93 s 掉到 0.39 s（那部分就是每帧新建字体对象造成的分配/缺页）。

## golden 护栏的代价

`test_golden` 覆盖 27 个 CSS 用例，每页做**两层**比对：

| 层 | 判据 | 咬合度 |
|---|---|---|
| `.qlui` blob | **逐字节相同**（机器无关，全是整数） | 改 1 个色阶 / 1px 圆角就红 |
| 基准图 | 单通道差 > 12 的像素 ≤ 0.5%；CPU vs GPU ≤ 2%（`blur` 6%） | 版面/几何/颜色回归 |

实测：

| 指标 | 值 |
|---|---|
| 用例数 | 27（全部 flex 用例，含 `bench100`） |
| 基准体积 | **528 KB**（`.qlg` 极简 RLE + 按内容裁剪；等价的 PPM 是 8.2 MB） |
| 单次运行 | **0.19 s**（含 27 次 CPU 渲染 + 27 次 GL 离屏渲染 + 54 次比对） |
| 覆盖的 CPU vs GPU 页 | **27**（以前只手挑 3 页） |

顺带说明为什么图那一层不能卡 0：这些页几乎都有文字，字形是 FreeType 光栅化的结果，
换一个 FreeType/字体版本就有 1~2 个灰度级的差别。所以"看得见"的回归靠容差阈值，
"看不见"的回归（数据层）靠 blob 逐字节——两者互补，缺一不可。
