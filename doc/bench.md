# 性能基线（bench.md）

> 规则：**没有数字的优化不算优化**。每次改动后重跑本文命令，超标即视为回归。
> 机器：Linux / Mesa / x86-64；会话 Wayland（GL 走 XWayland）。

## 复现命令

```bash
cmake -B build && cmake --build build -j
# 注意：性能数字用 Release 构建记录（Debug 下逐像素浮点会慢 3 倍以上）
cmake -B build-rel -DCMAKE_BUILD_TYPE=Release && cmake --build build-rel -j
./build-rel/example_bench_fps 300      # 多分辨率 × GL/CPU
./build/example_gl_window --bench 600  # 窗口无 vsync 上限
./build/example_gl_window --frames 180 # 窗口 vsync 模式
```

## 单帧开销（780 顶点，1 draw call，**Release 构建**）

> 顶点数 552 → 570 → 780，是示例页内容在增长（中文字体 → 渐变/阴影 → flex 布局）。
> 跨版本比绝对值意义不大，看"每像素成本"和"是否仍满足目标"。

| 分辨率 | GL CPU 提交 | GL 含 GPU 完成 | CPU 光栅（含阴影） | M4 之前 | 提升 |
|---|---|---|---|---|---|
| 320×240 | 0.025 ms | 0.146 ms | **0.296 ms** | 0.696 ms | 2.35× |
| 800×480 | 0.025 ms | 0.301 ms | **0.697 ms** | 1.854 ms | 2.66× |
| 1280×720 | 0.027 ms | 0.455 ms | **1.370 ms** | 3.169 ms | 2.31× |
| 1920×1080 | 0.030 ms | 0.738 ms | **2.191 ms** | 4.929 ms | 2.25× |

> "无阴影"列已省略：现在示例页有 3 处阴影，去掉它们不代表真实场景。

### 节点级基准（`example_bench_ui`，211 节点 / 480×360 / Release）

```bash
./build-rel/example_bench_ui --iter 3000
```

| 阶段 | M4 之前 | M4 之后 | 目标 |
|---|---|---|---|
| layout（全树） | 0.134 ms | **0.037 ms** | ≤0.1 ms ✅ |
| render（全量 CPU） | 0.975 ms | **0.348 ms** | 见下 |
| render（80×60 局部） | 0.048 ms | **0.016 ms** | 全量的 4.5% |
| hit_test | 0.001 ms | **0.001 ms** | — |

**"100 节点重绘 ≤0.3 ms" 的验收口径**：该页 211 节点全量重绘 0.346 ms，
归一化 **0.166 ms / 100 节点**，已达标 1.8×。`example_bench_ui` 直接打印这个
归一化值（并按它判定 `≤0.3/百节点`），不要拿 211 节点的绝对值去对 100 节点的阈值。

阴影占该页 render 的 **54%**（0.186 / 0.346）；其余是 100 个圆角填充 + 100 段描边 +
100 段文本 ≈ 0.16 ms。

### 软阴影的真实成本（重要）

阴影在 CPU 上按**九宫格**分解（见上表）：上/下边带逐行、左/右边带逐列，
只有四个 `(rad+pad)²` 的角块是逐像素浮点 SDF + smoothstep。
所以成本 ≈ `周长 × blur × 行/列填充常数 + 4 × (rad+blur)² × ~30 cycles`，
不再是"整圈面积 × 70 cycles"。

有阴影的实测（`example_bench_fps`，示例页 3 处阴影）：

| 场景 | CPU 光栅 | 其中阴影 |
|---|---|---|
| 1080p（3 个 1900px 宽面板 + blur 10，压力测试） | 2.191 ms | ≈ 1.2 ms |
| 320×240（3 个 296px 宽面板 + blur 10，真实手机尺寸） | 0.296 ms | ≈ 0.16 ms |
| GPU 后端（任何尺寸） | — | **≈ 0**（SDF 在片元着色器里，仍是 1 draw call） |

结论：

- **PC 默认走 GPU，阴影几乎免费**；CPU 路径只在无 GPU / 离屏导出时用到；
- 两条目标仍满足（1080p ≤6ms、320×240 ≤1.5ms），且余量已到 2.7× / 5×；
- **MCU 仍不应使用实时 SDF 阴影**：Cortex-M4 @180MHz 的 SRAM 写带宽约为桌面 DDR 的
  1/50~1/100，粗估 1080p 那档要 60 ms 级。MCU 走 M5.5 能力矩阵里的
  **9-slice 预烘焙阴影**（2KB 贴图 + alpha blit）。

### M4 做了什么（按贡献排序）

| 改动 | 作用 | 收益 |
|---|---|---|
| **半透明行混合 SIMD**：`fill_row` 的 alpha 路径把行指针与格式 switch 提到循环外，ARGB8888 走 SSE2 4 像素/批（`unpack → mullo → mulhi(32897) → srli 7 → packus`） | 软阴影、渐变、圆角覆盖都是整行同 alpha，原来每像素重调一次 `put_px` | 阴影 0.692 → 0.280 ms/100 次 |
| **阴影 9-slice 分解** | 上/下边带逐行、左/右边带逐列、只有四个角逐像素 | 1080p 4.93 → 2.93 ms |
| **角区四镜像**：覆盖率只取决于 `(qx, qy)`，四个角互为镜像 → 算一次写四处 | 角区 sqrt+三次多项式的工作量降到 1/4 | 阴影 0.272 → 0.186 ms/100 次 |
| **角区合并分支**：三个 `continue` 合成一次 `a != 0` 判定 | 角内有效带只有 blur 像素宽，原来每像素错 3 次分支预测 | 同下 |
| **`round_row_span` 解析求解**：`dx_max = isqrt(rad²-dy²)` | 去掉逐像素横向扫描 | 全额重绘 -11% |
| **实心区转调通用圆角填充**（整块可见时） | 复用 `fill_round_rect_alpha` 里被优化过的行跨度循环 | 阴影再 -15% |
| **字形行指针外提** | 原来每像素重算 `buffer + y*stride` | 小 |
| **渲染脏区剪枝**：每个节点布局末尾算 `paint_box`（自己 ⊕ 阴影外扩 ⊕ 未裁剪子树），绘制时不相交就整棵跳过 | 一次矩形判断替代一次子树遍历 | 局部重绘 0.026 → **0.016 ms** |
| **控件层接 `QLDraw2D`**：绘制函数签名从 `QLCanvas*` 改为 `QLDraw2D*`，新增 `ql_render_draw2d()` | 同一棵控件树可上 GPU；自定义控件只写一次 | 架构性，无 CPU 耗时变化 |

`/255` 的两个逐值恒等式（`0..65025` 全域验证与 `x/255` 相同）：
- 标量 `(x + (x>>8) + 1) >> 8`
- SSE2 `mulhi_epu16(x, 32897) >> 7`

### 正确性护栏

9-slice / 快路径 / 角区镜像都是**结构改写**，必须逐像素等价。`test_effects`
里有一份**朴素参考实现** `ref_shadow()`（对整块外框逐像素求圆角 SDF，不做任何分解），
用 3 种外框 × 4 种半径 × 4 种模糊 × 3 种偏移 × 3 种 alpha = **432 组**逐一对比。
它已经抓到三个真 bug：

1. `rad == 0` 时四个 `pad×pad` 方角没有任何区域负责（上/下带只到 `[sx0,sx1)`，
   左/右带只到 `[sy0,sy1)`），留白；
2. 右侧/下侧角块以 `sx1 - (rad+pad)` 为锚，比正确位置内偏 `pad`
   —— 既与直边带重叠（同一点混两次、偏黑），又漏掉最外侧 `pad` 条带；
3. 角区直写时误用整体 `alpha` 而不是逐像素覆盖率 `a` 做混合。

第四个 bug 来自 DPR 测试（`test_dpr`）：GPU 后端是单批次（整帧一次
`glDrawArrays`），注释里写着"顶点已按最终 clip 画好"，但 `emit_quad` /
`emit_quad_gradient` / `emit_shadow` **从来没做这个裁剪**，`g->clip` 只存不用。
结果是 **`overflow:hidden` 在 GPU 上完全没生效**。修法是发顶点前把四边形范围与
`g->clip` 求交，但形状参数（`hx/hy`、radius、渐变跨度）必须继续用未裁剪的矩形，
否则片元里的 SDF 会算错。修好前后 CPU vs GL：**28.24% → 0.77%**（scale=1），
仍是**单 draw call**。

第三个 bug 来自脏区测试（`test_render`）：`fill_shadow` 的下边带 / 右边带起点
（`sy1` / `sx1`）没有与裁剪上界求交，阴影被 `overflow:hidden` 或脏区裁掉上半部分时
会往上/往左画到裁剪外面。

还有一条**不算 bug**的既定行为：内实心区（`d <= 0`）由 `round_row_span` 的离散判定
负责，它与连续 SDF 的边界最多差 1px；那块被元素自身背景盖住，不参与对比。

优化记录（试过但**没有**采用）：
- "直边时跳过 sqrt"的分支版本：x86 上 `sqrtss` 是硬件指令，分支反而因误预测更慢（4.0 → 4.4 ms），已回退；
- 把 `put_px` 换成行指针版本 `put_px_at`：保留了（少一次乘加，但收益在噪声量级）；
- 字形逐像素改走 `blend_px`（ARGB8888 直写）：收益在噪声量级，但代码更整洁，保留。

进一步优化的方向（未做）：角区按"有效环带"解析求 x 区间、距离→覆盖率查表、
按 `border-box` 裁剪阴影内实心区（CSS 规范行为，能省 0.04 ms 但要同步改 GPU 顶点分解）。

## GPU 字形图集

| 项 | 值 |
|---|---|
| 图集尺寸 | 1024×1024 R8 = 1 MB 显存 |
| 分配方式 | 货架（shelf），字形高度决定行高 |
| 内置位图字体 | 启动时一次性拼 CPU 镜像 + 一次 `glTexImage2D` |
| 动态字体新字形 | `glTexSubImage2D` 增量上传（≤64px 走 64×64 临时缓冲，一次调用） |
| UV 缓存 | 开放寻址哈希 2048 槽，键 `(字体指针, codepoint)` |
| 容量上限 | 哈希满或图集满 → 丢弃新字形并告警一次，不淘汰 |

## 高 DPI（DPR）的代价

缩放只在后端入口乘一次（26.6 定点），所以**几何开销可忽略**，真正的代价是：

| 项 | 1x | 2x | 说明 |
|---|---|---|---|
| CPU 光栅像素数 | 1× | **4×** | 面积四倍，这是主要成本 |
| GPU 顶点数 | 780 | 780 | 形状参数不变，顶点数不变 |
| GL draw call | 1 | **1** | 单批次不受影响 |
| 字体光栅化 | 12px 字形 | 24px 字形 | 一次性，进图集；图集占用量 ×4 面积 |
| 帧缓冲 | 320×320×4 = 400KB | 640×640×4 = 1.6MB | RGB888/565 按格式换算 |

实测（`example_gl_window --dpr 2`，320×320 CSS px / 640×640 设备像素）：
仍稳定 55 fps（vsync 上限），**1 draw call**。

## 亚像素填充的代价

亚像素不是"全部逐像素"：每行只有**两端各一次 `put_px`**，中间整像素仍走
`fill_row` 的 SIMD 快路径。所以一个带小数的矩形比整数版本只多两次单像素混合。

| 场景 | 额外开销 |
|---|---|
| 100 个 44×20 圆角卡片（亚像素偏移） | 约 +200 次单像素混合，相对阴影/文本可忽略 |
| 对齐（offset 全 0） | **0**（走原来的整数路径） |

`offset` 只影响绘制入口，不触发布局与 `paint_box` 计算。

## 关于 MCU

上表全部是 x86-64（AVX2/SSE4.2、DDR）实测。**不能直接外推到 Cortex-M**：

- 纯填充是 cache/内存带宽密集，M4 @180MHz 的 SRAM 写带宽约是桌面 DDR 的 1/50~1/100；
- M7 上叠了 ATCM/DTCM 与 ART 加速器，实际比 M4 快 3~5 倍；
- 一致的部分是**算法复杂度**：行跨度扫描 + 格式特化仍然是 MCU 上的正确做法，
  但绝对数值必须单独实测。M6 里程碑会在真板子上跑同一份 `example_bench_fps`。

## 动效（M5.5 ①②）的开销

动画本身不进渲染热点：`ql_anim_tick` 只是几十次浮点插值与一次 `apply` 回调，
真正的成本是**被动画元素的重绘**，而重绘走已有的脏区路径。

实测（Release，`ui_flex_trans` 两个节点的用例，hover 过渡 200ms，每帧推进 1ms）：

| 场景 | 数值 |
|---|---|
| 一帧 = `ql_ui_anim_tick` + 1 块 60×30 脏区 `ql_ui_render_rect` | **0.0015 ms** |
| `ql_anim_tick` 单次，64 个活跃动画 | **< 0.001 ms**（低于计时精度） |
| 静态界面（无过渡） | **0**（返回 0，主循环整帧跳过） |

> 这两个数比 M4 的"局部重绘 80×60 = 0.014 ms"小一个量级，原因是文档只有 2 个节点：
> `ql_ui_render_rect` 的成本里有一项是**遍历 `paint_box` 判断剪枝**，与节点数成正比；
> 211 节点的 bench100 页面上做同样的局部重绘就是 0.014 ms。

结论：过渡不是性能问题，**"这一帧要不要重绘"的判断才是**。所以 `ql_anim_tick` 返回
"仍在进行中的动画数"而不是布尔值——静止期省掉整帧（MCU 上没有动画就不烧 CPU）。
